## Day A 对应 · IoT 接入与容量（变体 + 网络底层）

### 变体题（换场景考迁移）

**A-V1 · 50W 车联网 T-Box（TCP 私有协议 + 30s 心跳），容量怎么估？**
口径：先抓「和 CoAP 的差异」——① TCP 半开连接多，必须有应用层心跳 + 半开检测；② 吞吐被心跳主导：50W/30s ≈ 1.7 万 msg/s 起步（比业务消息大）；③ 连接内存重算：每连接 FD + 缓冲区 + 会话对象，网关层按连接数横扩；④ 结论格式不变：连接数 → 吞吐 → 单机内存 → 带宽，四算一个不少。

**A-V2 · 智能门锁 200W 台，每台日均 4 条低频消息，瓶颈在哪？**
口径：低频大连接——瓶颈从吞吐转到**连接数 × 会话内存**。200W 并发连接按每连接 4~8KB 算，单机撑不动，必须网关集群 + 会话路由；消息侧反而轻松，削峰需求弱。考的是「你会不会把吞吐思维无脑套到所有场景」。

**A-V3 · 充电桩 10W 台（OCPP/WebSocket），指令下发要求 2s 内到达，下行怎么设计？**
口径：下行比上行难——① 设备上线订阅指令主题 / 平台维护「设备→网关」会话路由表；② 指令带唯一 ID，超时重试 + 幂等（桩侧去重）；③ 离线设备进缓存队列，上线补发；④ 和我简历里 iot-web→EventBus→内嵌 MqttServer 的下行链路是同构的，只是协议换 WebSocket。

**A-V4 · 从 0 设计一个 IoT 接入平台（不限定你的项目），画架构。**
口径：五层说清楚——① 接入层：多协议适配（MQTT/CoAP/TCP），无状态可横扩；② 会话路由层：设备↔网关映射，下行找到人；③ 总线层：EventBus/MQ 削峰解耦；④ 业务层：规则引擎、物模型、告警；⑤ 存储层：最新态（Redis/MySQL）+ 时序（TDengine/ES）分家。每层给一句「为什么这样分」。

### 硬核通用题（往下挖）

**A-H1 · MQTT QoS2 的完整报文序列？**
口径：QoS2 报文序列是 PUBLISH(msgid) → PUBREC → PUBREL → PUBCOMP，并依赖双方状态与 msgid 去重。相比 QoS1，它增加握手、状态保存和重传管理开销；具体延迟、带宽或吞吐差异取决于网络、客户端、Broker和消息大小，不能说固定“两倍”。

**A-H2 · 一条长连接的完整生命周期？半开连接怎么发现？**
口径：TCP 握手 →（TLS）→ MQTT CONNECT（clientId 认证）→ SUBSCRIBE → 数据/PINGREQ 保活 → 断连。半开：网线拔了对端不知道，靠**应用层心跳超时（1.5 倍 keepalive）**主动踢，配合水位拒连保护自己。

**A-H3 · C10K 到 C10M，单机百万连接靠什么？**
口径：四件事——① epoll 事件驱动替代一连接一线程；② 每连接内存按对象、缓冲和会话逐项预算；③ FD、端口、网卡与内存上限算清；④ Reactor 模型让 IO 线程只做短任务。SO_REUSEPORT、内核旁路或 DPDK 只是在特定包速率/CPU 瓶颈下的候选优化，C10M 不等于“必须 DPDK”。

**A-H4 · Netty 的 boss/worker 线程模型？业务能不能跑在 IO 线程？**
口径：boss 只管 accept，worker 管 read/write 和编解码。业务**绝不能**卡 IO 线程——一个慢 SQL 就把整组 worker 拖死，所有连接跟着卡；必须业务池化异步执行。我现网的 R2DBC 异步链路就是这个思想的落地。

**A-H5 · 零拷贝是什么？sendfile 和 mmap 区别？**
口径：传统读写 4 次拷贝 4 次切换；sendfile 数据不回用户态（Kafka 用它做日志段传输）；mmap 把文件映射进用户态可改（适合改内容，如 RocketMQ）。IoT 场景一句话：大文件下发/日志传输才受益，小消息核心收益在批量+页缓存。

**A-H6 · 长连接网关怎么做水平扩展？**
口径：核心是**连接无状态化**——网关不存业务状态，只存「连接在哪」；① 接入层 LVS/Nginx 负载；② 会话路由表（Redis）记录 deviceId→gatewayId，下行按路由转发；③ 扩容就是加机器 + 客户端重连均衡。单点状态是分布式长连接的头号敌人。

**A-H7 · 私有二进制协议怎么设计？**
口径：定长包头（魔数/版本/包体长度/校验和）+ 变长包体；序列化选 Protobuf 而不是 JSON（体积小 3~5 倍、编解码快）；粘包拆包靠「长度字段」解。考的是你不是只会用现成协议。

**A-H8 · TCP keepalive 和应用层心跳的区别？**
口径：TCP keepalive 的默认值依 OS/配置而异，应用层心跳周期可控并可刷新 NAT 映射。NAT idle timeout 只是心跳周期的约束之一：心跳间隔通常要**小于**路径上最短 idle timeout，并同时权衡功耗、流量、误判和服务端压力；不能说 NAT 超时是心跳周期“下限”。

## Day B 对应 · 并发与 MySQL（变体 + 通用深度）

### 变体题

**B-V1 · 不用 Caffeine，自己设计一个有上限的本地缓存，怎么设计？**
口径：四要素——① 容量上限 + 淘汰策略（LRU/LFU/W-TinyLFU，说「频率 + 新近度」就够）；② 过期（惰性 + 定时清理）；③ 并发安全（分段/CAS，读不锁写锁段）；④ 统计命中率。答完反手对比 Caffeine：W-TinyLFU 用 Count-Min Sketch 记频率，防偶发批量污染。

**B-V2 · 设备状态表 5000W 行，怎么分库分表？**
口径：① 按 device_id 一致性哈希分 16 库 × 64 表（设备查询都是点查，天然带分片键）；② 跨片问题：管理台列表走 ES/汇总表，不强查分片；③ 扩容：双写迁移 + 灰度切读；④ 一句话收口：分片键选择 = 90% 查询能不能带上它。

**B-V3 · 高并发写：逐条写、批量写、攒批窗口，怎么选？**
口径：三档——实时性要求高走逐条 + 连接池扛；吞吐优先走批量（MySQL rewriteBatchedStatements、group commit）；可容忍延迟走攒批窗口（如 500ms/500 条 flush）。GIIC 规划量里 ES 写入约 15000 docs/s 是 `5000 msg/s × 3 属性` 反推，不是现网 bulk 实测；MySQL 热表按池化 + 批量思路讲。

### 硬核通用题

**B-H1 · 线程池 7 参数 + 拒绝策略 + 参数怎么定？**
口径：core/max/keepAlive/workQueue/threadFactory/handler（说全 7 个）。定法：CPU 密集 = 核数+1；IO 密集 = 核数 × (1 + 等待/计算)，压测校准；队列要有界，拒绝策略选业务可控的（日志+降级），不用默认 Abort 一扔了之。

**B-H2 · synchronized 和 ReentrantLock 区别？AQS 一句话？**
口径：synchronized JVM 级（锁升级：偏向→轻量→重量），ReentrantLock API 级（可中断/超时/公平/多 Condition）。AQS：volatile state + CAS 改状态 + CLH 双向队列挂起唤醒，一把锁的所有语义都从 state 上长出来。

**B-H3 · volatile 两个语义？happens-before 是什么？**
口径：① 可见性（写立即刷主存、读失效缓存行）；② 禁止指令重排（内存屏障）。happens-before 一句话：定义操作间的可见性偏序，volatile 写先于后续读、解锁先于加锁，JMM 靠它给「无锁正确性」背书。

**B-H4 · ConcurrentHashMap 1.8 怎么保证并发？size 怎么算？**
口径：CAS + synchronized 锁单桶（1.7 是分段锁）；扩容支持多线程协助迁移。size 用 baseCount + CounterCell 分散计数（ LongAdder 思想），不锁全表。

**B-H5 · ThreadLocal 为什么会内存泄漏？**
口径：ThreadLocalMap 的 key 是弱引用、value 是强引用——key 被 GC 后 value 挂在线程上够不着；线程池里线程不死就永久泄漏。修法：finally remove()。能引到我现网：operatorCache 那类「静态容器只增不减」是同族病。

**B-H6 · MVCC 和 ReadView？RR 下幻读解决了吗？**
口径：每行隐藏 trx_id + roll_pointer，undo log 串成版本链；快照读生成 ReadView（活跃事务列表）判断可见性。RR 复用第一次的 ReadView 所以可重复读；快照读防幻读（间隙锁 + 版本链），**当前读**仍要 next-key lock。答「RR 大部分防了，特殊情况（先快照后当前读）仍会幻读」是加分项。

**B-H7 · 索引失效场景，随口 8 个？**
口径：最左前缀断、列上函数/运算、隐式类型转换（varchar 用数字查）、前导 %、OR 两侧有无索引、不等于/not in（视选择性）、优化器判定回表太贵（选择性差）、join 字符集/排序规则不一致。

**B-H8 · redo/undo/binlog 各干什么？两阶段提交？**
口径：redo 保证崩溃恢复（WAL，物理，InnoDB 层）；undo 回滚 + MVCC 版本链（逻辑）；binlog 复制/归档（Server 层）。两阶段提交：redo prepare → 写 binlog → redo commit，保证两份日志一致，否则主从数据漂移。

**B-H9 · 连接池为什么不是越大越好？**
口径：连接数超 DB 核数×2 后，DB 侧线程上下文切换 + 锁竞争反而降吞吐（HikariCP 官方公式：核数×2 + 磁盘数）；池大了还会挤占应用内存。我压测时 MySQL cnf 和应用池是**配套档位表**调的，不是单边拉满。

## Day C 对应 · MQ 与性能（变体 + 通用深度）

### 变体题

**C-V1 · 把 Pulsar 换成 Kafka，怎么选？**
口径：架构差异一句话——Kafka 分区绑死 broker（扩容要搬数据、重平衡），Pulsar 存算分离（broker 无状态、BookKeeper 扛存储，扩容秒级）；海量 topic（百万级）和多租户 Pulsar 赢，生态和团队熟悉度 Kafka 赢。我只在级联/跨服务/长积压链路讲 Pulsar，不把设备上报第一跳说成 Pulsar。

**C-V2 · 消息丢失 / 重复 / 乱序，三大问题通用怎么保？**
口径：不丢：producer confirm + 持久化 + 消费手动 ack 三段全关照；不重：至少一次是常态，**幂等在消费端做**（业务唯一键 + 去重表/Redis setnx）；有序：同 key 进同分区 + 分区内单线程消费，失败要阻塞不能跳过（不然后面全乱）。

**C-V3 · 队列积压打满磁盘怎么办？（不限于你那个 155GB）**
口径：先止血再根治——① 降级上游/限流，保 DB 和消费端不死；② 加消费者横向扩（前提分区数够）；③ 跳过可丢消息（按时间戳 offset 追尾）；④ 根治：下游容量重估 + 背压（消费端限速反推生产端）。155GB 只作为 ES NFS 写慢导致 elasticsearch-buffer 积压的案例收口，不归因到外部 MQ。

### 硬核通用题

**C-H1 · Pulsar 三件套架构？为什么扩容不用搬数据？**
口径：Broker（无状态计算层，服务 topic）+ BookKeeper（bookie 集群，ledger 存储层，条带化写多副本）+ ZooKeeper（元数据）。数据在 bookie 不在 broker，所以 broker 扩容 = 加机器接管 topic 所有权，秒级，不搬一个字节。

**C-H2 · Kafka 高性能四个来源？**
口径：顺序写（磁盘 append 追 SSD 随机写）、页缓存（读写都走 OS cache，不挤 JVM）、零拷贝 sendfile、批量+压缩（攒批摊薄 RPC）。面试官想听「性能不是玄学，是四个机制各出一分力」。

**C-H3 · EventBus / 进程内 MQ 和外部 MQ 的边界？什么时候不能只用进程内？**
口径：进程内快但**不持久、不跨节点、进程死就丢**；外部 MQ 适合跨服务、长积压、削峰和持久化。我的现网边界是：设备上报第一跳先在 iot-server 解码，进 EventBus 做进程内分发，再落 ES/MySQL；Pulsar 只讲级联、跨服务等已证链路，不能说“落 ES/落库前过 Pulsar”。

**C-H4 · 性能优化的通用方法论（不限于你的案例）？**
口径：四步——① 度量先行（没数字不谈优化）；② 分层定位（系统→中间件→应用，二分缩小）；③ 单点假设、改一个变量验证；④ 复测 + 回归（防按下葫芦浮起瓢）。任何案例都能套这个壳，这是我 ES 写慢 / OOM / 连接打满三个案例的公共骨架。

**C-H5 · 压测怎么避免「压了个寂寞」？**
口径：四个真实度——数据真实（不是全同参）、行为真实（心跳/上报/下行混合）、链路真实（全链路不是只压单点）、水真实（影子表或压测标记，别污染生产）。压完必须给容量水位线（如 70% 拒连阈值），不能只报「压到多少」。

## Day D 对应 · JVM 与故障链（变体 + 通用深度）

### 变体题

**D-V1 · 不是本地缓存，是 Redis 大 key / 热 key，怎么排查？**
口径：大 key：`redis-cli --bigkeys` / 内存分析工具，危害是慢查询阻塞 + 网络放大；拆（hash 分桶）+ 异步删（unlink）。热 key：监控命令统计 / 客户端采样，本地二级缓存 + key 加随机后缀打散。

**D-V2 · CPU 100% 的排查链？**
口径：top 找进程 → top -Hp 找线程 → printf %x 转十六进制 → jstack 抓栈对线程号 → 区分：业务死循环 / GC 线程（jstat 看是不是 GC 打满）/ 锁竞争。再深一层上arthas profiler 火焰图。

**D-V3 · 三类 OOM 的排查路径分别是什么？**
口径：① 堆 OOM：jstat 趋势 → dump → MAT Dominator（我的 operatorCache 案例）；② 元空间 OOM：动态类生成（CGLIB/Groovy），看 loaded classes 趋势；③ 堆外/DirectMemory OOM：NMT 或 pmap 对账，Netty/IO 缓冲是惯犯。答出「OOM 不止堆」就已经超过 80% 候选人。

### 硬核通用题

**D-H1 · G1 核心机制 + 调优三件事？**
口径：Region 化分代、回收价值优先（Garbage First 得名）、SATB 并发标记。调优三件事：① 别设 Xmn（G1 自己算 young）；② MaxGCPauseMillis 别乱给（给小了 young 被压、mixed 次数变多，反而更糟）；③ IHOP 默认 45%，老年代分配速率高时下调提前 mixed。GIIC 32G 是 15W 容量规划线，不是 OOM 现场。

**D-H2 · CMS / G1 / ZGC 各一句话适用？**
口径：CMS 使用并发标记清除，存在碎片与并发失败风险，较新 JDK 已移除；G1 用 Region 和停顿目标在吞吐、停顿间折中；ZGC 通过并发搬迁、着色指针/读屏障降低停顿。适用堆范围、停顿和吞吐代价都依 JDK 版本、负载、对象分配、硬件与参数实测，不能固定成“4~32G、<1ms、TB级、损失5~10%”。

**D-H3 · Full GC 常见原因，随口 6 个？**
口径：老年代真满（泄漏/缓存无界）、元空间压力、显式 System.gc()、promotion failed / 担保失败、大对象直接进老年代等都可能触发 Full GC。Direct buffer 接近上限时可能触发引用处理或回收尝试，失败通常报 `Direct buffer memory` OOM，不把它写成确定的 Full GC 原因。

**D-H4 · jstat/jstack/jmap/jcmd 各干什么？线上 dump 的安全姿势？**
口径：jstat 看分代趋势（-gcutil 1s）；jstack 看线程/死锁；jmap -histo 看对象分布（:live 会 STW，谨慎）；jcmd 全能（GC.heap_info/Thread.print/VM.flags）。线上安全姿势：先 histo 后 dump；dump 用 gcore 或 jmap -F 兜底；大堆 dump 前先确认磁盘和 STW 影响——这就是我「12GB dump 拿不出来」案例的现场处置逻辑。

**D-H5 · 容器里 JVM 的内存账怎么算？**
口径：limit ≠ 堆。堆 + 元空间 + 线程栈（线程数×1M）+ 堆外 Direct + JIT 代码缓存 + 本地库，全部加起来 < cgroup limit，否则被 OOMKiller 无声杀掉（kill -9 都没日志）。JDK11 默认感知容器，但显式 Xmx 和 MaxRAMPercentage 择一，别混用。

**D-H6 · 「只增不减」类内存泄漏，通用怎么发现和止血？**
口径：发现：jstat Old 区爬坡不回落 + dump/histo 对比两个时点；方案：找出写入路径，增加容量上限、过期、失效和水位告警。本项目已完成定位并提出有界缓存方案，补丁待 Gerrit 正式流程合入，暂无复测收益。

## Day E 对应 · 通用系统设计 + 软素质（录音日兼防突袭）

> Day E 本来是抽题+录音日，这一节当「被突袭时的底牌」，每天不用全过，周末过一遍。

**E-1 · 幂等方案，随口 5 种？**
口径：唯一索引/唯一键、Redis setnx+过期、状态机（只允许合法迁移）、token 机制（先领后交验）、乐观锁 version。收口：选型看调用方能不能配合拿 token，不能就靠服务端唯一约束兜底。

**E-2 · 分布式锁三种实现对比？**
口径：Redis setnx+过期（快，但锁过期+业务没完的续期问题，RedLock 争议提一句）；ZooKeeper 临时顺序节点（公平、会话断自动释放，性能低）；DB 唯一约束（最土最可靠，低频场景够用）。ERP 项目只讲已证四件套：分布式锁、幂等、唯一约束、状态机；具体组合和先后顺序待证。

**E-3 · 限流四种算法？**
口径：计数器（窗口突刺）、滑动窗口（平滑）、漏桶（恒定速率整流）、令牌桶（允许突发+速率上限，最常用）。分布式限流用 Redis+Lua。长连接场景的变体是**水位拒连**——连接层限流；90% 是复盘文档口径，追问配置来源时要回现场配置/压测记录核对。

**E-4 · 熔断降级舱壁，三个词各一句话？**
口径：熔断 = 依赖挂了快速失败别拖死自己（三态： closed/open/half-open）；降级 = 有损服务保主干（关非核心、读缓存兜底）；舱壁 = 线程池/信号量隔离，一个依赖打满不连坐。

**E-5 · 你的项目流量 ×10，第一件事干什么？**
口径：**先说「不猜，先看水位」**——连接数/堆/CPU/ES 写/DB 各层水位拉出来，找最先打满的那层；然后按瓶颈给方案（接入层横扩 / 存储拆分 / 队列削峰）。答「第一件事是加机器」直接暴露没扛过事。

**E-6 · 「你最大的技术失误是什么？」（软素质必考）**
口径：用 OOM 案例讲已完成定位、但补丁待 Gerrit 正式流程合入；若“心跳参数调小导致订阅风暴”没有本人可核对证据，就不作为真事展开。可讲的教训是：任何缓解动作先做影响面推演、小流量验证和复测，再声称闭环。
