## 二、"实战→概念"对照表（核心交付物）

你的问题不是"没学过"，是**做的时候用的是 jetlinks/EMQX 的黑话，面试官问的是行业标准黑话**。缺的是一张映射表 + 几个有标准答案的小概念。逐条过：

| 你做过的（实战语言） | 面试官问的（标准术语） | 一句话标准答案 |
|---|---|---|
| EMQX 上看到设备频繁掉线重连 | MQTT QoS 等级与遗嘱消息 | QoS0 至多一次/QoS1 至少一次(可能重复,靠 DUP+msgid 去重)/QoS2 恰好一次(四步握手)；LWT 遗嘱消息=客户端异常断开时 Broker 代发的下线通知 |
| jetlinks 里配过的"设备属性/功能" | 物模型（属性/服务/事件） | 属性=可读写状态、服务=可调用指令、事件=设备主动上报；本质是设备能力的结构化描述，是规则引擎和影子机制的基础 |
| 你没明确用过但 jetlinks 里有 | 设备影子 | 云端存一份"期望值(desired)+上报值(reported)"的 JSON，设备离线也能下发配置、上线后对比差异同步——解决弱网下状态不一致 |
| 设备网关/协议包 | 协议适配与网关模式 | 网关协议转换(TCP私有协议→平台标准格式)、多设备复用一条连接、边缘侧就近处理 |
| 配过规则转发 | 规则引擎 | SQL 式过滤+转发(MQTT→Kafka/DB/HTTP)，你做过的 EMQX webhook 转发 Pulsar 就是实例 |
| 折磨你两周的订阅表泄漏 | MQTT 会话与共享订阅 | cleanSession/持久会话决定离线消息保留；共享订阅($share/group/topic)是 EMQX 在多消费者间负载均衡的机制——你的泄漏根因就是持久会话的订阅表只增不减 |
| 麒麟离线交付 | 云边协同/断网自治 | 边缘节点本地闭环运行(断网自治)、恢复后数据回传(补传)、云端统一下发配置——你是这个模式的生产级落地者 |
| ZLMediaKit nodePort | 流媒体信令与数据面 | RTSP/RTMP/GB28181 控制信令 + RTP/FLV 数据流分离，监控视频回传的标准架构 |
| MinIO | 设备数据对象存储 | 海量固件包(OTA 分发)、视频录像、遥测归档的标准后端 |

**背法**：不是背答案，是拿右列术语去重讲一遍左列你真做过的事——每个概念 30 秒，落在具体事上，面试官反而觉得你"有体系又有实战"。

## 三、必须能白话讲清的 6 个概念边界题（1 天能过完）

1. MQTT vs CoAP vs HTTP：长连接推 vs UDP 低功耗 vs 请求响应；谁适合海量低功耗设备。
2. QoS1 为什么可能重复、QoS2 为什么慢：消息 ID + PUBACK / 四报文握手的取舍。
3. 设备影子解决什么问题：弱网/离线下的状态同步与配置下发。
4. 一机一密 vs 一型一密 vs 证书认证：安全性 vs 生产成本的取舍。
5. OTA 灰度怎么做：按设备分组分批 → 版本校验 → 失败回滚 → 断点续传。
6. 时序数据库为什么不用 MySQL：写入吞吐、按时间分区、降采样、TTL——遥测数据的读写模式完全不同。
