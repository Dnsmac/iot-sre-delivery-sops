### A2 90 秒全链路（背 [`口述稿/W1-全链路.md`](口述稿/W1-全链路.md)）

顺序固定：**设备谁连 → 上报走哪 → 会话/下行 → 我改什么 → 压测一句**。要点：

```text
设备 → MQTT 1883 → MetalLB VIP → nginx TCP 透传 → iot-server 内嵌 MqttServer（JVM 监听，不是 EMQX）
clientId=设备ID，MySQL 认证；TCP 长连接在 Pod 内 localSessions；Redis 写 connectionServerId 做集群路由
PUBLISH → 内置 MQTT 解码 → DeviceMessageConnector → EventBus → ES(时序)/MySQL(最新态)/Redis(限流路由)
   —— 不是先进 Pulsar；Pulsar 用于级联等异步链路
下行：API 打到无会话 Pod → 查 Redis connectionServerId → 集群 RPC 转到持会话 Pod → MQTT 下发
我改最多的是 iot-server；GIIC 压测负责协议/网关段；平台整体方案不是 owner
```

### A3 压测 · 30 秒（被问「做过压测吗」）

> 我们有一条 **GIIC CoAP-TCP** 接入。目标 **15 万在线**，5 台压测机各 3 万线程。优化前大概 **5 千**就 Login 超时、Sink 断流，中期卡在约 **14 万**。我负责协议/网关侧：连接模型拆成 **per-connection**、L1 热缓存、Token 改 Redis、Login 写路径减负。现在 **15 万能稳住**，连续长稳 **96 小时（4×24h）**，超过内部 **72h** 验收节点。平台整体方案我不是 owner，这段链路的改造和验收闭环是我负责的。

### A5 红线（说了就扣分，背下来）

## C. 必背答案（全文背诵版 · 15 题）

> 每题 40~60 秒口述量。面试前一天只背 A 区 + 本区。

### C1 介绍一下 IoT 平台架构（90 秒）

> 设备通过 MQTT TCP 1883 连到我们 MetalLB VIP，由 iot-web 的 nginx 做 TCP 透传，进到 iot-server Pod 里内嵌的 MqttServer——JVM 线程在 Pod 里监听 1883，不是独立 EMQX Broker。连接时用 clientId 当设备 ID，从 MySQL 拿产品和密钥做认证。TCP 长连接驻留在 Pod 内存的 localSessions，同时往 Redis 写 connectionServerId 做集群路由。设备 PUBLISH 之后先进内置 MQTT 解码，再经 DeviceMessageConnector 发到 EventBus，不是先进 Pulsar；持久化上，ES 存时序、MySQL 存最新值和在线状态、Redis 做限流和路由，级联等场景才用 Pulsar。下行时，API 打到没有该设备会话的 Pod，会查 Redis 的 connectionServerId，经集群 RPC 转到持有 TCP 的那台，再 MQTT 下发。我日常改最多的是 iot-server，压测方面最近负责 GIIC CoAP-TCP 15 万级长连接优化。

### C2 压测规模多大、你怎么证明？

> 目标 15 万在线，5 台压测机各 3 万线程，服务端约 4 节点，走 CoAP-TCP。优化前大概 5 千就 Login 超时、Sink 断流，中期卡在约 14.3 万。到 7 月下旬同规模已经连续长稳 96 小时，也就是 4×24h，超过内部 72h 验收节点。证据是 JMeter Dashboard 截图，5 个应用各 3 万线程水位平稳。

### C3 为什么卡在 14 万？

> 不是单点机器不够，是三层叠在一起：一是全局单管道 Sink 背压，单连接慢会拖累全网关；二是 Login 热路径写 configuration 放大，把 DB 和连接池打满；三是跨节点 L1 Token 不一致会误杀合法连接。我按连接拆队列、把 Token 权威源迁到 Redis、Login 写路径减负，才把 14.3 万的卡点推过去。

### C4 L1 缓存和 Token 异步批写怎么保证不丢不错？

> L1 只是热缓存，miss 或校验不匹配会回 Registry/Redis 权威源重新加载，跨节点不靠纯本地。Token 改成 L1 先回 200、权威源异步批写，挂了靠 reload 和宽限兜底；后期 r8 解决的是队列跟不上和日志风暴，不是改协议语义。

### C5 为什么还要调 Nginx、内核和 MySQL？

> 15 万长连接不是只改业务 jar。入口不调，代理侧会先耗尽出站端口，报 errno 99，后端 JVM 还活着入口先挂；压测机少 IP 还会打爆单后端，所以粘滞要用源 IP+端口。库侧要按内存选生产档、连接池和应用池联动。应用、入口、库三层缺一层，高峰都会露底。

### C6 KEYS 为什么改 SCAN？

> KEYS 是阻塞式全量扫键，压测时统计前缀一扫就拖慢 Redis 主线程。公共工具改成 SCAN 优先、失败再 KEYS，把尖刺消掉。

### C7 ES 写 NFS 是怎么定位的？

> 10 万级压测时主机 CPU、内存都没打满，但 ES 的 write 线程在排队——这是典型"等 IO"而不是"算力不够"。查 data 路径发现 ES 数据盘挂在 NFS 上，bulk 超时后 iot 侧 elasticsearch-buffer 积压，每 pod 约 30G、合计约 155GB，属性历史落后实时态 2~3 小时。我们协助做了热索引 replicas=0、refresh 调优，长期建议是数据盘换本地 SSD，应用侧防止整批失败整批重试。

### C8 OpenAPI 压测为什么上不去？

> 五接口里拓扑查询约 78 TPS，E2E 读写只有 13~20 TPS，目标都是 100。拆开看是两类问题：拓扑是缓存 TTL 只有 1 秒，miss 后要重查多表和 registry；E2E 是每次调用重复解析大物模型，而且大头在等设备 MQTT 回包。我落地了物模型元数据的 Caffeine 缓存加 single-flight，拓扑缓存 TTL 配置化，并用分段耗时说明哪些必须端侧配合。

### C9 OOM 是怎么排查的？

> 现象是 Full GC 风暴、服务卡死。先用 jstat 看到 Old 区 96% 以上、Full GC 次数几乎等于 Young GC，说明有大对象常驻；dump 后用 MAT 的 OQL 数出 5050 个设备操作器对象，每个 retained 3 到 15 兆，合计约 5.66GiB，占 8G 堆的 78%。根因是物模型缓存无界。我已提出 Caffeine 上限/过期、注销失效等有界方案；补丁待 Gerrit 正式流程合入，暂无复测收益。

### C10 MQTT 拒连一定是连接打满吗？

> 不一定。我们遇到过 CONNECTION_REFUSED_SERVER_UNAVAILABLE，其实是 JVM 堆剩余低于水位线，网关主动拒连做自我保护；而且它在 Vert.x event loop 上调了 System.gc，把事件线程阻塞了 30 多秒。所以先看堆、看容器内存限制，再谈连接规模。

### C11 麒麟离线交付难点？

> 完全离线意味着物料必须闭包、版本不能断链。我做了三件事：26 处死 IP 收敛到两个 settings.env；统一镜像清单，部署前调 Harbor API 预检，把"Pod 起不来才发现"前移到部署前；部署脚本处理依赖顺序、Job 幂等、rollout 等待和失败显式退出。现场还排过 ARM64 64KB 页、Pulsar JWT Secret 缺失、containerd 私库这些坑，最后实施人员只改两个环境文件、跑两个脚本就能重复验收。

### C12 ERP 当前怎么答？

> 历史材料记录 300+ 商户、日峰值约 3000 万，并提到分布式锁、幂等、唯一约束、状态机四类机制；具体接口、回调、消费端、状态流落点与组合待本人核对。“零超卖”“零重复扣款”和 99.9%+ 没有当前证据，不主动深讲。

### C13 Seata AT 和本地消息表怎么选？

> 这是通用选型：强一致、小事务可评估 Seata AT；最终一致、可重放场景可评估本地消息表。不能绑定成 ERP 已落地事实。

### C14 供应商慢响应怎么隔离？

> 这是通用隔离方案：可评估 MQ、超时、熔断、并发上限和死信重试；ERP 是否使用这些组件待本人核对。

### C15 你最大的优势是什么？

> 我是 11 年 Java，能在业务链路和基础设施之间来回切换：既写过订单、库存这类高并发业务，也在 IoT 平台做过连接治理、ES/Redis 排障和 K8s 离线交付。遇到性能问题，我的习惯是先分层定位——是存储 IO、缓存、等设备回包还是代理连接池，再决定改代码、改配置还是换基础设施，而不是只会加机器。
