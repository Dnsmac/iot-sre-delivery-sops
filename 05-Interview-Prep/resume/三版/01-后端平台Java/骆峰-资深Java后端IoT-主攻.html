  • GIIC 15 万压测（CoAP-TCP）：改连接模型（队列、进程内 L1 缓存、Token 迁 Redis、批量落库），Nginx 按源 IP+端口做粘滞，让连接在 iot 节点间更均匀。Linux 内核参数、MySQL my.cnf 也一起调整优化。压测前几千在线就挂，最终 15 万设备连续跑满 4 天。
  • 20 万级设备压测（docker）：Pulsar 租户/命名空间/分区，消费者和分区数据需要对上（多消费者不能抢同一分区），ES 热索引 refresh、副本和应用写入缓冲也要一起看。规模上来时线上 OOM 过，定位后扩容调参，压测侧 20 万设备跑满 7 天（7×24h）。
  • 10 万级设备压测（k8s）： 写入链路 CPU 没打满但 ES write 线程堵死——data 盘走 NFS，IO 跟不上，单 Pod 消息堆到几十 G，属性历史比实时慢两三个小时。另排查过 NodeLocal DNS 偶发超时、Redis 代理和 R2dbc 拿连接慢，调池参数后写入恢复。
  • OpenAPI 压测有几条核心接口不达标：拓扑侧约 78 TPS，端到端读写只有十几 TPS。主要是缓存 TTL 太短、物模型节点反复解析；加了 Caffeine 元数据缓存和合并加载后改善。
  • 线上 OOM及BUG排查 ： 先看监控/链路/日志，如无法定位再 jmap dump，用 Eclipse MAT 分析，尽量找到具体配置或代码。 使用 MAT 看过一次 OOM 场景 ，5050 台设备物模型缓存无上限，单占堆 78%（Dominator 约 5.66GiB），改成 Caffeine 限大小和过期；ES 慢写、Redis 超时也是同一套思路，先分层再落到配置或代码。
  • 麒麟 V10 离线 K8s（v1.26，X86+ARM64）：K8s/依赖/中间件（Harbor、Pulsar、Redis、MinIO）离线包；脚本一键部署 IoT 与可观测子系统，多现场复用。
