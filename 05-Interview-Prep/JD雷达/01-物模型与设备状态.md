# 01 物模型与设备状态

> W1-D2 · 三行定稿（可背）

## 定义

物模型（TSL）用 **属性 / 事件 / 服务（functions）** 描述设备能力；设备状态是在线离线与最新属性等运行态，通常与物模型字段对应。

## 现网有没有

**有。** 产品侧配置物模型 JSON 存 MySQL；实例可带 `derive_metadata`（超级设备节点）；上报经协议解码成 `DeviceMessage` 后进 EventBus，最新值/在线写 MySQL，历史进 ES/TD。GIIC 线有 **双模型**：`metadata`（平台）+ `third_metadata`（GIIC），经 `GiicMetaMessageConvertUtil` 映射后再进同一套 DeviceMessage。

## 面试 30 秒

> 我们平台用 JetLinks TSL 描述产品能力：properties/events/functions 存 `dev_product.metadata`。设备上报不管 MQTT 还是 GIIC CoAP-TCP，解码后都是 DeviceMessage，走 EventBus 分流——时序进 ES、最新态进 MySQL、在线状态写 `dev_device_instance.state`。GIIC 还有 third_metadata 映射层，但下游不另搞模型。我主责接入解码和压测，物模型配置是平台能力，我能讲清链路和字段分工。

## 我们项目怎么做

### 1. 物模型存哪、长什么样

| 存储 | 表/字段 | 内容 |
|------|---------|------|
| 产品模型 | `dev_product.metadata` | 标准 TSL JSON：properties / events / functions |
| GIIC 三方模型 | `dev_product.third_metadata` | GIIC 侧能力描述 |
| 设备派生模型 | `dev_device_instance.derive_metadata` | 超级设备节点独立模型 |
| 字段映射 | `dev_metadata_mapping` | GIIC ID ↔ 平台 property/function ID |
| Things 扩展 | `th_thing_type_def`、`thing_property_metric` | 物类型与衍生指标 |

发布产品时 `LocalDeviceProductService.validateMetadata()` 用 `JetLinksDeviceMetadataCodec` 做结构校验，再 `registry.registerProduct()` 注册到运行时。

### 2. 上报怎么对齐物模型

```text
CoAP-TCP / MQTT / HTTP
  → *DeviceGateway
  → ProtocolSupport.getMessageCodec().decode()
  → [GIIC] GiicCoapTcpDeviceMessageCodec
       ├─ decodeByMetadataMapping（third_metadata + metadata → GiicMetaMessageConvertUtil）
       └─ 失败则 GiicMessageConverter 按 path 硬编码兜底
  → ReportPropertyMessage / EventMessage / FunctionInvokeMessageReply …
  → DeviceGatewayHelper → DeviceMessageConnector → EventBus
       topic: /device/{productId}/{deviceId}/message/property/report
              /device/{productId}/{deviceId}/message/event/{eventId}
              /device/{productId}/{deviceId}/online|offline
```

**校验边界（面试诚实说）**：

- **下行功能调用**：`DeviceMessageSendLogInterceptor` 会按 `PropertyMetadata.getValueType().validate()` 校验参数
- **上行属性上报**：一般 **不做严格类型拒绝**，主要靠物模型做存储/展示/规则匹配
- 超级设备「能力/节点」是 GIIC + Meta **双模型**，不是 AWS Thing Type 标准

### 3. 设备状态怎么维护

| 状态 | 来源 | 落库 |
|------|------|------|
| online | `DeviceOnlineMessage`（Login/Heartbeat/会话注册） | `dev_device_instance.state=online` |
| offline | 断连 / 心跳超时 / `DeviceOfflineMessage` | `state=offline`，`offlineTime` 写 config |
| 最新属性 | `ReportPropertyMessage` | MySQL latest（可选 `dev_lst_*`）+ 时序库历史 |
| 路由态 | 会话创建时 | DeviceOperator config：`connectionServerId`、`sessionId` |

GIIC 路径映射（`GiicMessageConverter`）：

- `/.sys/heartbeat`、`/.sys/login` → `DeviceOnlineMessage`
- `/.sys/data` → `ReportPropertyMessage`
- `/event/*` → `EventMessage`

### 4. 和 AWS IoT 物模型 / Shadow 的差距

| AWS 概念 | 我们项目 |
|----------|----------|
| Thing Type / TSL | ✅ `dev_product.metadata` + JetLinks Codec |
| reported state | ✅ 属性上报 + 可选 MySQL latest |
| desired state | ⚠️ 仅有配置字段 / `DeviceConfigKey` 写属性，**无版本化 Shadow 文档** |
| delta / version | ❌ 无 |
| 上报强类型校验 | ⚠️ 下行严、上行松 |

**成熟方案理解（我们没有的）**：AWS Device Shadow 用 JSON 文档维护 `desired` vs `reported`，带 version 乐观锁；设备离线时云端改 desired，上线后 delta 下发。我们等价物是 **写属性指令 + 配置缓存 + 最新属性表**，够用但没有 Shadow 语义。

## 面试追问速答

**Q：GIIC 和平台物模型不一致怎么办？**  
A：`dev_metadata_mapping` + `GiicMetaMessageConvertUtil` 做 ID/结构映射；映射失败走 path 硬编码兜底。

**Q：最新值和历史怎么分？**  
A：EventBus 订阅分流——`TimeSeriesMessageWriterConnector` 写 ES/TD 历史；MySQL latest 默认关（`enable-last-data-in-db: false`），开了才有 `dev_lst_*`。

**Q：超级设备和普通产品区别？**  
A: `dev_product_ex` 管模板树；节点设备有 `derive_metadata`；GIIC 超级模型还有 abilities 嵌套。
