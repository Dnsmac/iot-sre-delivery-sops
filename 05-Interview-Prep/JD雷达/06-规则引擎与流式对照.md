# 06 规则引擎与流式对照

> 三行定稿（可背）

## 定义

规则引擎按条件触发动作（告警、转发、下行）；流式计算（Flink/Kafka Streams 等）强调 **持续窗口聚合、状态化计算**。二者都可消费设备数据，但延迟模型、运维复杂度、语义不同。

## 现网有没有

**有规则/场景/告警**（JetLinks RuleEngine + ReactorQL + EventBus 订阅）。**Pulsar** 用于级联/数据流跨平台，**不是设备第一跳**。设备消息：`网关 → EventBus → 规则/时序/级联` 并行消费。我未做 Flink 主责；对照时说「我们先总线再规则，重窗口统计可外置 Flink」。

## 面试 30 秒

> 设备消息进 EventBus 后，场景规则和通用规则通过 ReactorQL 订阅 /device  topic 触发，动作包括告警、发消息、调功能。级联高峰走 Pulsar 进 /mq/** 再桥接 EventBus，规则引擎本身不直接消费 Pulsar。Flink 适合跨设备大窗口聚合和 Exactly-once，我们现网主路径是 EventBus 加规则引擎，足够覆盖告警和联动。我的优化在接入热路径，保证消息先稳稳进总线。

## 我们项目怎么做

### 1. 规则引擎架构

```text
DeviceMessageConnector → EventBus /device/**

并行消费者：
  ├─ TimeSeriesMessageWriterConnector   → ES/TD 历史
  ├─ SceneTaskExecutor (executor=scene)  → 场景规则
  ├─ RuleInstance DAG                   → 通用规则图
  ├─ @Subscribe 业务 Bean               → 固件/级联/…
  └─ CascadeMessageSendConnector        → Pulsar 上行
```

| 模块 | 路径 | 职责 |
|------|------|------|
| 组件层 | `rule-engine-component` | TaskExecutor、集群调度、ReactorQL |
| 管理层 | `rule-engine-manager` | Scene CRUD、告警、启停 |
| 集群总线 | `ClusterEventBus` | local + broker 跨节点 |

### 2. 场景规则怎么订阅设备消息

`SceneTaskExecutorProvider` 核心逻辑：

1. `SceneRule` + `DeviceTrigger` 生成 ReactorQL，FROM 子句是 EventBus topic，例如：
   - `/device/{productId}/{deviceId}/message/property/report`
   - `/device/{productId}/{deviceId}/message/event/{eventId}`
   - `/device/{productId}/{deviceId}/online`
2. table 以 `/` 开头 → `eventBus.subscribe(Subscription.justLocal())`
3. 订阅 ID：`scene:{ruleId}`；可带资产过滤 `AssetsUtils.subscribeByAssets`
4. 触发后 `eventBus.publish("/scene/rule/{ruleId}", SceneData)` + 执行动作节点
5. 支持分支、防抖（shakeLimit）、定时触发

**TaskExecutor 类型**（非穷举）：`scene`、`reactor-ql`、`timer`、`delay`、`script`、`device-message-send`、`sql`、`data-mapping`。

### 3. 场景规则 vs 通用规则 vs 告警

| | 场景 Scene | 规则实例 RuleInstance | 告警 Alarm |
|--|------------|----------------------|------------|
| 实体 | `SceneEntity` | `RuleInstanceEntity` + DAG | 告警配置 + 历史 |
| 触发 | 设备/定时/手动 | 任意图入口 | 规则命中 / 场景 |
| API | `SceneController` | `RuleInstanceController` | AlarmController |
| 日志 | ES 或 TD（互斥） | 同左 | `AlarmHistoryService` |

### 4. Pulsar 在哪、和规则的分工

| 维度 | 规则引擎 | 级联 kh-cascade | 数据流 kh-dataflow |
|------|----------|-----------------|-------------------|
| 总线 | **进程内 EventBus** | **Pulsar** 跨平台 | **Pulsar** + EventBus |
| topic | `/device/**`、`/scene/**` | Pulsar per 平台 | `/mq/up/**`、`/mq/down/**` |
| 是否跑规则 | ✅ | ❌ 转发/同步 | ❌ 路由/权限/落库 |
| 典型类 | `SceneTaskExecutor` | `SubscriptionUpMsgServiceImpl` | `DeviceMessageSyncListenerService` |

**级联桥接**：

```text
下级 Pulsar → SubscriptionUpMsgServiceImpl
  → eventBus.publish("/mq/up/...")
  → dataflow 消费 / 回写

本地 /device/** → CascadeMessageSendConnector
  → PersistenceBuffer → Pulsar 发上级
```

规则引擎 **不直接订阅 Pulsar**；若要让规则处理级联消息，需先桥到 EventBus（或写独立消费者）。

### 5. 和 Flink 的对照（成熟方案 · 我们未内置）

| 维度 | 我们 EventBus + RuleEngine | Apache Flink |
|------|---------------------------|--------------|
| 部署 | Spring 进程内 | 独立集群 JobManager/TaskManager |
| 语义 | 逐条触发 + ReactorQL 轻聚合 | 窗口（tumbling/sliding/session）、CEP |
| 状态 | 规则实例内存 + DB | RocksDB 状态后端 |
| 一致性 | at-least-once（Reactor） | exactly-once（checkpoint） |
| 适用 | 告警、联动、单设备逻辑 | 跨设备统计、复杂事件、TB 级流 |
| 延迟 | 毫秒~秒 | 秒~分钟（窗口） |

**面试怎么说**：「平台内规则覆盖 80%  IoT 联动；若 JD 要 Flink，我会说设备先进 EventBus/Pulsar 做边界，**重计算外置 Flink 消费 Pulsar topic**，和现网不是替代关系是分层。」

**Flink IoT 典型模式（理解用）**：

```text
Pulsar/Kafka (device-events)
  → Flink Source
  → keyBy(deviceId)
  → window(1 min) / CEP
  → Sink (告警 API / TSDB / 下行 topic)
```

## 面试追问速答

**Q：规则和设备消息怎么解耦？**  
A：完全靠 EventBus topic；接入层只负责 publish，规则 subscribe，互不知协议。

**Q：集群下规则会不会漏消息？**  
A：Scene 默认 `justLocal` 订本节点；设备消息需在本节点 `DeviceMessageConnector` 发布，或 Pulsar 桥到 `/mq/**`。集群设备分布要配合 broker 特性。

**Q：做过规则引擎优化吗？**  
A：主战场是接入；规则侧了解链路和 Scene/ReactorQL 模型，压测优化在 EventBus 写入和接入背压。
