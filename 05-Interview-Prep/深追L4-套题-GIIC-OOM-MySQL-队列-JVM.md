## 一、GIIC 15W · 15 题（L1→L4）

> **主故事线**：~5k 挂 → 中期卡 14.3W → 四类问题叠加 → 分层改造 r1–r8 → 15W × 96h 长稳。**禁改 device-manager** 是主动防线。

### G1 · 压测规模？（L1 · 20s）
- **一句话**：GIIC 走 CoAP-TCP，目标 **15 万在线**，压测模型 **5 台机 × 3 万线程 = 150k**，服务端约 **4 节点**。
- **数字**：150,000 `[文档]` · 5×30k · 4 节点
- **追问**：「40 万呢？」→ **不同接入线**；我负责 GIIC 15W 段，40W/级联是背景协助，别拼成 50W。
- **证据**：GIIC §1

### G2 · 验收指标？（L1 · 20s）
- **一句话**：**5000 msg/s 属性**上报、长稳 **≥72h**（实际跑到 96h）、Login ramp **≥99.5%**。
- **数字**：5000 `[文档]` · 96h · 99.5%
- **追问**：「96h 是验收吗？」→ 验收节点 72h，我们**跑到 96h（4×24h）超节点**，7D（168h）目标还在续。
- **证据**：重构设计 / T3 · GIIC §1/§4

### G3 · 5000 怎么推导？（L2 · 30s）
- **一句话**：**150000 台 ÷ 30 秒/台 = 5000 msg/s**，30s 是属性上报周期。
- **数字**：150000÷30=5000 `[反推]`
- **追问**：「心跳算进去吗？」→ **不算**，5000 是**属性 Data**；心跳单估 ~2500/s `[假设]`。「为什么不是 1W？」→ 验收写死 5000，不是 1W。
- **证据**：场景题 §1.2

### G4 · 优化前现象？（L2 · 30s）
- **一句话**：**~5k 连接就 Login 超时 / Sink 断流**，优化后中期爬到 **~14.3W 卡死**上不去。
- **数字**：~5k 挂 → ~14.3W 卡 → 15W 稳
- **追问**：「5k 就挂，是不是机器太小？」→ **不是**，是 Sink/Redis 架构问题；机器一直是 4×128G，从没换过。
- **证据**：GIIC §8 · 模块故事 §2

### G5 · 14.3W 根因？（L3 · 40s）🔥
- **一句话**：卡在 14.3W 不是单点「机器不够」，是**四类问题叠加**。
- **展开**：① 全局单管道 Sink 背压整网；② 热路径 Registry/Redis/DB 风暴；③ 跨节点 L1 token 不一致误杀；④ Login 写 configuration 放大。
- **追问**：「你怎么定位是这四类不是一类？」→ 分层五层逐看：入口 errno 99 / 网关 Sink 断流 / 协议 Login 风暴 / Redis slowlog（`KEYS`）/ MySQL 连接顶满，四类各落一层。
- **证据**：GIIC §3.2/§8 · 模块故事 §2/§3

### G6 · per-connection 解决什么？（L3 · 40s）
- **一句话**：把**全局单管道 → 每 TCP 独立队列**，让背压**局部化**，一个慢消费者不再拖垮所有连接。
- **展开**：全局单管道 = 一个 Sink 慢 → 背压反传 → 整网 Login 断流；per-connection 后 Sink 满只 reject 自己这条连接。
- **追问**：「队列满了怎么办？」→ **reject**，不是无限堆积（queue-size=32 见 Q3）。
- **证据**：GIIC r1 时间线 · 模块故事 §6

### G7 · L1 脏读？（L3 · 40s）
- **一句话**：L1 热缓存 miss 或不匹配时，**回 Redis/Registry 对称 reload**，r3 修复了「hit 与 miss 加载逻辑不对称 → stale loader 写回脏数据」。
- **展开**：L1 是第一跳缓存，命中直接回；miss 回源加载，**加载完成要写回 L1**，但旧逻辑 hit/miss 路径不对称，可能把过期值写回。
- **追问**：「L1 改了怎么生效？」→ 协议包 L1 改动**需重打协议包上传**，不是改 jar（现网口径）。
- **证据**：GIIC r3 · §3.3

### G8 · Token async 会丢吗？（L3 · 40s）
- **一句话**：**L1 先回 200**，权威源（Redis）**异步批写**；丢了靠 reload/宽限兜底，r8 解决的是**队列跟不上 + 日志风暴**，不是改协议语义。
- **展开**：async 模式 L1 先响应，Redis 批写滞后；可回滚 sync 保一致。r8 是因 PENDING 队列积压告警风暴 → 日志限频 + 抬 batch/concurrency/capacity。
- **追问**：「丢 token 怎么办？」→ 挂靠 Redis reload + prevAccess 宽限（r6），不是保证 100% 不丢，是**最终一致 + 故障降级**。
- **证据**：GIIC r7/r8 · §8

### G9 · 为什么 32G 堆？（L4 · 60s）🔥
- **一句话**：稳态 8~10G + **密钥 Caffeine ~5.6G** + Login 尖刺 **×3**，所以申请 **32G**。
- **展开**：堆要按**缓存模型**估，不是按稳态均值。密钥是大头（5.6G），Login 瞬时并发会把对象树临时推高 3 倍。
- **追问**：「5k 就挂还申请 32G 不是浪费？」→ **5k 挂是 Sink/Redis，不是堆不够**；32G 按 15W + Login 尖刺规划。「和 OOM 的 8G 什么关系？」→ OOM 是 v3 另线（5k 台物模型无界），不是同一条（见 J11）。
- **证据**：scalability-plan · 场景题 §2.4

### G10 · 440MB 连接内存？（L4 · 60s）
- **一句话**：Netty/CoAP/PSK/Session/Operator 等 **逐项 ~11.8KB × 37500 连接 ≈ 440MB/实例**。
- **数字**：~440MB `[文档]` · 37500 连接/实例
- **追问**：「最坏情况呢？」→ 队列峰值 32×20KB 最坏 ~640KB/连接，但 concatMap(1) 串行处理常态很低（见 Q10）。「37500 怎么来？」→ 150000÷4 节点。
- **证据**：场景题 §2.4

### G11 · 带宽 120Mbps 从哪来？（L4 · 60s）
- **一句话**：历史按 **5000 msg/s × 3 属性 × 1KB** 保守假设，约 **120Mbps**，加 ACK/心跳约 **152Mbps**；均为 `[假设]+[反推]`。
- **展开**：450B 只见 Playbook 文档值 `[文档/待补实测]`；仓内没有原始抓包/脚本输出，不能替代成唯一实测值。
- **追问**：「1KB/450B 哪量的？」→ 1KB 是历史规划假设；450B 待抓包、网卡增量核对。**ES 不是 1KB/doc**。
- **证据**：场景题 §2.2/§3

### G12 · ES 15000 docs/s？（L4 · 60s）
- **一句话**：**5000 msg × 3 属性/msg = 15000 docs/s**；单 doc ~0.5KB、日增 ~620GB/天均为历史 `[假设]`，未完成 ES 增量实测。
- **展开**：ES 存的是**属性点**（时序），不是整包；msg→doc 是 1:3 展开。
- **追问**：「620GB/天还不堵？」→ 10W 实测 ES on **NFS** 写不进（IO 瓶颈），不是公式算小（见 Q6）。
- **证据**：场景题 §2.3/§3

### G13 · 为何还调 Nginx？（L4 · 60s）
- **一句话**：长连接全代理会**耗尽出站临时端口（errno 99）**，且 `$remote_addr` 单一 IP 会让少数压测机打爆单后端，需 `hash(ip+port)`。
- **展开**：errno 99 = Cannot assign requested address；hash ip+port 做粘滞；单入口单 IP 代理连接约 **6 万级硬顶**，再高要 LVS/多入口。
- **追问**：「应用 profile 不就行了吗？」→ **独立**，sysctl/Nginx 是基础设施长期保留，不是 `application-perf` 开关。
- **证据**：全栈运维 §2

### G14 · 和 40W 关系？（L4 · 40s）
- **一句话**：**不同接入线**；我主讲 GIIC 15W（CoAP-TCP），40W/级联（Pulsar）是背景协助，别拼成「我主导 40W」。
- **追问**：「HA50w 那条线呢？」→ 截图同屏有 HA 线，但**主叙事是 GIIC 15W**，禁止把两条拼成 50W。
- **证据**：GIIC §0/§4.3

### G15 · device-manager 边界？（L4 · 40s）🔥
- **一句话**：**禁改** `device-manager`——`refactorHeader` skip、`event-bus-fire-and-forget` 两刀**政策禁止，已回滚永不合入**。
- **展开**：影响是 connector 仍走 `getSelfConfigs` / 等 EventBus 完成；所以靠**网关/协议/Redis 侧卸压**顶住，这是工程取舍，不是不会。
- **追问**：「那你们怎么减压的？」→ skip-persist-on-data、Token async、Login 减负（上游减负，不碰 connector）。
- **证据**：GIIC §3.1 · 场景题 §0.4

## 二、OOM / JVM · 15 题（L1→L4）

> **主故事线**：8G 堆卡死 → jstat Old 96% / FGC≈YGC → jstack 无死锁 → MAT Dominator 定位 operatorCache 5.7G → 根因「有限 key × 胖 value × 不淘汰」→ Caffeine 修复。

### J1 · 现象？（L1 · 20s）
- **一句话**：**8G 堆卡死**，接口超时、消息处理停滞；**6G 和 8G 都一样卡**。
- **数字**：-Xmx8G · 运行 ~2.7 天后卡死
- **证据**：OOM README

### J2 · 规模？（L1 · 20s）
- **一句话**：**~5050 台设备**，不是设备数无限涨——MAT OQL 证实 Operator **正好 5050 个**。
- **追问**：「那为什么堆爆了？」→ key 没失控，**value 太胖 + 永不释放**（见 J8）。
- **证据**：OOM MAT OQL

### J3 · jstat 看什么？（L2 · 30s）
- **一句话**：Old **96.41%** 恒定、YGC≈FGC、FGCT **12406s**——典型的 **Full GC 风暴**。
- **展开**：Old 顶满 + FGC 次数追平 YGC = 堆常驻集过大，回收不掉，不是偶发尖刺。
- **追问**：「YGC≈FGC 说明什么？」→ 每次 Young 回收都触发 Full GC，说明 Old 已满，对象晋升即爆。
- **证据**：OOM §2/§3.1

### J4 · jstack 结论？（L2 · 30s）
- **一句话**：319 线程，**无死锁**，大量 WAITING——排除死锁，指向 **GC 风暴**（线程在等分配）。
- **追问**：「无死锁就排除了吗？」→ 是，配合 jstat 的 Old 96% 一起看，定位从「线程问题」转到「堆问题」。
- **证据**：OOM README

### J5 · Dominator 是谁？（L3 · 40s）🔥
- **一句话**：`ExtendDeviceClusterConfiguration` 一个对象 **Retained ~5.66GiB（78%）**，其余（EventBus、H2 等）远小于此。
- **展开**：Dominator Tree 的 retained = 这个对象及它独占引用的子树总大小；78% 说明**几乎整个堆都是它**。
- **追问**：「怎么找到的？」→ jcmd GC.heap_dump → 本地 MAT 分析，Dominator Tree 一眼见。
- **证据**：OOM §3.3

### J6 · 1800 万 HashMap？（L3 · 40s）
- **一句话**：是**每台物模型 JSON 展开的内部节点**，不是 1800 万个 cache key。
- **展开**：5050 台 × 每台 ~3600 个 HashMap = 1800 万；histogram 里的 204 万 metadata 是 5050 棵树上的枝叶，**不是 204 万台设备**。
- **追问**：「所以 histogram 能定因吗？」→ **不能**，class_histogram 只能看「有什么类」，定因必须 heap dump + Dominator Tree。
- **证据**：OOM §2/§4.1

### J7 · 为何加内存无效？（L3 · 40s）
- **一句话**：**无界缓存**，6G→8G 只是多撑 2~3 天，根因不清加多少都只是推迟。
- **展开**：泄漏是「key 只增不减」，内存越大只是让「填满」来得晚一点，Dominator 5.7G 在 8G 下已占 78%。
- **追问**：「那该加吗？」→ 短期止血可以，**长期必须加缓存上限**，否则 8G→16G 也一样爆。
- **证据**：OOM §4

### J8 · 根因机制？（L3 · 60s）🔥
- **一句话**：`operatorCache` **无 maximumSize、无 TTL、注销不 invalidate**，每台物模型 3.4~15.6MB 永驻。
- **展开**：`ConcurrentHashMap<String, Mono<DeviceOperator>>` 无界；历史补报 `registry.getDevice()` 每条灌缓存；旧 AOP 的 remove 逻辑 `@Deprecated` 关闭。
- **追问**：「为什么 5050 台能占 5.7G？」→ 5050 个 key × 每台 3~15MB 物模型对象树（含 ~40 metadata、~3600 HashMap/台）= 5.7G。
- **证据**：OOM §3.5/§4

### J9 · G1 为何 Full GC 风暴？（L4 · 60s）
- **一句话**：**大对象常驻 + 高分配速率**，Mixed GC 回收不动这些常驻大对象，Old 持续逼近上限 → 频繁触发 Full GC。
- **展开**：G1 的 Mixed GC 主要回收短命对象，5.7G 的 Dominator 是「常驻集」，Mixed 动不了它；新生代分配速率又高，晋升持续挤压 Old，最终 Full GC 拼命做也腾不出空间。
- **追问**：「调 G1 参数能救吗？」→ 治标，`-Xmx` 或 region 参数只是延长；**治本是清掉常驻集**（缓存上限）。
- **证据**：Java_Interview 03 · OOM §4

### J10 · 方案与当前状态？（L4 · 60s）
- **一句话**：已完成定位并提出 Caffeine **maximumSize + expireAfterAccess** + 设备注销 **invalidate** 方案；补丁待 Gerrit 正式流程合入，暂无复测收益。
- **展开**：maximumSize 限制条目、expireAfterAccess 按访问过期、注销主动失效；这些是待合入方案，不说已经治理完成。
- **追问**：「为什么用 Caffeine 不用手写 LRU？」→ 可比较 W-TinyLFU、统计与淘汰能力；最终参数必须结合回源压力和命中率压测。
- **证据**：OOM §6 · README 优先级表

### J11 · 和 GIIC 32G 对比？（L4 · 60s）🔥
- **一句话**：15W **规划** Caffeine 密钥是**有界**的；5k OOM 的 operatorCache **无界**成了 Dominator——**证明堆要按缓存模型估，不是按设备数估**。
- **展开**：同样「缓存设备相关对象」，一个有 maximumSize（GIIC 规划），一个裸 Map（OOM），结局天差地别。
- **追问**：「两条线会串吗？」→ **不同接入线**：GIIC 是 CoAP-TCP 15W，OOM 是 v3 MQTT ~5k 台 -Xmx8G，别拼成一个项目。
- **证据**：场景题 vs OOM

### J12 · dump 拿不回？（L4 · 60s）
- **一句话**：11GB hprof，堡垒机带宽难整包下载 → **服务器 headless 生成 Leak_Suspects.zip（几 MB）**，或本地分析 `.gz`。
- **展开**：不用把 11G 拉回本地；MAT 命令行 headless 模式在服务器上算，只把 Leak_Suspects 报告（几 MB）传回。
- **追问**：「还能更轻吗？」→ 现场采样先做：jstat / jcmd GC.class_histogram / jstack，不一定要 dump；定因才 dump。
- **证据**：OOM §3.2

### J13 · 水位拒连关系？（L4 · 60s）
- **一句话**：堆 <10% 时**主动拒连**，在 Vert.x loop 上触发 System.gc 抢救——是**内存过载保护**，不是治本。
- **展开**：水位线触发拒新连接，防止堆被打满后连正常连接都处理不了；但 System.gc 是兜底，长期靠缓存治理。
- **追问**：「拒连会不会业务受损？」→ 短时拒连换取集群存活，新连接可重连到其他节点（配合负载均衡）。
- **证据**：mqtt-watermark

### J14 · 容器 limit 注意？（L4 · 40s）
- **一句话**：RSS = 堆 + 元空间 + 线程栈 + 直接内存 + 页缓存，`-Xmx=limit` 必被 OOM Kill，用 **MaxRAMPercentage**。
- **追问**：「Exit 137 什么意思？」→ 128 + SIGKILL(9)，是**容器 OOM Kill**，不是 JVM OutOfMemoryError。
- **证据**：26-云原生 §5/§6

### J15 · 以后第一眼查什么？（L4 · 40s）
- **一句话**：**jstat Old%** → **histogram 看 JetLinksDeviceMetadata** → **查缓存有没有上限**。
- **展开**：Old 长期 >90% + FGC≈YGC → 先怀疑堆常驻集过大；class_histogram 找候选类；核对缓存配置有无 maximumSize/TTL/invalidate。
- **追问**：「设备数有限就安全吗？」→ **不是**，「有限 key × 胖 value × 不淘汰」照样 OOM。
- **证据**：OOM §7

## 三、MySQL 生产联动 · 10 题（GIIC 上下文 · L3~L4）

> **主故事线**：15W 长连接不是只改 jar，库要**按内存选档 + 连接池联动**，否则应用优化会被 MySQL 连接顶满拖回去。

### M1 · 15W 用哪档 cnf？（L3 · 40s）
- **一句话**：**prod-128g**，Buffer Pool **16G**，`max_connections` **≈1200**。
- **展开**：按**机器内存选档**（prod-128g / 64g / test-4g），不按「今天压 GIIC」单独改一版危险参数。
- **追问**：「BP 16G 够吗？」→ 热表注释 7~10G+，16G 能盖住热表（见 M6）。
- **证据**：ops cnf

### M2 · 应用池怎么设？（L3 · 40s）
- **一句话**：4 节点 × **64 ≈ 256**，必须 **< max_connections × 0.7**（1200×0.7=840），留足余量。
- **追问**：「为什么 ×0.7？」→ 防单应用池把库连接打满，DB 还有管理连接、备份、监控等其他占用。
- **证据**：交接文档

### M3 · 为何不能只加大池？（L3 · 40s）
- **一句话**：池加到**打满 1200** 也没用，Login 仍写放大——**瓶颈在写放大，不在连接数**。
- **展开**：只加大应用池 → 库连接顶满 → 别的服务也拿不到连接，形成级联。
- **追问**：「那怎么减写放大？」→ Login 减负（skip-persist-on-data、setConfigs 批量写），从源头降（见 M10）。
- **证据**：全栈运维 §3

### M4 · 混部内存账？（L3 · 40s）
- **一句话**：128G − 32G JVM − 8G OS ≈ **86G 给 MySQL 预算**，prod-128g 余量足。
- **追问**：「OS 只留 8G？」→ 加 file cache、连接、代理等杂项，实际要更保守，这是**粗算口径**。
- **证据**：场景题 §2.4

### M5 · GiicHotCache vs BP？（L4 · 60s）
- **一句话**：L1 热缓存**减读**，但**不能替代 Buffer Pool 容量规划**——Login/状态等仍可能打库。
- **展开**：HotCache 挡的是「高频重复读」，BP 负责「热表数据驻留内存」；两者层次不同，不能因为加了缓存就砍 BP。
- **追问**：「什么时候会穿透缓存打库？」→ 冷 Login、miss、状态查询，缓存 miss 时回源。
- **证据**：全栈运维 §3

### M6 · 热表有哪些？（L4 · 60s）
- **一句话**：`dev_device_instance` 等热表，注释 **7~10G+**，是 BP 16G 要盖住的核心。
- **追问**：「热表多大算出来了吗？」→ 注释口径 7~10G+，正好被 16G BP 覆盖，留余量。
- **证据**：prod-128g 注释

### M7 · 压测开「关刷盘」档吗？（L4 · 40s）
- **一句话**：**否**，**一套生产参数长期在线**，压测 ≠ 另开「关刷盘」档，否则压测结果失真。
- **展开**：关刷盘（`innodb_flush_log_at_trx_commit=0` 等）会虚高吞吐，上线回生产档就露馅。
- **追问**：「那压测和生产差异在哪？」→ 只调压测流量模型，不调库的危险参数。
- **证据**：全栈运维 §3

### M8 · R2DBC 超时说明？（L4 · 60s）
- **一句话**：超时是**池/代理窄路**，不一定是 MySQL Cluster 本身挂了——**分层定位，先看连接池和代理**。
- **展开**：R2DBC 响应式，超时可能来自连接池耗尽、代理抖动、网络，而非 DB 慢查询。
- **追问**：「怎么区分？」→ 看 MySQL 侧 slowlog 有无对应慢查询，无则查池/代理/网络。
- **证据**：redis-camellia（交叉）

### M9 · 最新态 vs 时序？（L4 · 60s）
- **一句话**：MySQL 存**行级最新态**（一设备一行，覆盖写），ES 存**属性点时序**（追加），分工不同。
- **展开**：MySQL 管「设备当前状态」，ES 管「历史曲线」；Redis 管「实时热点」。
- **追问**：「为什么不全存 ES？」→ 最新态要精确单值 + 事务，时序要聚合查询，两者查询模式不同，强行合一成本高。
- **证据**：全链路白板

### M10 · Login 风暴怎么减负？（L4 · 60s）
- **一句话**：**skip-persist-on-data** + **Token async** + **减 getSelfConfigs 触发**，从源头降写放大。
- **展开**：Login 每次写 configuration 大字段是放大点；skip 跳过不必要的持久化、Token 异步批写、少触发 getSelfConfigs。
- **追问**：「getSelfConfigs 为什么频繁？」→ 禁改 device-manager 后 connector 仍走它，只能靠上游减触发频率。
- **证据**：GIIC §3

## 四、队列 / 背压 / 缓冲 · 10 题（L3~L4）

> **主故事线**：设备上报 → 解码 → **EventBus**（不是 Pulsar 第一跳）→ 下游订阅；背压靠 per-connection 队列 + concatMap(1) 串行；ES 写不进时 elasticsearch-buffer 磁盘 FIFO 兜底。

### Q1 · 设备上报先进哪？（L3 · 40s）
- **一句话**：解码后进 **EventBus**，**不是 Pulsar**——Pulsar 用于级联/跨平台，不是设备第一跳。
- **追问**：「为什么不用 MQ？」→ 设备上报是**内存总线分发**，低延迟；Pulsar 是**跨平台/级联**的持久化通道，场景不同。
- **证据**：真相源

### Q2 · Pulsar 干什么？（L3 · 30s）
- **一句话**：**级联 / 跨平台**数据搬运，非设备第一跳。
- **追问**：「级联积压怎么办？」→ backlog 排查是另一条线（W3/W6），此处只答位置不展开。
- **证据**：画像

### Q3 · per-connection 队列大小？（L3 · 40s）
- **一句话**：GIIC `queue-size=32` 见只读现网 `application.yml` 与交接 §5，表示单连接入队容量；满则 reject，不外推到所有协议。
- **展开**：32 是每 TCP 队列上限，背压局部化；满了 reject 该连接，防止单连接拖垮节点。
- **追问**：「reject 后客户端怎么办？」→ 客户端重连/重发，服务端保持可用（和 J13 水位拒连同理）。
- **证据**：交接 §5

### Q4 · 全局 vs per-connection？（L3 · 60s）
- **一句话**：优化前**全局单管道 Sink 断流 ~5k**，改 per-connection 后**局部背压**，一个慢消费者不再拖垮全网。
- **追问**：「全局管道为什么必挂？」→ 单点 Sink 慢 → 背压反传整个管道 → 所有连接 Login 一起超时，5k 就露底。
- **证据**：GIIC §3.2

### Q5 · elasticsearch-buffer 是什么？（L4 · 60s）
- **一句话**：写 ES 前的**磁盘 FIFO 缓冲**，**不是 Kafka**——ES 写不进时先落盘，防丢消息。
- **展开**：它是应用侧本地磁盘队列，ES 慢时堆积在 buffer，等 ES 恢复再回放；和 Kafka 的区别是**无独立 broker、单机、非跨平台**。
- **追问**：「为什么不直接用 Kafka？」→ 设备第一跳走 EventBus 内存总线，buffer 只是 ES 写失败时的兜底，引入 Kafka 过重。
- **证据**：es-nfs case

### Q6 · 155GB 说明什么？（L4 · 60s）🔥
- **一句话**：ES **写不进**，iot buffer 高峰合计 **~155GB**——**先看 IO，再算公式**。
- **展开**：~620GB/天只是历史假设；现场已证的是**写线程满 + CPU 不高 = 等 IO**，根因是 data path 在 NFS。
- **追问**：「CPU 不高怎么还慢？」→ 写线程在**等 NFS IO 返回**，不是算力不够，这是经典「资源不高但慢」陷阱。
- **证据**：es-nfs §2

### Q7 · dead 队列？（L4 · 60s）
- **一句话**：失败永久堆在 dead（每 pod ~26G），`hasFailures` **整批 requeue** 反而加重 ES。
- **展开**：死信不回 ES，永久占盘；更糟的是代码「只要有一批里有失败，整批重试」，把好数据也重发一遍，ES 雪上加霜。
- **追问**：「怎么修？」→ 改「只重试失败项」（需改代码）+ 消化 buffer + 限流，防 ES 恢复后继续灌爆。
- **证据**：es-nfs §2/§3

### Q8 · Token 批写队列 r8？（L4 · 60s）
- **一句话**：PENDING 队列积压 → **告警风暴**，r8 **日志限频 + 抬 batch/concurrency/capacity**，让刷盘跟上入队。
- **展开**：async 批写入队速度 > 刷盘速度 → PENDING 堆积 → 每条告警 → 日志风暴；r8 不是改协议语义，是**队列/日志加固**。
- **追问**：「和丢 token 有关吗？」→ 无关，丢不丢看 reload/宽限；r8 解决的是**性能抖动**。
- **证据**：GIIC r8

### Q9 · EventBus 为何不能 fire-and-forget？（L4 · 60s）🔥
- **一句话**：**device-manager 禁改**，fire-and-forget 那刀政策禁止；connector 仍等 publish 完成、仍可能 `getSelfConfigs`。
- **展开**：改 fire-and-forget 能卸压，但模块政策禁止；所以靠**上游减负**（skip-persist、Token async）顶住，这是工程取舍。
- **追问**：「不改成吗？」→ 改成，但现网政策不允许，已回滚；面试要主动交代这个边界，显得诚实。
- **证据**：GIIC §3.1

### Q10 · concatMap(1) 含义？（L4 · 60s）
- **一句话**：**单连接串行处理**，一次只处理一个消息，防乱序、防内存暴涨。
- **展开**：concatMap 是顺序扁平化，参数 1 = 并发度 1；长连接消息要保持顺序（PSK/Login/Data 有先后），串行保证不乱序。
- **追问**：「串行会不会慢？」→ 单连接串行、多连接并发，总体吞吐靠连接数撑，单连接顺序比吞吐重要。
- **证据**：设计文档

## 五、练法（每日 20min · 升级版）

### 5.1 五段式自测（每道 L4 题都过）

```
① 遮答案，看题 → 40s/90s 口述
```
