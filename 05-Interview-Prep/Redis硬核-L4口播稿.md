## 一、线程模型与底层结构（R1～R4）

**R1 · Redis 为什么快？** 40s
口径：四点——① 纯**内存**操作；② **IO 多路复用**（epoll），单线程处理海量连接；③ 命令执行**单线程**，无锁、无上下文切换；④ 高效数据结构（SDS / 跳表 / 压缩列表）。注意「快」是有边界的：单 key 大 value、慢命令（keys、hgetall 大 hash）照样拖垮。

**R2 · Redis 是单线程还是多线程？** 40s 🔥
口径：**核心命令执行一直是单线程**。6.0 起引入 **IO 线程**只做网络读写（解析请求、写回响应），命令处理仍单线程串行——所以「多线程」只是把 IO 摊薄，不改变单线程执行的模型，也不会带来并发写一致性问题。好处：不用锁，原子性天然成立。

**R3 · 五种类型 + 底层编码？** 50s
口径：String（SDS/整数）、Hash、List（quicklist=ziplist+双向链表）、Set（整数集合/哈希）、ZSet（跳表 + dict）。3.2 后 ziplist 逐步被 **listpack** 替代（解决连锁更新）。要点：**小数据用紧凑编码省内存**，元素变多自动转哈希/跳表——这是「省内存」的底层手段。

**R4 · ZSet 为什么用跳表不用红黑树？** 40s
口径：三个理由——① 跳表实现简单、好写少 bug；② **范围查询快**（O(log n) 定位后顺链表走，红黑树要中序遍历）；③ 更省内存（概率平衡，不存颜色指针）。ZSet 实际是跳表 + 哈希（哈希按成员 O(1) 查分数）。

## 二、持久化（R5～R7）

**R5 · RDB 和 AOF 区别？** 50s 🔥
口径：RDB 是**某时刻内存快照**（二进制，`bgsave` fork 子进程写盘），恢复快、体积小，但**可能丢最近一段**（两次快照之间）。AOF 是**追加写每步命令**，丢得少（`appendfsync everysec` 最多丢 1s），但文件大、恢复慢。

**R6 · AOF 重写为什么？** 40s
口径：AOF 只追加不覆盖，文件会无限膨胀。重写 = fork 子进程**按当前内存状态生成一份精简 AOF**（去掉中间态，如只留最终 set），不是读旧 AOF 合并。重写期间新命令写 AOF 重写缓冲区，完成后追加，保证不丢。

**R7 · 生产怎么配持久化？** 40s
口径：默认**混合持久化**（4.0+）：RDB 做基础快照 + AOF 记增量，兼顾恢复快和丢得少。项目钩子只能讲“Redis 在 IoT/ERP 里偏缓存和路由层，强持久不靠 Redis”；设备影子、Token 等具体使用需按现网证据补齐。

## 三、缓存三大问题 + 一致性（R8～R11 · 必考）

**R8 · 缓存穿透？** 40s 🔥
口径：请求的 key **缓存和库里都没有**（多为恶意/不存在 id），全打到 DB。解法：① **布隆过滤器**前置拦（存在性判断，宁可误判不放行）；② **空值缓存**（查不到也缓存短 TTL 空值）；③ 参数校验。

**R9 · 缓存击穿？** 40s 🔥
口径：**热点 key 过期瞬间**，海量请求同时打 DB。解法：① **互斥锁/分布式锁**：一个线程去回源重建，其余等待或降级；② **逻辑过期**：物理不过期，值里带过期时间，过期就异步重建、旧值继续扛。区别穿透：穿透是「key 不存在」，击穿是「热点 key 过期」。

**R10 · 缓存雪崩？** 40s 🔥
口径：**大量 key 同时过期或 Redis 挂了**，请求全压 DB。解法：① 过期时间加**随机抖动**（TTL ± 随机值，避免同一时刻集体过期）；② **多级缓存**（本地 Caffeine + Redis）；③ 高可用（主从/哨兵/集群）+ 限流降级。

**R11 · 缓存和 DB 双写一致性怎么保证？** 60s 🔥🔥
口径：主流 **Cache-Aside 旁路缓存 + 删缓存**：更新时**先更新 DB，再删缓存**（不是先删缓存，避免并发下读到旧值再写回）。进阶三招：① **延迟双删**（先删 → 更新库 → 再延迟删一次，防并发写回旧值）；② 删缓存失败补偿——**订阅 binlog**（canal）异步删，保证最终一致；③ 接受**最终一致**，靠 TTL 兜底。项目钩子：IoT 最新态/路由类读模型可以讲最终一致思想，但具体是否用了 canal 或延迟双删待补证。

## 四、分布式锁（R12～R14）

**R12 · 用 Redis 做分布式锁的完整姿势？** 50s 🔥
口径：`SET key value NX PX 30000`——**NX 互斥 + 过期防死锁 + value 唯一标识**（UUID，释放时校验是自己加的锁）。释放用 **Lua 脚本**（`if get==value then del`）保证「判断 + 删除」原子，否则删了别人的锁。
项目钩子：ERP 可讲分布式锁，但必须补一句“锁不是唯一正确性来源，幂等和唯一约束兜底”。

**R13 · Redisson 看门狗解决什么问题？** 40s
口径：锁的过期时间难定——业务没执行完锁先过期就出并发。看门狗**自动续期**：默认 30s，每 10s 续到 30s，直到业务完成显式释放；业务挂了不续期、锁自然过期。本质是**把「锁时长」从「拍脑袋」变成「跟随业务」**。
分级：通用机制题。除非确认项目使用 Redisson，否则只讲“如果用 Redisson，它解决什么问题”。

**R14 · Redlock 的争议？** 40s
口径：Redlock 是**多实例加锁**（向 N 个独立 Redis 依次加锁，过半成功才算拿到），防单实例宕机丢锁。争议（Martin Kleppmann）：分布式锁在**时钟回拨/GC 停顿**下仍可能失效，本质是「没有完美分布式锁」。实践：单实例 + 看门狗 + 幂等兜底，多数业务够用；真正要强一致用 ZK/etcd（CP 系统）。
项目边界：ERP 不主动说用了 Redlock；只讲“即使用锁，也要幂等/唯一约束兜底”。

## 五、集群与生产（R15～R18 · IoT 钩子）

**R15 · 主从 / 哨兵 / Cluster 三选一？** 50s
口径：**主从** = 读写分离 + 数据备份，无自动 failover；**哨兵** = 主从 + 监控 + 自动选主（高可用）；**Cluster** = 数据分片（16384 槽）+ 高可用（每个分片带从），适合量大。选型：小量高可用用哨兵，数据量大要横向扩容用 Cluster。项目钩子：IoT Redis 可以讲低延迟缓存/路由表职责；具体单实例、哨兵还是 Cluster 需按现网配置核对。

**R16 · 大 key / 热 key 的影响与处理？** 40s 🔥
口径：**大 key**（如一个 hash 几十万字段）→ 单命令阻塞、网络大包、迁移卡顿：拆 key 或分片存储。**热 key**（秒杀商品）→ 单分片 CPU 打满：**本地缓存兜底**（Caffeine 前置）、热 key 复制多份、读写分离。定位：`redis-cli --bigkeys`、`hotkeys`。项目钩子：Caffeine/Redis 分层可以讲选型思想；没有热 key 事故证据时不说“线上就是这么修的”。

**R17 · 内存淘汰和过期删除策略？** 40s
口径：过期删除 = **惰性删除**（访问时检查）+ **定期删除**（周期性抽样清理）结合。内存满时按淘汰策略：`allkeys-lru`（最常用，淘汰最近最少用）、`volatile-lru`（只淘汰设了过期的）、`noeviction`（不淘汰、写入报错）。选 `allkeys-lru` 作为纯缓存最合适。

**R18 · 什么会让 Redis 阻塞？** 40s
口径：慢命令（keys、hgetall 大 key、sort）、大 key 删除（`DEL` 大对象，用 unlink 异步）、fork 快照（大内存 fork 抖动）、AOF 刷盘阻塞、内存淘汰、集群数据迁移。定位用 `slowlog`。项目钩子：IoT 会话路由应走精确 key 查询；是否使用 hash 结构、字段设计待补证。
