## 卡① 内嵌 MqttServer（vs 独立 EMQX）· Day A

**背景**：kh-iot-server 用 Netty 内嵌 MQTT 服务端接入设备，外面 nginx 透传，没有独立 EMQX 集群。

**为什么选内嵌（3 个真理由）**：
1. **会话同进程 = 下行少一次跨进程路由**：设备连接和会话表在应用 JVM 内，下发可按本地会话写回；跨 Pod 时仍需 Redis `connectionServerId` 与集群 RPC。operatorCache OOM 是 **DeviceOperator/物模型 JSON 对象树无界**，与 MQTT 订阅表不是同一对象，不能拿来证明内嵌会话设计。
2. **少运维一个集群**：独立 EMQX 会增加节点发现、会话和集群运维面；“团队 2～3 人”缺少当前证据，不作为项目事实。通用取舍是组件越多，运维成本越高。
3. **协议能力可随业务实现**：内嵌方案可在应用代码中控制连接、认证、订阅和下发；代价是 Broker 已有的集群、共享订阅、规则引擎等能力需要自行评估或实现，不能笼统说“只需要一小撮能力”。

**代价（说得出代价才是 L4）**：
1. **接入上限要靠压测定**：内嵌 Netty 接入的极限受连接内存、业务耦合、下游写入共同影响；约 14.3W 只作为本项目中期现象 `[文档]`，不能上升为“内嵌 Netty 天花板”。
2. **接入层不能独立扩容**：接入和业务耦合在一个进程，接入峰值要把整个应用横扩（业务逻辑跟着复制）。
3. **QoS/集群语义自己做**：EMQX 送的会话迁移、共享订阅、桥接，内嵌版要么不做要么自己写。

**实现要点（一句话层）**：Netty（boss/worker + MQTT 3.1.1 编解码器）+ sessionId→Channel 会话表 + keepalive 超时踢半开 + QoS1 PUBACK 确认 + 水位拒连保护。

**30s 口径**：「项目事实是 Netty 内嵌 MqttServer、会话与业务同进程，少一套独立接入集群；代价是接入与业务耦合，扩容要一起评估。单机 10W、50W 必须换 EMQX 都没有当前实测依据；是否拆独立 Broker，要按连接模型、会话迁移、多协议能力和运维成本压测决策。」

**追问三层**：L2 "为什么不用 EMQX" → 卡上三条；L3 "什么时候考虑拆独立 Broker" → 连接与业务能否独立扩容、会话迁移、多协议和运维成本，结论需压测验证；L4 "会话同进程的分布式版怎么做" → deviceId→节点路由表（Redis）+ 下行跨节点转发（追问包 A-H6）。

## 卡② nginx 透传（接入层薄化）· Day A

**背景**：设备连接先过 nginx（stream 四层透传）再到内嵌 MqttServer。

**为什么**：① 复用 nginx stream 的四层转发与 upstream 管理；② 横扩时可调整 upstream 而不改应用。TLS 是否在 nginx 终结当前没有配置证据，只能作为通用可选方案，不能当项目事实。

**代价**：多一跳会增加延迟和连接状态；具体是否微秒级没有实测，不报绝对数字。连接数和错误水位需要在 nginx 与应用两侧观测。

**30s 口径**：「项目已证是 nginx stream 四层透传并参与连接与超时参数联动；TLS 终结属于通用可选方案，是否启用要回现场配置核对。」

## 卡③ EventBus 进程内总线（vs 一切走外部 MQ）· Day C

**背景**：设备上报第一跳在 iot-server 内解码，先进 EventBus（vert.x 风格）做进程内分发，再进入 ES/MySQL 等处理；Pulsar 只用于级联、跨服务、长积压等已证链路。

**为什么**：① 上报第一跳需要低延迟分发，进程内调用通常少一次序列化和网络跳转；具体差值需压测验证；② 是否允许丢失必须按消息类型和业务语义确认；③ EventBus handler 的消费并发、积压上限和失败策略要单独设计，不能拿 GIIC 连接队列参数代替。

**代价**：① **进程内 EventBus 不提供外部 MQ 等价的持久化与跨节点恢复语义**；② handler 消费变慢可能形成内存积压。具体 handler 是否使用有界队列、串行还是并发消费，需按实现和压测核对。

**30s 口径**：「分层思想：设备上报先在 iot-server 解码进 EventBus，实时分发后再落 ES/MySQL；Pulsar 只讲级联、跨服务和长积压这些已证链路。判据是『这消息要不要跨进程、能不能积压、丢不丢得起』，但不能把设备上报第一跳说成 Pulsar。」

**追问**："EventBus 堆爆怎么办" → 先核对具体 handler 的消费速率、积压结构、并发和失败策略，再决定有界缓冲、降级或外部 MQ。GIIC `queue-size=32` 是 **CoAP-TCP per-connection 连接入队容量**，不能写成 EventBus handler 参数。155GB 只讲 ES NFS 导致 elasticsearch-buffer 积压。

## 卡④ Pulsar（vs Kafka/外部 MQ）· Day C

**背景**：级联、跨服务异步、长积压场景用 Pulsar；设备实时上报不走 Pulsar（走 EventBus）。

**为什么选 Pulsar（3 条）**：
1. **存算分离**：Broker 无状态，数据在 BookKeeper（bookie）；扩容 broker **不搬数据**，Kafka 扩分区常要 rebalance 搬副本。
2. **多 topic / 多租户**：级联、跨服务异步链路里 topic/订阅会变多，Pulsar 的 namespace + 分层存储适合；Kafka topic 过多时运维成本更高。
3. **适合长积压场景**：可讲持久化、订阅模型和 backlog 处理思路；本卡不引用 155GB，该数字归 ES NFS / elasticsearch-buffer 案例。

**代价**：
1. **生态和运维心智**：团队熟 Kafka 时 Pulsar 学习成本高；BookKeeper + ZK 组件更多。
2. **延迟**：多一跳存储，极致低延迟不如 Redis/进程内 EventBus。
3. **调试**：订阅模型、ack 语义、重试策略要和业务对齐，否则重复消费。

**30s 口径**：「Pulsar 用在级联和长积压，不是设备 MQTT 上报。选它因为存算分离扩容快、topic 多、积压大；代价是组件多、团队要熟 BookKeeper。若纯日志流且已有 Kafka 运维，Kafka 更省心。」

**追问三层**：L2 Kafka 四高性能来源（顺序写/页缓存/sendfile/批压缩）→ C-H2；L3 为何不丢不重（confirm+持久化+幂等消费）→ C-V2；L4 级联分区数怎么定 → [11-MQ](../work/Java_Interview/面试题/11-消息队列MQ.md) 级联 4 连追问。

## 卡⑤ R2DBC 响应式（vs JDBC + 线程池）· Day B

**背景**：kh-iot-server 是 WebFlux/R2DBC 响应式栈（jetlinks 框架底座）。

**为什么**：IoT 平台存在大量长连接和 IO 等待。阻塞式模型在请求等待期间可能长期占用工作线程，但“5000 并发=5000线程”并不成立，实际取决于线程池、连接复用和阻塞点。响应式目标是用有限事件线程处理异步 IO、降低等待期间的线程占用；收益必须通过线程数、吞吐和延迟压测验证。

**代价（比好处更爱被问）**：
1. **调试难**：堆栈没有业务方法名（都在 lambda/reactor 链里），我排查时要靠日志上下文 + reactor 工具（onErrorResume 处处兜）；
2. **一条阻塞全链卡**：链路里任何一个阻塞调用（同步 HTTP、锁）就卡死整组 EventLoop——所以池化、队列、超时参数都要显式声明（M8 的 R2DBC 超时就是这条的现场）；
3. **学习曲线**：背压、冷热流、订阅时机，团队上手慢。

**30s 口径**：「项目使用 WebFlux/R2DBC，目标是让 IO 等待不长期占用工作线程，并与 Netty 事件模型衔接；它不天然等于高吞吐，任何阻塞调用都可能放大影响，最终要看线程、吞吐、延迟和错误率压测。」

## 卡⑥ Caffeine operatorCache（vs 直接查 Redis/DB）· Day B

**对象边界**：operatorCache 只指 `DeviceOperator`/物模型 JSON 对象树缓存；它不是 MQTT 订阅表，不是 GIIC per-connection 连接队列，也不是 EventBus handler 缓冲。

**为什么**：这类对象可能被消息处理频繁访问，进程内缓存的目标是减少重复加载和反序列化；实际命中率与收益尚无复测数据，不能写成已确认的吞吐收益。

**代价与事故（我的 W3 案例）**：本地缓存的命门是**容量纪律**——约 5050 个 key，每个 key 约 3~15MB，`-Xmx8G` 下 MAT Dominator 看到约 5.7G/78% 都压在这棵对象树上。所以本地缓存上线三件事：上限（W-TinyLFU 淘汰）+ 过期 + 命中率监控。

**30s 口径**：「operatorCache 不是操作员权限缓存，而是 DeviceOperator/物模型 JSON 对象树缓存；`-Xmx8G`、约 5050 台时 Dominator 约 5.7G/78%。我已完成定位并提出有界缓存、过期和失效方案，补丁待 Gerrit 正式流程合入，目前暂无复测收益。」

**追问**："和 Redis/DB 的一致性" → 物模型变更走「写 DB → 失效/重建本地缓存 → 短 TTL 或版本号兜底」，不追求强一致，但必须能防止无界增长。

## 卡⑦ 水位拒连 + per-connection 队列（自我保护三件套）· Day D

**为什么**：背压哲学是过载时保护存量。三件套：① `SystemUtils` 默认在 JVM 最大堆剩余比例 <10% 且持续 >5s 时拒新 MQTT 连接，“约 90%”是已用堆比例派生值，不是连接数水位；② GIIC `per-connection` 队列默认 `queue-size=32`，见只读现网 `application.yml` 与交接 §5；③ 消费串行 `concatMap(1)`。

**对象边界与代价**：这里的 `queue-size=32` 只属于 GIIC CoAP-TCP 的 per-connection 连接入队容量，不是 operatorCache，也不是 EventBus handler 队列。队列过小会更早 reject，过大增加内存占用；32 是仓库默认/交接文档值，是否适合其他负载仍需压测验证。

**30s 口径**：「MQTT 拒连水位看的是 JVM 最大堆剩余比例，默认低于 10% 持续 5 秒才拒新连接；GIIC 单连接队列默认 32。两者属于不同接入线和不同保护维度，32 不外推到所有协议，约 90% 也不是连接数水位。」

## 卡⑧ Token 异步批写（写路径攒批）· Day D

**为什么**：登录/Token 校验是高频小写，逐条写会放大下游压力；攒批是在满 N 条或 T 毫秒时 flush。收益需按批大小、窗口、下游容量和错误率压测，不报倍率。

**代价**：① **崩溃窗口**：进程挂了队列里没 flush 的丢——所以只用于「可容忍少量丢失」的数据（token 状态可重登，不用于设备消息本体）；② 延迟 +T 毫秒；③ flush 时的写放大要压测。

**30s 口径**：「Token 写入采用攒批思路，目标是减少逐条下游操作；代价是引入批次延迟、崩溃窗口和 flush 压力。能提升多少必须看批大小、窗口、下游和错误率压测，不能报数量级收益。」
