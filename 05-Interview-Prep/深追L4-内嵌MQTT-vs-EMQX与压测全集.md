## 〇、先背这三段（开口即稳）

### 0.1 内嵌 vs EMQX · 30s（⏱ 30s）

> 我们现网是 **iot-server 内嵌 MqttServer**（JetLinks 系），nginx **TCP 透传** 1883，**没有独立 EMQX 集群**。选内嵌是因为 **会话和业务同 JVM**，解码后直进 **EventBus**，下行少一跳；代价是 **接入和业务耦合**，扩连接要扩整个 fat jar，EMQX 自带的集群会话迁移、规则引擎、桥接要自己做或不要。是否换独立 Broker，看 **连接模型、会话迁移、多协议、运维成本** 四项压测定，不能拍脑袋说 10W 内嵌、50W 必 EMQX。

### 0.2 压测 · 30s（⏱ 30s）

> 我主讲 **GIIC CoAP-TCP 15 万在线**，5 机 × 3 万线程，验收 **5000 msg/s 属性 + 长稳 ≥72h**（我们跑到 **96h**）。优化前 **~5k Login/Sink 挂**，中期卡 **~14.3W**；我负责协议/网关：**per-connection 队列、L1、Token→Redis 异步批写、Login 写减负**，并协助 **Nginx/sysctl、MySQL 生产档**。瓶颈不在「连接数本身」，而在 **每条消息下游写放大**（ES/MySQL/Redis）和 **Login 风暴**；**不是全场 40W owner**。

### 0.3 连接数 vs 并发 · 15s（⏱ 15s · 防混淆）

> **连接数是静态成本**（FD + 会话内存 + epoll 挂着）；**并发是动态成本**（msg/s × 每条触发的 CPU/IO）。15W 连接若 30s 一条属性，只有 **~5000 msg/s**——网关优化后不是主矛盾，**存储侧放大**才是。

## 一、架构一张图（白板 60s）

```text
【内嵌 · 我们现网】
设备 ──TCP:1883──► MetalLB ──► nginx(stream透传) ──► iot-server Pod
                                                      ├─ MqttServer/CoAP Gateway（Netty）
                                                      ├─ 解码 → DeviceMessageConnector
                                                      ├─ EventBus → ES/MySQL/规则
                                                      └─ localSessions + Redis 路由

【独立 EMQX · 对比口径，非现网】
设备 ──TCP:1883──► LB ──► EMQX 集群（Erlang/OTP）
                              ├─ ACL / 规则引擎 / 桥接
                              └─ Paho/HTTP ──► 业务微服务 ──► DB
```

| 维度 | 内嵌 MqttServer（现网） | 独立 EMQX（行业常见） |
|------|-------------------------|------------------------|
| 进程边界 | 接入 + 业务 **同 JVM** | 接入 **独立集群** |
| 消息第一跳 | 解码 → **EventBus**（进程内） | Broker → **订阅/桥接**（跨进程/跨服务） |
| 下行 | `localSessions` + Redis `connectionServerId` + **RPC** | Broker 集群内路由 / 共享订阅 |
| 扩容 | 扩 **iot-server 副本**（业务跟着扩） | 扩 **EMQX 节点**（业务不动） |
| 运维面 | 少一套 Broker | Dashboard、ACL、规则、桥接开箱 |
| 天花板 | **压测定**（我们 GIIC 15W 有证据） | 百万连接行业案例多 |
| 典型代价 | 业务 OOM 拖接入；Rolling 要处理长连接 | 多一跳延迟；桥接/消费链路要治理 |

### E5 · EMQX 集群会话迁移 vs 你们 Redis 路由？（L4 · 60s）

| | |
|---|---|
| **问** | EMQX 不是有无缝迁移吗？ |
| **答** | EMQX **企业版/特定策略** 可做会话接管，本质是 **Broker 层** 的集群语义；我们是 **应用层** `deviceId → PodId` 存在 **Redis**，下行 **RPC 到持连接 Pod**。对比：EMQX 把复杂度关在 Broker；我们把复杂度放在 **应用 + Redis + RPC**。各有取舍，不是谁绝对先进。 |

### E7 · 共享订阅 / 队列订阅？（L4 · 60s）

| | |
|---|---|
| **问** | 多消费者怎么分摊设备上行？ |
| **答** | **EMQX**：`$share/group/topic` 在 **Broker 侧** 分摊到多个订阅客户端。**内嵌**：设备消息进 **EventBus**，由 **进程内 handler** 消费；多副本是 **每 Pod 各收各的连接上的消息**，不是「一条 MQTT 被多 Pod 抢消费」。若要 **跨 Pod 消费分摊**，得 **桥到 Pulsar/Kafka** 或 **分片接入**——我们设备上报 **第一跳不走 Pulsar**。 |
| **红线** | 不说「EventBus = Kafka 共享订阅」 |
| **→ 追问** | E9 那 Pulsar 干什么？ |

### E8 · 什么时候你会建议上 EMQX？（L4 · 60s）🔥

| | |
|---|---|
| **问** | 给你重来一次怎么选型？ |
| **答** | 四条判据：**① 连接与业务能否独立扩容**——连接涨 10 倍但 QPS 不涨，适合拆 Broker；**② 会话迁移/多协议**——MQTT+WS+JT808 等要统一接入层；**③ 多下游订阅**——很多异构系统各订各的 Topic，Broker 解耦更干净；**④ 运维编制**——有人专职 Broker SRE。反过来说：**平台型 IoT、解码后强耦合物模型/EventBus、团队小**，内嵌仍合理。 |

### E10 · Netty 内嵌 Broker 和 EMQX（Erlang）架构差在哪？（L4 · 90s）🔥

| | |
|---|---|
| **问** | 底层机制讲讲？ |
| **答** | 都是 **事件驱动 + 非阻塞 IO**：Netty **Reactor（boss/worker）** + Java 堆上 Session；EMQX 基于 **Erlang/OTP**，进程轻量、**监督树** 隔离故障，长连接调度成熟。内嵌优势在 **与业务线程模型统一**（我们 WebFlux/R2DBC）；劣势是 **GC 与连接数同堆**。EMQX 连接状态在 **Broker 堆外/独立进程**，业务 JVM GC **不直接拖 FD**。 |
| **→ 追问** | E11 C10K/C10M？ / E12 业务能跑 IO 线程吗？ |

### E11 · 单机怎么扛很多连接？C10K → C10M？（L4 · 60s）

| | |
|---|---|
| **问** | epoll 知道，再往下呢？ |
| **答** | 四件事：① **一连接一线程 → epoll 事件驱动**；② **每连接内存预算**（FD + 收发缓冲 + Session 对象，我们规划 ~10KB/连接量级 `[假设]`）；③ **系统上限**（`ulimit -n`、`ip_local_port_range`、内核 somaxconn）；④ **IO 线程只做编解码**，业务 **异步线程池**。C10M 还要 **SO_REUSEPORT、内核调优、多机水平扩展**；DPDK 是包速率极限时的选项，不是默认答案。 |
| **证据** | [追问包 A-H3](举一反三-超简历追问包.md) |
| **→ 追问** | E12 Netty worker 上能查 DB 吗？ |

### E12 · 为什么业务不能阻塞 IO 线程？（L3 · 40s）

| | |
|---|---|
| **问** | 一条慢 SQL 会怎样？ |
| **答** | **一个 worker 绑一组连接**；IO 线程阻塞 → 这组连接 **读写全停**，表现为 **全局卡顿**。我们 GIIC 热路径用 **reactive / 异步批写**，PSK 等不能 `.block()`。这是内嵌架构的 **硬约束**，也是压测时 Login 风暴的放大器。 |
| **→ 追问** | G6 per-connection 队列 |

### E13 · QoS / Clean Session / 半开连接？（L3 · 40s）

| | |
|---|---|
| **问** | MQTT 可靠性你怎么保证？ |
| **答** | **QoS0** 遥测可丢；关键指令 **QoS1 + 业务幂等**。半开靠 **keepalive 超时踢**（1.5 倍 keepalive 常见做法）。**Clean Session=false** 时会话状态占内存，压测要 **和生产一致**。内嵌和 EMQX **协议语义一样**，差别在 **集群持久会话** 谁实现。 |
| **→ 追问** | P8 压测 QoS 矩阵 |

### E14 · 内嵌怎么做限流 / 背压？（L3 · 40s）

|---|---|

| **答** | 四类：**① 规模**（150k 在线）；**② 吞吐**（5000 msg/s 属性 `[文档]`）；**③ 稳定性**（≥72h，我们 96h）；**④ 成功率**（Login ramp ≥99.5%）。缺任何一类都是 **压了个寂寞**。 |
| **证据** | [GIIC §1](../02-EMQX-IoT-Tuning/GIIC-15万压测参与复盘.md) · [C11 门槛示例](../middleware/mqtt/docs/03-运维篇/C11-loadtest-connections.md) |
| **→ 追问** | P3 怎么避免压了个寂寞 |

### P3 · 怎么避免「压了个寂寞」？（L3 · 40s）🔥

| | |
|---|---|
| **答** | 五条：**① 压测配置 = 生产配置**（我们 r2 后一套）；**② 真实 payload 与周期**（不是空连接）；**③ 全链路观测**（入口/网关/Redis/MySQL/ES）；**④ 阶梯加压**（1K→10K→…→目标）；**⑤ 验收可复现**（截图/面板/脚本 CSV）。只压连接不上报 = **假压测**。 |
| **→ 追问** | P4 阶梯模型 |

### P4 · 阶梯加压怎么压？（L3 · 40s）

| | |
|---|---|
| **答** | **连接阶梯**：1K → 10K → 50K → 目标，每阶 **稳 15–30min**；记录连接成功率、P99 连接耗时、CPU、内存、fd。**Login ramp** 单独阶段（我们早期 Login 风暴）。EMQX 行业也同理，[C11](../middleware/mqtt/docs/03-运维篇/C11-loadtest-connections.md)。 |
| **→ 追问** | P5 空连接 vs 真实上报 |

### P5 · 只压连接和压真实上报差在哪？（L3 · 40s）🔥

| | |
|---|---|
| **答** | **空连接**只测 **FD/内存/epoll**；**真实上报**才测 **解码、EventBus、ES/MySQL、Redis**。我们中期卡 14.3W 是 **Login/写放大**，空连接 **根本测不出来**。面试官问「几十万连接影响不大」——因为 **动态成本在存储**，不是连接挂着。 |
| **→ 追问** | P6 存储放大公式 |

### P6 · 为什么你体感瓶颈总在存储？（L4 · 60s）🔥

| | |
|---|---|
| **答** | 算一笔：15W 连接、30s/条 → **5000 msg/s** `[反推]`。每条进 EventBus 触发 **ES 时序 + MySQL 最新态 + Redis**；若 1 msg 展开 **3 属性** → **15000 ES docs/s** `[反推]`。连接静态 ~**1.5GB** 级 `[假设]`；存储 IO 是 **按 msg 线性放大**。所以网关优化后，**ES/NFS、MySQL 连接池、Redis 慢命令** 先爆。 |
| **证据** | [场景题 §2–3](场景题-容量预估L4-GIIC15W标准用例.md) · [ES NFS case](../02-EMQX-IoT-Tuning/cases/es-nfs-write-bottleneck-2026-08/README.md) |
| **→ 追问** | P7 连接数算内存 |

### P7 · 连接数内存怎么估？（L3 · 40s）

| | |
|---|---|
| **答** | **逐项加**：TCP 缓冲 + Channel 对象 + Session + 协议状态（PSK/Token）+ 业务 Operator 引用。我们文档有 **~11.8KB×37500≈440MB/实例** `[文档]` 与 **~10KB/连接** 规划 `[假设]`。**最坏**要算 **队列峰值**（32×payload `[文档]`）。 |
| **→ 追问** | G9/G10 |

### P8 · 压测参数矩阵（QoS / KeepAlive / Payload）？（L3 · 40s）

| | |
|---|---|
| **答** | 必须和生产 **同构**：QoS0/1、keepalive（过短 **心跳 CPU 高**）、payload 大小、上报间隔、Clean Session。改一项可能 **CPU 翻倍或内存翻倍**；EMQX/Mosquitto 开发机 **不能代替** 生产签字。 |
| **证据** | [C11 参数矩阵](../middleware/mqtt/docs/03-运维篇/C11-loadtest-connections.md) |
| **→ 追问** | P9 50W 心跳算吞吐 |

### P9 · 50W 设备 30s 心跳，吞吐多少？（L4 · 60s · 变体）

| | |
|---|---|
| **答** | 心跳也算消息：**50W/30s ≈ 1.67W msg/s** 起步，**比业务上报还大**。容量题 **先问消息模型**，不能把连接数当 QPS。门锁 **200W 低频** 则瓶颈回 **连接内存**，不是吞吐。 |
| **证据** | [追问包 A-V1/V2](举一反三-超简历追问包.md) |
| **→ 追问** | P10 四算框架 |

### P10 · 容量预估四算/六算？（L4 · 90s）🔥

| | |
|---|---|
| **答** | **连接数 → msg/s → 带宽 → CPU → 堆/连接内存 → 存储写入**。GIIC：**150k → 5000 msg/s → ~120Mbps 假设 → 72 核反推 → 32G 堆规划 → 15000 ES docs/s**。每步报 **态别**；带宽/ES 我们部分仍是 `[假设]`。 |
| **证据** | [场景题 Step 0–6](场景题-容量预估L4-GIIC15W标准用例.md) |
| **→ 追问** | P11 为什么不能峰值×3 |

### P11 · 为什么不用「峰值×3」估容量？（L3 · 30s）

| | |
|---|---|
| **答** | **峰值是验收给定的**（15W 就是 15W）；冗余针对 **拥堵和尖刺**（Login 风暴、bulk 落后），不是无脑乘系数。见 [压测评估基于实际数据](../02-EMQX-IoT-Tuning/压测评估基于实际数据.md)。 |
| **→ 追问** | G9 Login 尖刺 |

### P12 · 优化前 5k 就挂，是不是机器太小？（L3 · 40s）🔥

| | |
|---|---|
| **答** | **不是**。机器一直 **4×128G**；根因是 **全局 Sink 背压 + Redis/Login 风暴**，不是堆不够。32G 堆是按 **15W+Login 尖刺** 规划，和 5k 现象 **不矛盾**。 |
| **证据** | G4/G5/G9 |
| **→ 追问** | G6 per-connection |

### P13 · 入口层压测踩过什么坑？（L4 · 60s）

| | |
|---|---|
| **答** | **errno 99** 临时端口耗尽；**单 IP hash** 导致少机压测打爆单 Pod；**no live upstreams**。手段：**sysctl ip_local_port_range**、**hash(ip+port)**、**max_fails/backoff**、多入口/LVS。 |

### P16 · 你怎么定位瓶颈在哪一层？（L4 · 60s）🔥

|---|---|
