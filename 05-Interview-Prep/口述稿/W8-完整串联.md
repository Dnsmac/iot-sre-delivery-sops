## 2. 90 秒 IoT 全链路

设备通过 MQTT TCP 1883 连到 MetalLB VIP，由 Web 入口的 nginx 做 TCP 透传，进到 IoT 云平台接入服务 Pod 里内嵌的 MqttServer。这里不是独立 EMQX Broker，而是 JVM 线程在 Pod 里监听 1883。

连接时用 clientId 当设备 ID，从 MySQL 拿产品和密钥做认证。真正的 TCP 长连接在 Pod 内存里的 localSessions；同时往 Redis 写 connectionServerId 做集群路由。Pod 重启后 TCP 仍然要设备重连。

设备 PUBLISH 后，先进云平台内置 MQTT/CoAP 解码，再通过 DeviceMessageConnector 发到 EventBus；持久化侧由 ES 写时序、MySQL 写最新值和在线状态、Redis 做限流和路由。Pulsar 只讲级联、跨服务异步等已证链路，不说设备上报第一跳必须过 Pulsar。

下行时，API 如果打到没有该设备会话的 Pod，会查 Redis 的 connectionServerId，再经集群 RPC 转到持有 TCP 的 Pod，最后通过 MQTT 写回设备。

## 3. 三故事串联

### 故事一：IoT 云平台 15W 接入

IoT 云平台的接入服务（内部叫 iot-server）是接入网关，内置 MQTT 和 CoAP-TCP 两套网关，解码后统一进 EventBus。我参与的是 GIIC CoAP-TCP 15 万长连接压测；可讲的事实边界是：亲手处理或配合应用协议网关侧的明确事项，不把自己包装成整条接入线 owner 或全场方案 owner。验收口径是 5000 msg/s、连续长稳 96h。优化前几千连接就 Login 超时、Sink 断流，中期卡在十四万出头。

排查是分层的：入口临时端口耗尽、全局单管道背压、Login 写配置放大、Redis 热点叠在一起。我亲手处理/配合的应用协议网关侧事项是按连接拆队列、协议侧 L1 热缓存、Token 迁 Redis 并异步批写、公共工具 KEYS 改 SCAN。Nginx/sysctl 和 MySQL 生产档是协助对齐，平台整体方案不是我 owner。

### 故事二：operatorCache OOM

稳定性上有个典型问题：云平台服务跑两三天卡死，6G 和 8G 堆都一样。我先用 jstat 看 Old 区长期 96%，Full GC 次数几乎等于 Young GC，判断是堆常驻集过大，不是临时对象。

heap dump 用 MAT 看 Dominator Tree，发现 ExtendDeviceClusterConfiguration 一个对象占堆约 78%。沿 GC Root 追到 operatorCache，一个无界 Map 缓存了约 5050 个 DeviceOperator/物模型 JSON 对象树，每个 key 约 3 到 15MB，合计约 5.7G。我已完成定位并提出 Caffeine 上限和过期、设备注销 invalidate、历史补报绕开高频加载等方案；补丁待 Gerrit 正式流程合入，暂无复测收益。

### 故事三：ERP 并发正确性

ERP/电商只按历史材料讲：300+ 商户、日峰值约 3000 万，并记录分布式锁、幂等、唯一约束、状态机四类机制。它们在接口、回调、消费端、状态流里的具体落点和组合待本人核对，“零超卖/零重复扣款”也没有当前证据，因此不主动深讲，不包装成秒杀 owner。
