## 一、binlog 与两阶段提交（M1～M4 · 最易被挖穿）

**M1 · binlog 三种格式？各自问题？生产用哪个？** 60s 🔥
口径：三种——① **STATEMENT** 记 SQL 语句，省空间，但含 `UUID()`/`NOW()`/`LIMIT` 不带 `ORDER BY` 的函数在主从会不一致，已弃用；② **ROW** 记每行变更前后值，主从绝对一致，但量大；③ **MIXED** 默认 statement、判断有风险自动降 row（历史折中）。生产默认 **ROW**（MySQL 5.7.7+ 默认就是 row）：宁可量大，也要主从一致 + 可回放。

**M2 · binlog 和 redo log 的区别？** 50s 🔥
口径：四个维度——① 归属：redo 是 **InnoDB 引擎层**，binlog 是 **Server 层**（所有引擎共用）；② 内容：redo 是**物理日志**（记录"哪个页改了哪几字节"），binlog 是**逻辑日志**（记录 SQL 或行变更）；③ 写盘：redo 循环写（固定大小 ib_logfile），binlog 追加写（文件滚出）；④ 用途：redo 保证**崩溃恢复**（持久性），binlog 用于**主从复制 + 数据恢复**。

**M3 · 两阶段提交为什么需要？说清 commit 顺序** 60s 🔥
口径：更新一条数据时，InnoDB 写 redo、Server 写 binlog，两个日志必须**同时成功或同时失败**，否则主从不一致。2PC 流程：① redo 先 `prepare`；② 写 binlog；③ redo `commit`。为什么这个顺序能兜住：如果写完 redo 崩了、binlog 没写 → 重启按 redo 未 commit 回滚，主从都没这条数据；如果 binlog 写完了、redo 没 commit 就崩 → 重启时发现 binlog 有而 redo 是 prepare，就**补 commit**，主从都有。反过来如果先 commit redo 再写 binlog，中间崩溃会导致主库有数据、从库没有。核心就一句：**binlog 是主从一致性的仲裁者，redo 提交必须等 binlog 落盘**。

**M4 · binlog 怎么驱动主从复制？** 40s
口径：主库起 `dump` 线程把 binlog 推给从库；从库 `I/O 线程`写进本地 **relay log**，`SQL 线程`回放。半同步（`rpl_semi_sync`）是主库等至少一个从库 ack 才返回客户端，换一致性、牺牲一点延迟。

## 二、MVCC：快照读 vs 当前读（M5～M8 · 说不清就露怯）

**M5 · 快照读和当前读分别是什么？** 60s 🔥
口径：**快照读** = 普通 `SELECT`，读的是 ReadView 可见的历史版本，**不加锁、不阻塞写**。**当前读** = `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT`，读的是**最新已提交版本**并**加锁**。分水岭意义：同一个事务里，快照读看到的是事务开始时的世界，当前读看到的是实时世界——所以「用快照读判断、用当前读操作」是常见坑。
项目钩子：ERP 状态更新属于当前读/写路径，必须用短事务和状态条件约束；具体 SQL 待本人补证。

**M6 · ReadView 什么时候生成？RC 和 RR 差在哪？** 60s 🔥
口径：ReadView 是"这一刻哪些事务版本对我可见"的快照，含 active 事务列表 + 最小活跃 id + 下一个要分配的 id。**RC 每次快照读都重新生成** ReadView → 能看到别的事务新提交的数据（产生不可重复读）。**RR 只在事务第一次快照读时生成一次**，之后复用 → 看到的版本固定（解决不可重复读）。这就是「隔离级别靠 ReadView 生成时机」的本质。

**M7 · 幻读是什么？InnoDB RR 能完全防住吗？** 60s 🔥🔥
口径：幻读 = 同一事务内两次查询**多出了新插入的行**（重点：是**行数变化**，不是行值变化——行值变化叫不可重复读）。InnoDB 在 RR 下基本防住了，分两路：**快照读**靠 MVCC（ReadView 固定，新插入的行版本不可见，看不到）；**当前读**靠**间隙锁/next-key lock**（把插入位置锁死，别的连接插不进来）。所以「RR 不能防幻读」是**教科书（标准 SQL）的说法**，指当前读；InnoDB 用 next-key lock 补上了。一句话收口：**标准 RR 防不住，InnoDB 靠 next-key lock 防住了**。

**M8 · undo log 版本链怎么支撑 MVCC？** 50s
口径：每条记录带 `DB_TRX_ID`（最后改它的事务 id）和 `DB_ROLL_PTR`（指向上一个版本的 undo 指针）。每次更新不覆盖，而是**写一条 undo 串成版本链**。读时从最新版本沿指针往回找，找到 `trx_id < 当前 ReadView 可见下限` 的那个版本。这就是「读旧版本不阻塞写」的物理基础。清理靠 **purge 线程**，把没事务再需要的旧版本物理删掉。

## 三、锁与锁等待（M9～M12 · 定位是 L4 实操分）

**M9 · InnoDB 三种行锁？next-key lock 是什么？** 50s 🔥
口径：**记录锁 Record Lock** 锁单行；**间隙锁 Gap Lock** 锁索引记录之间的空隙，防插入；**临键锁 Next-Key Lock = 记录锁 + 左间隙**，RR 默认用 next-key 防幻读。关键前提：**行锁加在索引上**——查询走不到索引，锁退化成表锁，并发直接崩。等值查询且命中唯一索引时会退化成记录锁（不用 gap）。
项目钩子：ERP 的唯一约束可以讲“唯一索引兜底防重复”；不要编具体唯一键字段。

**M10 · 锁等待怎么定位？** 50s 🔥（实操 L4）
口径：三步走——① `SELECT * FROM information_schema.innodb_trx` 找长事务（`trx_started` 很早、状态 `LOCK WAIT`）；② `SELECT * FROM performance_schema.data_lock_waits`（8.0）或 `information_schema.innodb_lock_waits`（5.7）看「谁在等谁」的阻塞链（blocking_pid → requesting_pid）；③ `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段落。定位到阻塞事务后要么 `KILL` 掉，要么优化这个事务把锁范围缩小。
分级：通用机制题。除非本人补充事故证据，否则不说“我线上处理过某次锁等待”。

**M11 · 死锁怎么产生的？怎么避免？** 50s
口径：两事务**互相持有对方要的锁**形成环。经典场景：两个事务按**不同顺序**更新同一批行（A 先锁行1 再行2，B 先锁行2 再行1）。InnoDB 有死锁检测，检测到就**回滚代价最小的事务**。避免三板斧：① 更新顺序统一；② 缩小事务（快进快出，别在事务里做 RPC/远程调用）；③ 减少锁粒度（命中索引、避免范围锁）。项目钩子只能讲 ERP 状态机能收敛并发更新面；是否出现过死锁风暴待本人补证。

**M12 · 事务里放远程调用为什么危险？** 40s
口径：锁持有时间 = 事务时长。事务里调一次 RPC，可能几十 ms 到几 s，期间行锁一直不放 → 其他事务排队 → 连锁成锁等待甚至死锁。原则：**事务只包数据库操作，RPC/文件/缓存读写挪到事务外**（或拆成「先查→业务→再短事务更新」）。
项目钩子：ERP/IoT 都能讲“短事务 + 幂等补偿”，但不能编具体远程调用事故。

## 四、主从与高可用（M13～M15 · 兜底）

**M13 · 主从延迟怎么处理？** 40s（对齐 D9，升级）
口径：三层——① 写后立即读走**主库**（强制路由）；② 关键读带**版本号/时间戳**，判断陈旧则回源主库；③ 监控 `Seconds_Behind_Master` 阈值告警。根因治理：从库并行复制（组提交并行）、避免大事务。

**M14 · 分库分表后全局唯一 ID 怎么生成？** 40s
口径：雪花算法（时间戳 + 机器号 + 序列号，趋势递增适合索引）；Redis 自增；号段模式（一次取一段放内存，性能高）。不能再用单库自增（会重复）。
项目边界：ERP 可讲“唯一业务号/唯一约束防重复”的思想，具体 ID 生成方案待本人补证。

**M15 · 高可用方案一句话？** 30s
口径：主从 + 半同步（保数据不丢），MHA / MGR / 上云 RDS 自动 failover。兜底：异地灾备靠 binlog 同步 + 定期演练。
