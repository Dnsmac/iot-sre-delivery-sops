# 面试连环深追脚本

> 用途：七个必问维度的主练脚本。所有数字和边界以 [数字与边界-唯一索引](数字与边界-唯一索引.md) 为准。
> 固定顺序：真实锚点 → 项目怎么用 → 数字/证据 → 机制 → Why/代价 → 3~5 连追 → 换场景 → 反抛 → 边界。

---

## 1. 业务场景：IoT 设备接入主链路

- **真实锚点**：GIIC 15W CoAP-TCP 长连接、iot-server 第一跳解码、EventBus 进程内分发。
- **项目怎么用**：设备报文先进入 iot-server 协议网关段，解码后通过 EventBus 分发到后续 ES/MySQL 等处理链；下行由业务侧触发后按会话路由找到连接所在实例再写回设备。
- **数字/证据**：15 万在线连接、5000 msg/s、96h 长稳 `[文档]`；15W ÷ 30s = 5000 msg/s `[反推]`。
- **机制**：协议解码和连接治理放在入口服务内，实时主链路避免先落外部 MQ；跨服务、级联、长积压才讲 Pulsar。
- **Why/代价**：EventBus 减少第一跳链路长度和延迟，代价是进程内分发的背压、隔离和故障边界要自己治理。
- **3~5 连追**：
  1. 设备上报第一跳为什么不先走 Pulsar？
  2. EventBus handler 慢了怎么隔离？
  3. 下行怎么找到设备在哪个 Pod？
  4. 15W 连接怎么估算入口机器和 JVM 档位？
  5. 如果 10 倍设备量，先扩哪一层？
- **换场景**：换成车联网或充电桩，入口协议不同，但“连接入口、会话路由、异步落库、背压保护”仍是主线。
- **反抛**：您想听 30 秒链路图，还是听 15W 压测里这条链路怎么验收？
- **边界**：不说设备上报第一跳走 Pulsar；不说自己是平台总体方案 owner。

## 2. 并发：连接队列与背压

- **真实锚点**：GIIC 压测中 per-connection 队列和水位保护。
- **项目怎么用**：入口侧按连接维度控制消息排队，队列满或服务水位过高时拒绝/降级，避免一个热点连接或全局队列拖垮所有连接。
- **数字/证据**：`queue-size=32` 见只读现网 `application.yml` 和 GIIC 交接 §5 `[文档]`；它是 GIIC 单连接入队容量，不外推到所有协议。所谓 90% 是默认“最大堆剩余 <10% 且持续 >5s”的派生表达 `[源码/文档]`，不是连接数水位。约 14.3W 为阶段性现象 `[文档]`。
- **机制**：局部队列 + 明确拒绝策略 + 水位阈值，比无限队列更可控；线程池只负责执行，不能替代业务背压。
- **Why/代价**：有界队列保护 JVM 和下游，代价是会提前暴露失败，需要客户端重试、幂等和监控配合。
- **3~5 连追**：
  1. 32 是怎么来的，能不能无限调大？
  2. reject 会不会丢消息？
  3. 队列按连接拆和全局队列有什么差别？
  4. 90% 水位看的是连接、线程、堆还是下游？
  5. 线程池满和连接队列满分别怎么处理？
- **换场景**：电商秒杀也一样，入口限流和库存预扣要先挡峰值，不能让请求无限进库。
- **反抛**：这个题我可以从线程池讲，也可以从 15W 连接背压讲，您想听哪条？
- **边界**：引用 [`GIIC压测-规划方法论与交接Playbook.md`](../02-EMQX-IoT-Tuning/GIIC压测-规划方法论与交接Playbook.md) Phase 3；32 是 GIIC 默认配置，不声称全场景压测校准。90% 只答“最大堆已用比例的近似派生值”，不与 OOM 的 `Old >90%` 混同。

## 3. MySQL：幂等、唯一约束与状态机

- **历史材料锚点**：300+ 商户、日峰值约 3000 万；材料记录分布式锁、幂等、唯一约束、状态机四类机制。
- **项目怎么用**：具体落在接口、回调、消费端还是状态流，当前待本人核对；面试不替历史材料补链路。
- **数字/证据**：规模与四类机制为历史材料 `[文档]`；组合顺序、表结构、SQL、事故、结果与优化收益均待本人补证。
- **机制**：唯一约束负责“不能重复”，状态机负责“不能乱跳”，事务负责“同一笔状态更新原子提交”；锁只是降低冲突，不是正确性的唯一来源。
- **Why/代价**：把正确性落在 MySQL 约束上更稳，代价是要处理唯一键冲突、状态更新失败和重试幂等。
- **3~5 连追**：
  1. 幂等号选订单号、请求号还是第三方流水号？
  2. 只有 Redis 锁没有唯一约束行不行？
  3. 状态机通用上怎样限制非法流转，项目具体状态流是否已核对？
  4. 并发更新同一订单怎么避免锁等待扩大？
  5. 如果要证明没重复，查什么证据？
- **换场景**：IoT 指令下发、设备注册、告警去重也可以用“幂等 key + 唯一约束/状态机”防重复。
- **反抛**：这段历史材料的具体链路还没核对，我当前只讲规模和四类机制；若需要我可转到有证据的 IoT 并发案例。
- **边界**：ERP 当前不主动深讲；不宣称零超卖、零重复扣款，不编接口/回调/消费端/状态流落点。

## 4. MQ：EventBus 与 Pulsar 的边界

- **真实锚点**：设备上报主链路走 iot-server EventBus；Pulsar 只讲级联、跨服务异步、长积压等已证链路。
- **项目怎么用**：实时解码后在进程内分发；需要跨服务削峰、级联或积压隔离时才引入 Pulsar。
- **数字/证据**：设备上报链路、Pulsar 边界见唯一索引 `[文档]`；不把 155GB ES buffer 积压拿来证明 MQ 优劣。
- **机制**：EventBus 是进程内发布订阅，低延迟但隔离弱；Pulsar 是外部 MQ，能持久化和削峰，但引入序列化、网络和消费延迟。
- **Why/代价**：主链路追求实时和短路径，跨服务链路追求解耦和可恢复，两者不是互相替代。
- **3~5 连追**：
  1. 为什么设备上报不先落 Pulsar？
  2. Pulsar 用在哪些链路才合理？
  3. 积压了先看生产端、Broker 还是消费端？
  4. 顺序性按设备维度怎么保证？
  5. 消息重复怎么靠业务幂等兜底？
- **换场景**：电商订单可以先写本地事务再发 MQ，IoT 指令也要靠业务 idempotency 接受至少一次。
- **反抛**：您想追“消息不丢不重”，还是追“为什么这条链路不用 MQ”？
- **边界**：不说“落 ES/MySQL 前必须过 Pulsar”。

## 5. 性能：ES 写慢但 CPU 不高

- **真实锚点**：10W 级 K8s/IoT 写入链路，ES data on NFS 导致 bulk 写慢和 buffer 积压。
- **项目怎么用**：排查时不只看 CPU，而是沿入口、队列、bulk、ES 线程池、磁盘/网络 IO 分层定位，最终把慢点收敛到 NFS 写路径。
- **数字/证据**：elasticsearch-buffer 积压合计约 155GB `[文档]`。
- **机制**：Lucene 写段、flush/fsync 对数据盘延迟敏感；NFS 把本地磁盘写放大成网络 IO 等待。
- **Why/代价**：把 ES 数据盘放 NFS 容易获得运维便利，但牺牲实时写入稳定性；改成本地盘或专用块存储要付出迁移和容量管理成本。
- **3~5 连追**：
  1. CPU 不高为什么服务还是慢？
  2. 怎么区分应用慢、bulk 慢和 ES 存储慢？
  3. 155GB 积压说明了什么，不能说明什么？
  4. 如果不能立刻迁盘，怎么止血？
  5. 怎么证明修复后不是偶然恢复？
- **换场景**：MySQL 慢写、Kafka/Pulsar 积压也按“入口速率、队列、消费、存储 IO”分层。
- **反抛**：这个题我建议按故障定位讲，因为 CPU 不高但慢最容易考排查链。
- **边界**：不编造完整修复收益，不把 155GB 用作外部 MQ 对比。

## 6. 压测：GIIC 15W 容量验证

- **真实锚点**：GIIC 15W CoAP-TCP 长连接，5000 msg/s，96h 长稳。
- **项目怎么用**：从连接数、吞吐、带宽、存储写入、连接/会话内存、机器/JVM/DB 档位六项估算，再用压测验证瓶颈。
- **数字/证据**：15W、5000 msg/s、96h `[文档]`；1KB×3、152Mbps、约 620GB/天是历史保守 `[假设]+[反推]`。450B 仅见 Playbook 文档值 `[文档/待补实测]`；抓包、网卡增量和 ES 增量实测均未完成。
- **机制**：先定 SLA 和流量模型，再分层压入口、应用、下游和存储；每次只改一类关键变量，避免不知道是哪层生效。
- **Why/代价**：容量估算能提前暴露瓶颈，代价是模型参数必须标证据态，不能把假设说成现网实测。
- **3~5 连追**：
  1. 5000 msg/s 怎么从 15W 推出来？
  2. 15W 连接要不要等于 15W 活跃写？
  3. 带宽和 ES 写入怎么估？
  4. 96h 长稳主要看哪些指标？
  5. 40W/20W 和 15W 关系怎么诚实表达？
- **换场景**：20W MQTT 是官方/假设迁移题，我没做过；只迁移 GIIC 的澄清、六算、基线和验收方法。
- **反抛**：我可以直接按六算展开，也可以先讲 96h 稳定性验收。
- **边界**：40W 只作平台背景；20W MQTT 明确没做过，不作为经历。

## 7. 优化：operatorCache OOM 定位与待合入方案

- **真实锚点**：`-Xmx8G`、约 5050 台设备后 OOM，operatorCache 缓存 DeviceOperator/物模型 JSON 对象树。
- **项目怎么用**：通过 jstat、histo/dump、MAT Dominator 定位大对象和引用链，提出有界、过期、水位告警和写入路径治理方案；补丁待 Gerrit 正式流程合入。
- **数字/证据**：约 5050 key、每 key 约 3~15MB、Dominator 约 5.7G/78% `[文档]`。
- **机制**：无界缓存持有强引用，GC 只能回收不可达对象，无法回收仍在 Map/Caffeine 中的对象树；大对象留在老年代后触发连环 Full GC。
- **Why/代价**：扩堆只能缓解容量压力，不能修复无界缓存；有界方案的代价是可能增加回源、重建延迟和缓存命中率波动。目前暂无合入后的复测收益。
- **3~5 连追**：
  1. 为什么 GC 回收不了？
  2. 怎么从现象定位到 operatorCache？
  3. 为什么不是直接把 8G 改 32G？
  4. maximumSize、TTL、水位告警分别解决什么？
  5. 怎么验证修复没引入频繁回源？
- **换场景**：Redis 热 key、本地 Caffeine、ThreadLocal 泄漏都先看“引用是否可达、容量是否有界、淘汰是否生效”。
- **反抛**：这个题我建议从真实 OOM 数字讲，比只背 GC 参数更有说服力。
- **边界**：8G OOM 和 32G GIIC 容量规划必须分开讲；只说“完成定位并提出方案，补丁待合入，暂无复测收益”。
