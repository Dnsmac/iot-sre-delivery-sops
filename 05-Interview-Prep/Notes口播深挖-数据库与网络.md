## 一、数据库 · 10 题（面试最高频）

### D1 · 为什么 InnoDB 用 B+ 树不用 B 树 / 哈希？

- **一句话**：B+ 树 **非叶子只存键**，叶子链表串联，**IO 次数少 + 范围查询稳**；哈希只支持等值。
- **展开**：磁盘页 16KB，B+ 树扇出大 → 树矮；范围查扫叶子链表即可。哈希等值 O(1) 但不支持排序/最左前缀。
- **钩子**：GIIC Login 风暴时 MySQL 连接顶满，索引对不对直接决定是 **索引查找还是全表扫**。

### D2 · 聚簇索引 vs 二级索引？

- **一句话**：聚簇索引 **叶子存整行**，表数据物理按主键排序；二级索引叶子存 **主键值**，回表再查聚簇。
- **追问**：「覆盖索引？」→ `EXPLAIN` 里 `Using index`，不回表。 「一个表几个聚簇？」→ **只能一个**（InnoDB 主键即聚簇）。
- **钩子**：设备在线状态表我们查 **deviceId 主键 + 状态字段覆盖**，避免回表放大。

### D3 · 索引什么时候失效？（随口 5 条）

- `%like` 左模糊、**or 一侧无索引**、**隐式类型转换**（字符串列比数字）、**不满足最左前缀**、优化器判断 **全表扫更便宜**。
- **定位**：`EXPLAIN` 看 `type`、`key`、`rows`；`possible_keys` 有但 `key` 空就是没用上。
- **钩子**：压测时 Redis `KEYS` 和 MySQL 全表扫一样——都是 **热路径上的 O(N) 炸弹**。

### D4 · 事务隔离级别 + 各解决什么？

- **一句话**：RU 脏读；RC 解决脏读；RR（MySQL 默认）解决不可重复读；Serializable 解决幻读但性能最差。
- **机制**：RC/RR 靠 **MVCC 快照读**；当前读（`SELECT FOR UPDATE`）靠 **间隙锁/next-key** 防幻读。
- **钩子**：ERP 订单状态迁移用 **状态机 + 行锁**，不靠调高隔离级别硬扛。

### D5 · MVCC 怎么实现？（RR 下）

- **一句话**：每行有 **隐藏版本链**（undo log），ReadView 决定可见哪个版本；**快照读** 不阻塞写，**当前读** 加锁。
- **追问**：「RR 能完全防幻读吗？」→ 快照读防；当前读靠间隙锁。 「幻读和不可重复读区别？」→ 前者 **新行出现**，后者 **同一行值变**。
- **钩子**：Token 异步批写是 **最终一致**，和 MVCC 读快照不是一回事——别混成「数据库解决了就不用管业务一致」。

### D6 · redo / undo / binlog 各干什么？

- **redo**：崩溃恢复，保证 **持久性**（物理页级，WAL 先写日志再写盘）。
- **undo**：回滚 + MVCC 版本链，保证 **原子性**。
- **binlog**：主从复制、审计，**逻辑日志**；两阶段提交保证 redo 与 binlog 一致。
- **钩子**：ES NFS 写慢是 **存储 IO 等**，和 MySQL redo 刷盘慢是同一类「持久化路径堵了」。

### D7 · 慢 SQL 怎么定位？（40s 定位链）

- **链**：慢日志 / `SHOW PROCESSLIST` → `EXPLAIN` → 看 `type`（至少 range）→ `rows` 是否离谱 → 是否回表 → 是否锁等（`information_schema.innodb_trx`）。
- **改**：加/改索引、改写 SQL（去 `SELECT *`、深分页改游标）、拆大事务。
- **钩子**：GIIC 中期 **MySQL 连接池打满**，根因之一是 Login 写 configuration **写放大**，不是单纯「加内存」。

### D8 · 深分页为什么慢？两解法？

- **原因**：`LIMIT 1000000,10` 要扫/排序丢弃前 100 万行。
- **解法**：**游标分页**（`WHERE id > last_id LIMIT 10`）；或 **延迟关联**（子查询只拿 id 再 join）。
- **钩子**：ERP 订单列表我们禁止无脑深分页，必须 **带时间范围 + 索引列游标**。

### D9 · 主从延迟怎么处理？

- **一句话**：写后读走 **主库** 或 **缓存**；关键读带 **版本号/时间戳** 判断陈旧则回源主库；监控 `Seconds_Behind_Master`。
- **钩子**：设备影子「最新态」在 Redis，MySQL 是持久层——和读写分离延迟处理同构。

### D10 · 连接池怎么配？（结合 IoT）

- **原则**：`连接数 × 实例数 < MySQL max_connections`；池大小跟 **并发写线程** 走，不是跟 **设备连接数** 走（R2DBC 异步更要显式限流）。
- **钩子**：GIIC 我们按 **内存档位选 MySQL 生产档 + 连接池联动**，不是默认 Hikari 10。

## 二、网络 · 8 题（IoT 岗必挖）

### N1 · TCP 三次握手 / 四次挥手（各一句话）

- **握手**：SYN → SYN+ACK → ACK；目的 **同步序列号 + 双方确认收发能力**。
- **挥手**：FIN → ACK → FIN → ACK；**TIME_WAIT** 等 2MSL 防旧包干扰（高并发要调 `tcp_tw_reuse` 等，GIIC Nginx 侧干过）。
- **钩子**：MQTT 长连接建立在 TCP 之上；**半开连接**靠应用层 keepalive 踢，不能只信 TCP。

### N2 · TCP 和 UDP 选型（IoT 语境）

- **TCP**：可靠、有序、有连接；适合 **指令下发、固件、要确认的业务**。
- **UDP/CoAP**：省头部、可广播；适合 **低功耗传感器**；可靠自己补（CoAP 有 CON/ACK）。
- **钩子**：GIIC 走 **CoAP-TCP** 折中；MQTT 默认 TCP 1883。

### N3 · 流量控制 vs 拥塞控制？

- **流量控制**：接收窗口，**端到端**「你别发太快我收不下」。
- **拥塞控制**：慢启动/拥塞避免，**网络路径**「大家都别挤爆路由器」。
- **钩子**：应用层我们还有 **水位拒连 + per-connection queue-size=32**，是第三层「别把我 JVM 撑死」。

### N4 · epoll 为什么能 C10K/C10M？

- **一句话**：**事件驱动**，fd 就绪才回调，O(1) 监听大量连接；对比 `select/poll` 的 O(n) 扫全表。
- **LT vs ET**：LT 水平触发安全但唤醒多；ET 边缘触发高效但要把缓冲区读空。
- **钩子**：Netty **boss/worker + epoll**，内嵌 MqttServer 百万连接讨论都绕不开这套。

### N5 · Socket 编程流程对应三次握手？

- **服务端**：`socket → bind → listen → accept`（accept 返回时三次握手完成）。
- **客户端**：`socket → connect`（connect 成功即握手完成）。
- **数据**：`send/recv`；结束 `close`。

### N6 · HTTP/1.1 vs HTTP/2 一句话？

- HTTP/1.1：**队头阻塞**（同连接请求串行）、Keep-Alive。
- HTTP/2：**多路复用** 单连接并行流，头部 HPACK 压缩；仍受 TCP 丢包阻塞影响。
- **钩子**：设备接入不用 HTTP 扛百万连接；**管理面 OpenAPI** 才是 HTTP，要和数据面分开讲。

### N7 · TLS 握手在链路哪一层？（15s）

- **顺序**：TCP 握手 → **TLS 握手**（证书、密钥交换）→ 应用数据（MQTT CONNECT）。
- **钩子**：nginx 做 **TLS 终结**，后端 Pod 内明文 MQTT，证书收口在接入层（选型卡②）。

### N8 · 长连接网关水平扩展（和 A-H6 对齐）

- **三件套**：接入 LB → **会话路由表**（deviceId→nodeId）→ 下行 **跨节点 RPC** 转发。
- **禁忌**：在网关进程里堆 **无界本地状态**（OOM 案例 operatorCache 反面教材）。
- **钩子**：Redis `connectionServerId` + 集群 RPC，就是我们现网答案。
