# 故事草稿 · 压测与性能优化证据包

> 卖点：**参与压测闭环 + 分层排障**，不卖「全平台压测负责人」。  
> 索引：[`02-EMQX-IoT-Tuning/cases/README-压测性能案例索引.md`](../../02-EMQX-IoT-Tuning/cases/README-压测性能案例索引.md)

## 背景

IoT 平台同时扛：长连接接入压测（GIIC 15W）、超级设备 OpenAPI 接口压测、ES 高写入、堆内存与 Redis 代理链路问题。

## 冲突

1. 主机资源未打满，写入/接口仍不达标 → 瓶颈常在 IO、缓存、等设备、代理窄路。  
2. 容易误判：把 MQTT 拒连当「连接打满」、把 Redis 超时当「Redis 挂了」、把 TPS 不够当「只缺加机器」。  
3. 政策边界：部分模块禁改；压测角色是参与优化与验收，不是方案唯一 owner。

## 行动（可举证）

| 线 | 做了什么 |
|----|----------|
| GIIC 15W | 协议/网关侧多轮改造 + 协助 Nginx/sysctl/MySQL；96h 长稳证据 |
| OpenAPI 五接口 | 拆拓扑 vs E2E；物模型节点缓存（36630）；拓扑 TTL/缓存方案 |
| operatorCache OOM | jstat/jcmd → MAT → OQL 证实 5050×~1MB+ 常驻 ~6G |
| ES 写入 | 定位 NFS IO + buffer/dead；给出 replicas/refresh/换盘分层建议 |
| Redis 压测 | camellia 上游窄路 / 假连接；直连 Cluster 与池对齐方案 |
| MQTT 水位 | 区分水位拒连 vs 业务打满 |

## 结果（诚实）

- 有铁证数字：15W/96h、5050/5.7G、五接口优化前 TPS 表、ES buffer 量级。  
- 部分优化「方案+PR 已落、复测数字待补」——面试讲方法与边界，不编造达标率。

## 30 秒

> 我参与过 GIIC 十五万长稳，也做过超级设备 OpenAPI 压测拆解和堆 OOM 的 MAT 定位。习惯先分清瓶颈在存储 IO、本地缓存、等设备回包还是代理连接池，再决定是改代码、改配置还是换基础设施，避免只加机器。
