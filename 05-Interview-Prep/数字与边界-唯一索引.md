## 0.5 对外命名映射（2026-09-03 定）

> 规则：**对面试官说/写的表述用业务名，内部服务名只作证据索引**。本仓 SOP、题库、命令、源码路径里的真实服务名不改（那是证据锚点）；一切口述稿、话术、画像、简历表述按本表翻译。

| 内部叫法 | 对外表述 | 用法 |
|----------|----------|------|
| iot-server / kh-iot-server | **IoT 云平台**（接入服务） | 口述首次说「IoT 云平台，内部服务叫 iot-server」，之后只说 IoT 云平台；命令/路径/类名场景可念 iot-server |
| iot-web | 平台 Web 入口（nginx TCP 透传层） | 不单独念服务名 |
| device-manager | 设备管理服务（内部名） | 提及时带「内部叫 device-manager」 |
| EventBus | 平台进程内事件分发（EventBus） | 保留，EventBus 本身是通用词 |

## 1. 红线五条

1. **不说设备上报第一跳走 Pulsar**：第一跳是协议解码 → iot-server EventBus → ES/MySQL；Pulsar 只讲级联/跨服务等已证链路。
2. **不把 GIIC 15W 说成 40W/20W owner**：15W CoAP-TCP 是主讲；20W MQTT 是官方/假设迁移题，不是个人经历；40W 仅作平台背景且不充当 20W 证据。
3. **不把内嵌 MqttServer 说成独立 EMQX 集群**：现网是 Netty 内嵌 MQTT，外层 nginx stream 透传。
4. **不混 OOM 8G 和 GIIC 32G**：OOM 案例是 `-Xmx8G`、约 5050 台；32G 是 GIIC 15W 容量规划线。
5. **不把 operatorCache 说成操作员权限缓存**：它是 DeviceOperator/物模型 JSON 对象树缓存，不是“操作员/权限”业务缓存。

## 2. GIIC 15W 六算

> 主口径：GIIC 15W CoAP-TCP 长连接，验收 5000 msg/s、连续长稳 96h；本人负责/参与协议网关段和稳定性排查，平台总体方案非 owner。

| 六算 | 口径 | 证据态 |
|------|------|--------|
| ① 连接数 | 15 万在线连接；压测侧按 5 × 3 万线程组织 | `[文档]` |
| ② 吞吐 | 5000 msg/s；可由 150000 ÷ 30s 反推 | `[文档]` + `[反推]` |
| ③ 带宽 | 历史保守模型：5000 × 3 属性 × 1KB × 8 ≈ 120Mbps；加心跳/ACK 约 152Mbps | `[假设]` + `[反推]`；未完成抓包实测 |
| ④ 存储写入 | ES 约 15000 docs/s = 5000 msg/s × 3 属性；历史按单 doc 0.5KB 粗算约 620GB/天 | `[假设]` + `[反推]`；未完成 ES 增量实测 |
| ⑤ 连接/会话内存 | 单实例连接对象、缓冲、会话表按项估算；口播只报数量级和公式 | `[假设]` + `[反推]` |
| ⑥ 机器/JVM/DB 档位 | 服务端 4 × 128G 物理机混部；GIIC 容量规划可讲 32G JVM 档；MySQL 按生产档位和连接池联动 | `[文档]` |

### 2.1 中期现象与保护参数

| 项 | 唯一口径 | 证据态 |
|----|----------|--------|
| ~14.3W | 中期现象：优化后曾在约 14.3W 附近卡住；只用于说明阶段性瓶颈，不上升为“内嵌 Netty 天花板” | `[文档]` |
| 450B/msg | 仅见 `GIIC压测-规划方法论与交接Playbook.md` 的文档值，仓内无原始抓包、脚本输出或网卡增量证据 | `[文档/待补实测]`；不能标 `[实测]`，不能据此制造唯一带宽/存储实测值 |
| queue-size=32 | 现网只读配置 `khlinks-standalone/src/main/resources/application.yml` 的 `giic.connection.queue-size: 32`；交接 `docs/ops/GIIC压测优化-交接文档.md` §5 同值 | `[文档]`；是 GIIC CoAP-TCP 单连接入队容量，不代表所有协议/场景都校准为 32 |
| “90% 水位” | `SystemUtils` 默认 `memory.watermark=0.1`，判定的是 JVM 最大堆**剩余比例 <10% 且持续 >5s**；`MqttServerDeviceGateway.handleConnection` 随后拒绝新 MQTT 连接 | `[源码/文档]`；“约 90%”是已用堆比例的派生表达，不是连接数水位，也不等同于 OOM 案例的 Old 区占用率 |

## 3. OOM 数字

| 项 | 唯一口径 |
|----|----------|
| 触发线 | `-Xmx8G`，约 5050 台设备后出现堆 OOM |
| 根因对象 | `operatorCache` 缓存 DeviceOperator/物模型 JSON 对象树 |
| 规模 | 约 5050 key，每个 key 约 3~15MB |
| MAT 证据 | Dominator 约 5.7G，占堆约 78% |
| 当前结论 | 已完成定位并提出有界缓存方案；补丁待 Gerrit 正式流程合入，暂无复测收益 |
| 方案边界 | maximumSize/过期/invalidate/写入路径收敛均为待合入方案，不得说“已治理、已修完或收益从 A 降到 B” |
| 禁混 | 32G 是 GIIC 15W 容量规划，不是这次 OOM 现场堆大小 |

## 4. ES NFS / 155GB

| 项 | 唯一口径 |
|----|----------|
| 场景 | 10W 级 K8s/IoT 写入链路排查，可作为 ES 写慢故事 |
| 根因链 | ES data on NFS → Lucene/fsync 等待网络 IO → bulk 写慢/超时 → buffer 积压 |
| 数字 | elasticsearch-buffer 积压合计约 155GB |
| 面试重点 | CPU 不高但慢，优先看 IO wait/写线程/存储路径；NFS 不适合作 ES 实时数据盘 |
| 边界 | 155GB 仅是 ES NFS / elasticsearch-buffer 积压证据；不用于任何外部 MQ 优劣对比；不编造完整修复收益 |

## 6. EventBus / Pulsar 链路边界

| 链路 | 唯一口径 |
|------|----------|
| 设备上报主链路 | 设备协议报文 → iot-server 第一跳解码 → EventBus 进程内分发 → ES/MySQL |
| 下行链路 | iot-web/业务触发 → EventBus/会话路由 → 内嵌 MqttServer 写回设备 |
| Pulsar 可讲链路 | 级联、跨服务异步、长积压、已证削峰场景 |
| Pulsar 禁区 | 不把设备上报第一跳、实时解码主链路说成 Pulsar；不说“落 ES/MySQL 前必须过 Pulsar” |
