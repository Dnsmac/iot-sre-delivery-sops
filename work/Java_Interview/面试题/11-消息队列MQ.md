# 11 · 消息队列 MQ

> 覆盖：为什么用 MQ、主流选型、可靠投递（不丢消息）、消息不重复（幂等）、顺序消费、消息积压、重复消费、事务消息、如何设计一个 MQ。以 Kafka / RocketMQ / RabbitMQ 为主。

---

## 一、为什么用 MQ

### 1. MQ 的三大核心作用 🔥

- **解耦**：上下游通过消息通信，互不依赖。
- **异步**：非核心流程异步化，缩短主流程响应时间。
- **削峰填谷**：流量高峰时消息堆积在 MQ，消费者按自身能力消费，保护下游。

### 2. MQ 的缺点 ⭐

- **系统可用性降低**：MQ 挂了影响整个链路（需高可用）。
- **复杂度提升**：要处理重复消费、顺序、一致性、积压。
- **一致性问题**：异步可能导致数据不一致。

### 3. 主流 MQ 选型 🔥

| 维度 | RabbitMQ | Kafka | RocketMQ |
| --- | --- | --- | --- |
| 语言 | Erlang | Scala/Java | Java |
| 吞吐 | 万级 | **百万级** | 十万~百万级 |
| 延迟 | 微秒级（最低） | 毫秒级 | 毫秒级 |
| 功能 | 灵活路由 | 流处理、日志 | 事务/顺序/延迟消息齐全 |
| 适用 | 业务解耦、低延迟 | **大数据、日志、流** | **金融级业务、电商** |

> 选型经验：日志/大数据流 → Kafka；电商/金融业务且要事务/顺序/延迟消息 → RocketMQ；中小业务、复杂路由 → RabbitMQ。

## 二、可靠性（不丢消息）🔥🔥

消息丢失可能发生在三个环节，要逐段保证：

### 4. 生产者不丢

- 同步发送 + 确认机制：Kafka `acks=all`（所有 ISR 副本确认）+ 重试；RabbitMQ **confirm 机制**；RocketMQ 同步发送返回 SEND_OK。
- 发送失败重试 + 本地消息表兜底。

### 5. MQ 自身不丢

- **持久化 + 多副本**：Kafka `replication.factor>=3`、`min.insync.replicas>=2`；RabbitMQ 队列和消息持久化 + 镜像/Quorum 队列；RocketMQ 同步刷盘 + 主从同步复制。
- 关闭可能丢数据的优化（如 Kafka `unclean.leader.election`）。

### 6. 消费者不丢

- **手动 ACK**：消费**处理成功后**再确认，而非拉到就确认（自动 ACK 在处理失败时会丢）。
- 消费失败重试 + **死信队列（DLQ）** 兜底。

## 三、重复消费与幂等 🔥

### 7. 如何保证不重复消费（幂等）

MQ 通常保证 **at-least-once（至少一次）**，无法天然 exactly-once，所以**消费端必须幂等**：

- 业务唯一键 + 数据库唯一索引（重复插入失败）。
- 用 Redis/DB 记录已处理的消息 ID（去重表）。
- 状态机：只允许特定状态流转。
- 乐观锁（version）。

> 详见 [15-分布式](./15-分布式.md) 幂等设计。

---

## 四、顺序消费 🔥

### 8. 如何保证消息顺序

- **全局顺序**：单分区/单队列 + 单消费者（牺牲吞吐，少用）。
- **局部顺序（推荐）**：把需要有序的消息（如同一订单）按 key **路由到同一分区/队列**，分区内有序，消费者单线程消费该分区。
  - Kafka：同一 key → 同一 partition。
  - RocketMQ：`MessageQueueSelector` 按订单 ID 选队列，顺序消费用 `MessageListenerOrderly`。
- 注意消费端多线程会打乱顺序，需保证单分区单线程处理。

## 五、积压与延时 🔥

### 9. 几百万消息积压几小时怎么解决

- 临时**扩容消费者**：但受分区数限制（Kafka 消费者数 ≤ 分区数）。
- 紧急方案：写一个临时分发程序，把积压消息**快速转发到一个新建的、分区数更多的临时 topic**，再用大量临时消费者并行处理。
- 事后：排查消费慢的原因（下游慢、消费逻辑重），优化消费性能，提前做好容量规划与监控告警。

### 10. 消息过期失效 / 队列满了

- 设置了 TTL 的消息过期会被丢弃 → 高峰期临时关闭 TTL，事后**手动写程序补偿**重发丢失的消息。
- 队列满 → 触发拒绝/死信，需扩容 + 限流生产者。

### 11. 延迟消息 ⭐

- RocketMQ：内置延迟级别（或 5.0 任意时间延迟）。
- RabbitMQ：TTL + 死信队列，或 `delayed-message-exchange` 插件。
- Redis：ZSet（score 为到期时间）轮询，或 Redisson 延迟队列。

## 六、事务消息与设计

### 12. RocketMQ 事务消息 🔥

解决“本地事务 + 发消息”的原子性（典型：下单扣库存）：

1. 发送**半消息（half message）**，对消费者不可见。
2. 执行本地事务。
3. 本地事务成功 → **commit**（消息可见）；失败 → rollback（丢弃半消息）。
4. 若 Broker 未收到二次确认，**回查**生产者本地事务状态，决定提交还是回滚。

是分布式事务“**最终一致**”的经典实现，类似本地消息表。

### 13. 让你设计一个 MQ，怎么设计 ⭐（架构题）

- **存储**：顺序写磁盘 + 分段日志（参考 Kafka 的分区 + 顺序追加 + 零拷贝），保证高吞吐。
- **高可用**：分区多副本 + Leader/Follower + 故障自动切换。
- **可扩展**：Topic 分区化，水平扩展 Broker。
- **可靠性**：刷盘策略、副本同步、生产/消费确认机制。
- **消费模型**：消费组 + offset 管理，支持广播/集群消费。
- 配套：消息索引、重试、死信、延迟、监控。

## 项目实战 · IoT 消息链路（EventBus / Pulsar / 缓冲队列 · 脱敏）

> **红线**：设备 **PUBLISH 第一跳 → EventBus**，**不是 Pulsar**。Pulsar 用于 **级联/异步** 另线。

### 1. 三条「队列」别混

| 名字 | 是什么 | 积压时现象 |
| --- | --- | --- |
| **EventBus** | 进程内/集群 **消息分发**（DeviceMessageConnector 后） | connector 等 publish；**禁改** device-manager 时不能 fire-and-forget |
| **Pulsar** | **级联、跨平台** 异步 | “20W级联”仅为历史材料/待核对，当前无硬证，不作本人主讲经历 |
| **PersistenceBuffer / elasticsearch-buffer** | 写 ES 前的 **磁盘 FIFO 队列** | ES on NFS 堵 → 每 Pod **~30GB+**，合计 **~155GB**；失败进 **dead** |

### 2. 和 MQ 八股的对照答法

| 面试问 | IoT 口径 |
| --- | --- |
| 为什么用 MQ？ | 设备接入用 **EventBus 解耦** 规则/持久化；跨平台才 **Pulsar** |
| 怎么不丢？ | ES 路径：**bulk + buffer 重试**；Pulsar：**持久化+消费确认**（级联） |
| 积压怎么办？ | ES 堵：**先修 IO（SSD）**，再消化 buffer；不是无限扩消费者 |
| 顺序？ | 单设备消息进 **per-connection 队列** 保序；Kafka 分区思想类似 |

### 3. GIIC 连接队列（非 Kafka）

- `giic.connection.queue-size=32`：每连接有界；满则 **reject**（背压）  
- Token async r8：**批写队列**跟不上 → 调 batch/concurrency/capacity + **PENDING 日志限频**

### 4. 口播 30 秒

> 设备上报 **先进 iot-server 内置 MQTT/CoAP，再 EventBus**，Pulsar 只服务级联。压测写 ES 堵时，应用侧 **elasticsearch-buffer** 堆到百 GB，说明 **MQ/缓冲层积压** 和 **存储 IO** 要一起看，不能只调 JVM。

### 5. Pulsar 级联分区（通用机制 + 历史材料边界）

> **口径**：“20W级联”目前只有历史简历材料，`40万压测参与复盘.md` 线 B 仍为空表，没有规模、脚本、指标或结果硬证据，不作本人可主讲经历。它与“20W MQTT官方/假设容量题”完全不同。若后续补证，仍只按实际角色写参与/协助；当前以下分区内容按通用机制回答。

**Q1：级联为什么用 Pulsar，设备上报为什么不走？**
> 设备上报要**低延迟 + 单连接保序 + 进程内分发**，EventBus 内嵌在 iot-server 直接分发，不过中间件；Pulsar 是**跨平台/级联异步**（把消息投递给外部平台），要的是**持久化 + 削峰 + 多租户**。两者诉求不同，别混成「设备走 MQ」。

**Q2：Pulsar 分区数怎么定？**
> `目标写入吞吐 ÷ 单分区安全能力(5~10 MB/s)`，向上取整，再乘 1.3~2 余量。分区是**并行度上限**：消费者并行度 ≤ 分区数，分区定小了积压时「加消费者也没用」。**只能增不能减**（Key 哈希路由会乱），所以初始宁可留余量。

**Q3：积压了怎么处理？**
> 先看**下游为什么慢**（级联对端/存储），不是无脑扩分区。真要大并发消化：**扩分区 + 对应加消费者**（受分区数约束）；或临时转发到分区更多的新 Topic，用临时消费者并行。这和 Kafka「临时扩分区转发」同思路（本文 9）。

**Q4：级联要顺序吗？**
> 按设备/消息 Key 要局部有序 → **分区 + Key_Shared**（同 Key 进同分区、同消费者）；否则 Shared 并行消费即可。**Key_Shared 要求 Producer 必设 Key**，否则退化成乱序。

## 高频追问清单

- 怎么保证消息不丢？→ 生产/存储/消费三段（本文 4/5/6）。
- exactly-once 能做到吗？→ 一般 at-least-once + 消费幂等（本文 7）。
- 怎么保证顺序又不牺牲全部吞吐？→ 按 key 局部有序（本文 8）。
- 大量积压怎么紧急处理？→ 扩分区 + 临时转发（本文 9）。

- **级联分区数怎么定，能减少吗？** → 吞吐÷单分区能力(5~10MB/s)向上取整；只能增不能减（项目实战 §5 Q2）。
