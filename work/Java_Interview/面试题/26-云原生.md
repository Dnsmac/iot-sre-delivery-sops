## 〇、什么是云原生

### 0.1 一句话

云原生不是「用了 Docker + K8s」，而是一套**让应用在分布式、弹性、可观测环境下持续交付的工程方法论**。CNCF 定义的代表技术：容器、微服务、服务网格、不可变基础设施、声明式 API。

### 0.2 十二要素（面试只背这 5 条）

| 要素 | 一句话 | 现网映射 |
|------|--------|----------|
| 配置与代码分离 | 配置走环境变量/配置中心，不打包进镜像 | K8s ConfigMap / Nacos |
| 无状态进程 | 本地不存会话/数据，状态外置 | Redis / MySQL / ES |
| 端口绑定 | 应用自声明端口，不依赖外部容器注入 | Spring Boot `server.port` |
| 日志当事件流 | 输出 stdout，平台采集 | Filebeat → ELK |
| 快速启动与优雅终止 | 启动快才能弹性扩；终止前处理完存量 | `preStop` + `SIGTERM` 处理 |

> **面试官陷阱**："你们应用是有状态还是无状态？"——iot-server 内嵌 MqttServer 维护长连接会话，**表面无状态、实际有连接状态**，所以 Rolling Update 时必须配 `preStop` 等待连接漂移，否则客户端重连风暴。

## 一、容器与 Docker（底层机制）

### 1. 容器与虚拟机的本质区别 🔥

| 维度 | 容器 | 虚拟机 |
|------|------|--------|
| 隔离机制 | Namespace + Cgroups（内核级，共享宿主内核） | Hypervisor + 硬件虚拟化（独立内核） |
| 启动速度 | 秒级（`clone` 新进程） | 分钟级（完整 OS 引导） |
| 资源开销 | MB 级（只多一个进程空间） | GB 级（完整 OS 内存） |
| 安全边界 | **共享内核 = 内核漏洞可穿透**（如 CVE-2016-5195 Dirty COW） | 硬件级隔离，漏洞穿透难 |
| 密度 | 单机千级 | 单机数十级 |

> **关键认知**：容器不是轻量 VM，是**「被限制和隔离的进程」**。理解这一点才能解释为什么容器里 `top` 看到的是宿主机的 CPU（早期没有 `pid` Namespace 隔离 `/proc`）。

### 2. Namespace：隔离了什么、没隔离什么 🔥🔥

Linux Kernel 3.8+ 支持的 8 种 Namespace：

| Namespace | 隔离资源 | 系统调用 / 标志 | 没隔离的坑 |
|-----------|----------|----------------|-----------|
| PID | 进程 ID 空间 | `CLONE_NEWPID` | `init` 进程退出后所有子进程被 SIGKILL |
| Network | 网络设备、端口、路由、防火墙 | `CLONE_NEWNET` | **宿主机 `/proc/net` 仍可见**（直到 Kernel 4.6+ `netns` 完全隔离） |
| Mount | 文件系统挂载点 | `CLONE_NEWNS` | `mount` 传播（`shared`/`slave`）导致宿主机挂载被容器看到 |
| UTS | 主机名/域名 | `CLONE_NEWUTS` | — |
| IPC | System V IPC / POSIX 消息队列 | `CLONE_NEWIPC` | — |
| User | UID/GID 映射 | `CLONE_NEWUSER` | 内核文件系统（如 `/proc`）仍用真实 UID 检查权限 |
| Cgroup | Cgroup 根目录（v2） | `CLONE_NEWCGROUP` | v1 无此 Namespace |
| Time | 系统时间 | `CLONE_NEWTIME` | 极少用 |

**创建容器的系统调用链**：
```c
// Docker / containerd 底层调用 runc → 调用 clone()
clone(CLONE_NEWNS | CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWIPC | CLONE_NEWUTS | CLONE_NEWUSER)
```

> **追问**：Namespace 隔离了视图，但**系统调用还是走宿主内核**。所以容器里加载内核模块（`insmod`）会影响全宿主机——除非用 User Namespace 做 root 映射 + capabilities 裁剪。

### 3. Cgroups：资源限制的实现与坑 🔥🔥

#### 3.1 Cgroups v1 的层级结构

```
/sys/fs/cgroup/
├── cpu/
│   └── docker/<container-id>/
│       ├── cpu.cfs_quota_us    # 限制：每周期可用 CPU 时间（微秒）
│       ├── cpu.cfs_period_us   # 周期（默认 100ms = 100000）
│       └── cpu.shares          # 相对权重（CPU 争抢时分配比例）
├── memory/
│   └── docker/<container-id>/
│       ├── memory.limit_in_bytes      # 硬上限（超则 OOM Kill）
│       ├── memory.usage_in_bytes      # 当前使用
│       ├── memory.stat                # 详细统计
│       └── memory.kmem.limit_in_bytes # 内核内存（Docker 默认不限制！）
└── blkio/...
```

**核心公式**：
- CPU limit = `quota / period`。设 `quota=50000, period=100000` → 限制为 **0.5 核**
- `cpu.shares` 只在 CPU 饱和时生效。容器 A shares=1024，B shares=512，A 拿 2/3。

#### 3.2 Cgroups v1 的致命坑：内存统计不准确

```bash
# 容器里看内存
$ cat /sys/fs/cgroup/memory/memory.usage_in_bytes
# 这个值 = RSS + Cache + 内核内存(kmem)
# 但 kmem 默认不限制！Java 堆外内存（DirectBuffer / JNI）走 kmem → 容器 OOM 但 kmem 没统计进去
```

**你的现网 case**：`operatorCache OOM` 那次，如果容器 limit=8G，`-Xmx8G`，JVM 认为自己用了 8G，但容器 `memory.usage_in_bytes` 还包含元空间、线程栈、直接内存、页缓存——**实际 RSS 远超 limit** → K8s OOM Kill。**这不是 JVM OOM，是容器 OOM**（Exit Code 137 = 128 + `SIGKILL` 9）。

#### 3.3 Cgroups v2 的改进

| v1 问题 | v2 改进 |
|---------|---------|
| 内存 controller 统计含 page cache，应用无法区分 | `memory.current` 细分 `anon`（RSS）vs `file`（cache） |
| kmem 单独限制，默认不启用 | 统一计费，`memory.max` 一刀切 |
| 多个 hierarchy（cpu/memory/blkio 分离） | 统一挂载到 `/sys/fs/cgroup`，单文件树 |
| 线程级迁移复杂 | `thread` 模式支持线程粒度 |

> **面试金句**："我们 K8s 集群用的 Cgroups v1，Java 容器化时踩过 kmem 不限制的坑，后来升级到 JDK 11 + 显式设 `-XX:MaxRAMPercentage=75` + 容器 limit 留 25% 给非堆，才稳住。"

### 4. UnionFS / overlay2：镜像分层与写时复制 🔥🔥

#### 4.1 overlay2 的三元组结构

```
mount -t overlay overlay \
  -o lowerdir=/var/lib/docker/overlay2/l/XXX:/var/lib/docker/overlay2/l/YYY, \
     upperdir=/var/lib/docker/overlay2/<id>/diff, \
     workdir=/var/lib/docker/overlay2/<id>/work \
  /var/lib/docker/overlay2/<id>/merged
```

| 目录 | 作用 |
|------|------|
| `lowerdir` | 只读层（镜像层），可多层，用 `:` 分隔 |
| `upperdir` | 可写层（容器层），所有修改写这里 |
| `workdir` | 内核工作目录，必须和 `upperdir` 同文件系统 |
| `merged` | 合并视图，容器内看到的文件系统 |

**文件查找规则**：
- 打开文件：从 `upperdir` 往下层 `lowerdir` 找，找到第一个即停。
- 写文件：
  - 若文件只在 `lowerdir`：**CoW（写时复制）**——先把文件拷贝到 `upperdir`，再修改。
  - 若文件已在 `upperdir`：直接改。
- 删除文件：在 `upperdir` 创建 **whiteout 文件**（字符设备 `0:0`）标记删除，不真删 `lowerdir`。

#### 4.2 生产坑：overlay2 的 inode 耗尽

Docker 默认存储驱动 `overlay2`，但 `/var/lib/docker` 和容器数据目录如果在同一个文件系统：
- 每个镜像层、每个容器的 `upperdir` 都占 inode。
- 频繁构建产生大量中间层 → **inode 耗尽但磁盘空间还有** → `No space left on device`，`df -i` 看 inode 使用率 100%。

**排查命令**：
```bash
# inode 使用率
$ df -i /var/lib/docker
# 哪个 layer 占最多 inode
$ find /var/lib/docker/overlay2 -xdev -printf '%h\n' | sort | uniq -c | sort -k1 -n | tail -20
# Docker 清理
$ docker system prune -a --volumes
```

> **现网映射**：你们镜像构建用 Harbor，CI 节点如果 `docker build` 不清理中间层，inode 耗尽会导致后续构建失败。建议 CI 流水线加 `docker system prune` 或改用 Kaniko（无 daemon，每层独立清理）。

### 5. Dockerfile 与镜像优化（从「能跑」到「最优」）

#### 5.1 多阶段构建的层缓存策略

```dockerfile
# 阶段 1：依赖层（变动最少，放最前）
FROM maven:3.9-eclipse-temurin-21 AS deps
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline

# 阶段 2：编译层（源码变动时才重建）
FROM deps AS build
COPY src ./src
RUN mvn -B clean package -DskipTests

# 阶段 3：运行层（最小攻击面）
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
USER app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**层缓存失效规则**：只要某层之前任何一层变化，该层及之后全部重建。所以 `COPY pom.xml` 在 `COPY src` 前面——改一行代码不重新下载 500MB 依赖。

#### 5.2 Java 镜像的「不可能三角」

| 目标 | 手段 | 代价 |
|------|------|------|
| 体积小 | alpine / distroless | musl libc 兼容性问题（某些 JNI 库崩溃） |
| 启动快 | AOT / CDS | 构建时间增加、反射受限 |
| 调试方便 | 保留 shell / jcmd / jmap | 攻击面大、镜像体积增加 |

**选型建议**：
- **生产运行**：`eclipse-temurin:21-jre`（glibc，兼容性好，体积适中）
- **严格安全场景**：`distroless` + sidecar 调试（单独跑一个 debug 容器进 Namespace 调试）
- **避免**：`alpine` + 复杂 JNI（如某些物联网协议库依赖 glibc）

### 6. Java 应用容器化的深度调优 🔥🔥🔥

#### 6.1 JVM 容器感知的演进

| JDK 版本 | 容器支持 | 默认行为 |
|----------|----------|----------|
| < 8u191 | ❌ 无 | 按宿主机 CPU/内存设默认值 |
| 8u191+ / 10+ | ✅ `UseContainerSupport` | 读取 cgroup limit，但只读 v1 |
| 15+ | ✅ Cgroups v2 支持 | 兼容 v1/v2 |

**关键参数链**：
```bash
# 推荐（比例而非固定值，适配不同 limit 的 Pod）
-XX:+UseContainerSupport          # JDK 8u191+ 默认开启
-XX:MaxRAMPercentage=75.0         # 堆占容器内存 75%
-XX:InitialRAMPercentage=50.0     # 初始堆 50%（避免启动时频繁扩堆）
-XX:MaxDirectMemorySize=1G        # 限制堆外直接内存（Netty / NIO 用）
```

#### 6.2 CPU Limit 对 Java 的隐性伤害

K8s CPU limit 通过 Cgroups `cpu.cfs_quota_us` 实现。**Java 的 JIT 编译器、GC 线程数、`ForkJoinPool.commonPool` 都依赖 `Runtime.availableProcessors()`**。

问题：JVM 读取的是 Cgroups 的 CPU **quota**（即 limit），而非实际分配。如果 limit=1 核：
- `availableProcessors()` 返回 1
- G1 GC 线程数 = 1（默认 `MaxGCPauseMillis` 下需要并行 GC 线程 = CPU 数）
- JIT 编译线程 = 1
- `ForkJoinPool` 并行度 = 0（`max(1, availableProcessors()-1)`）

**结果**：一个需要 2~4 核 GC 吞吐的应用，被 limit=1 后，GC 时间暴涨 → STW 增加 → RT 飙升。**CPU 没打满但 RT 高**，就是因为 limit 卡死了并行度。

> **面试话术**："我们压测时遇到过：CPU 使用率 50% 但 P99 很高，后来发现是 CPU limit=1，G1 只能单线程 GC。取消 limit（只设 request）或提高 limit 后，P99 下降 60%。"

#### 6.3 容器内存 = 堆 + 元空间 + 线程栈 + 直接内存 + 页缓存 + JVM 自身

估算公式（容器 limit 必须覆盖）：
```
container_limit ≥ heap(-Xmx) + metaspace(~256M) + threads(线程数×1M) + directMemory + nativeMemory + 页缓存(buffer/cache)
```

**你的 iot-server**：`-Xmx8G` + 大量 Netty 直接内存（MQTT 连接）+ 线程数高（5k~15k 连接）→ 实际 RSS 可能 10G+。如果容器 limit=8G → **必被 OOM Kill**。

**正确做法**：
- 先压测看实际 RSS（`kubectl top pod` 或容器内 `cat /sys/fs/cgroup/memory/memory.usage_in_bytes`）
- limit = RSS 峰值 × 1.3（缓冲）
- 堆设 limit 的 60~70%，留出非堆空间

### 7. 容器运行时演进：dockershim → CRI → 更短链路

```
K8s 1.23 及以前：
  kubelet → dockershim（K8s 内嵌）→ dockerd → containerd → runc → 容器

K8s 1.24+：
  kubelet → CRI → containerd（或 CRI-O）→ runc → 容器

未来趋势（安全沙箱）：
  containerd → containerd-shim → gVisor / Kata Containers（独立内核）
```

**关键理解**：
- `runc` 是 OCI 标准运行时，真正调用 `clone()` 创建容器。
- `containerd` 是守护进程，管理镜像拉取、容器生命周期、存储。
- **Docker 构建的镜像仍能在 containerd 运行**，因为都遵循 OCI image-spec。

## 二、Kubernetes（控制循环与生产陷阱）

### 10. 为什么需要 K8s 🔥

Docker 解决「单个容器怎么跑」，K8s 解决「**大规模容器集群怎么编排**」：
- **调度**：把 Pod 放到合适的 Node（过滤 + 打分）
- **自愈**：Pod 挂了自动重建；Node 挂了上面的 Pod 漂移到其他 Node
- **弹性**：HPA 按指标扩缩 Pod
- **发布**：滚动更新、回滚
- **服务发现**：Service 提供稳定 IP，DNS 自动注册
- **配置管理**：ConfigMap / Secret 解耦配置与镜像

### 11. 控制平面与声明式 API 🔥🔥

#### 11.1 控制循环（Reconcile Loop）

K8s 的核心设计模式：
```
用户声明期望状态（YAML）→ etcd 存储
    ↓
Controller（Informer List-Watch）监测到变化
    ↓
Controller 对比「期望状态」vs「实际状态」
    ↓
执行操作让实际状态逼近期望状态（创建 Pod、删 Pod、扩缩容）
    ↓
循环往复
```

**每个核心对象都有对应的 Controller**：
- Deployment → Deployment Controller → 管理 ReplicaSet
- ReplicaSet → ReplicaSet Controller → 管理 Pod 副本数
- Service → EndpointSlice Controller → 维护后端 Pod IP 列表
- Node → Node Controller → 监测 Node 健康，驱逐超时 Node 上的 Pod

> **追问**："如果我直接 `kubectl delete pod`，Deployment 会做什么？"——ReplicaSet Controller 发现实际 Pod 数 < 期望数，会立即创建新 Pod。**删除 Pod 只是触发了一次重建**。

#### 11.2 etcd：为什么是唯一事实源

- **Raft 共识算法**：3/5 节点，Leader 处理写请求，Follower 异步复制。写操作需要半数以上确认才提交。
- **所有状态都存在 etcd**：Pod 定义、Node 状态、ConfigMap、Secret、Service 端点。
- **API Server 是唯一读写 etcd 的组件**：其他组件（Scheduler、Controller、kubelet）都通过 API Server 间接访问，保证一致性。
- **性能瓶颈**：etcd 是 K8s 集群规模的硬瓶颈。官方建议 ≤ 5k Node / 150k Pod。大规模集群需要拆分 etcd（事件分离）或提升磁盘 IOPS。

### 12. 核心对象与使用场景 🔥

| 对象 | 适用场景 | 不适用 |
|------|----------|--------|
| **Deployment** | 无状态应用（Web、API、iot-server） | 需要稳定网络标识 / 有序部署 |
| **StatefulSet** | 有状态中间件（MySQL、Redis、Kafka、ES） | 无状态应用（浪费） |
| **DaemonSet** | 每节点一个（日志采集、监控、网络插件） | 多副本弹性应用 |
| **Job / CronJob** | 一次性批处理 / 定时任务 | 长期运行服务 |
| **Service** | 集群内服务发现 + 负载均衡 | 外部七层路由（用 Ingress） |

**StatefulSet 为什么有状态**：
- 稳定网络名：`pod-name-0.service-name.namespace.svc.cluster.local`
- 独立 PVC：每个 Pod 挂独立盘，删 Pod 数据不丢
- 有序部署：从 0 到 N-1 逐个启动，逆序停止（保证主从复制不中断）

> **现网映射**：你们的 MySQL 集群、Redis 集群、ES 集群应该都是 StatefulSet + PVC。iot-server 是 Deployment（无状态，连接断了自己重连）。

### 13. 资源管理：requests / limits 与 QoS 🔥🔥🔥

#### 13.1 requests vs limits 的本质区别

| 维度 | requests | limits |
|------|----------|--------|
| **调度时** | Scheduler 按 requests 算 Node 剩余资源，决定 Pod 放哪 | 不参与调度 |
| **运行时** | 不限制实际使用 | Cgroups 硬限制，超则 throttle（CPU）或 OOM Kill（内存） |
| **HPA 依据** | 可按 requests 计算利用率（如 `targetAverageUtilization: 70` = 实际 CPU / requests） | — |

#### 13.2 QoS 等级与驱逐顺序

K8s 在 Node 资源紧张（内存/磁盘压力）时，按 QoS 驱逐 Pod：

| QoS | 条件 | 驱逐优先级 |
|-----|------|-----------|
| **Guaranteed** | 所有容器：requests == limits；且只设了 CPU + 内存 | **最后驱逐** |
| **Burstable** | 至少一个容器：requests < limits；或只设了 requests | 中间 |
| **BestEffort** | 所有容器：requests/limits 都没设 | **最先驱逐** |

**生产陷阱**：
- 内存 limits **必须设**，且建议 `requests == limits`（Guaranteed），否则 Node 内存紧张时先被驱逐。
- CPU **建议不设 limits**（只设 requests），避免 throttle。需要上限时用 HPA 控制副本数，而不是掐单 Pod。

> **你的现网 case**：10W K8s 压测时，BestEffort Pod（没设 requests/limits）占满内存 → iot 和 ES 竞争 → **必须加反亲和（Anti-Affinity）** 把两类 Pod 分到不同 Node。如果当时设了 Guaranteed + 合理 requests，Scheduler 会在调度时就拒绝超售，不会运行时才争用。

### 14. 调度：从 nodeSelector 到 Pod 拓扑分布 🔥

#### 14.1 调度三阶段

```
1. 过滤（Predicates）：排除不满足硬性条件的 Node
   - 资源足够（requests 之和 < Node allocatable）
   - 满足 nodeSelector / Affinity
   - 不满足 Taint（除非有 Toleration）
   - 满足 Pod 拓扑分布约束

2. 打分（Priorities）：给剩余 Node 打分，选最高分
   - 资源均衡（避免单个 Node 堆满）
   - 亲和性权重
   - 节点已运行同镜像 Pod（镜像缓存命中）

3. 绑定（Bind）：把 Pod 和 Node 关联，写入 etcd
```

#### 14.2 亲和与反亲和：什么时候用什么

| 场景 | 用 | YAML 关键字段 |
|------|-----|--------------|
| 必须跑在 SSD 节点 | nodeSelector | `nodeSelector: {disk: ssd}` |
| 偏好 SSD 但机械也能跑 | Node Affinity | `preferredDuringScheduling` |
| 同一应用副本分散到不同 Node | Pod Anti-Affinity | `podAntiAffinity: topologyKey: kubernetes.io/hostname` |
| 缓存 Pod 和 Web Pod 同 Node | Pod Affinity | `podAffinity` |
| 专用节点（如 master）排斥普通 Pod | Taint + Toleration | `taints: [{key: node-role, value: master, effect: NoSchedule}]` |

> **追问**："如果 Node 挂了，上面有 Anti-Affinity 的 Pod 怎么办？"——Anti-Affinity 只影响**调度时**的放置，不影响运行时的迁移。Node 故障后，Pod 被驱逐，重新调度时会再次检查 Anti-Affinity，保证新 Node 不冲突。

### 15. 网络模型：从 Pod IP 到 Service 到 Ingress 🔥🔥

#### 15.1 三层网络

```
Pod Network（CNI）：
  每个 Pod 一个独立 IP，集群内直接互通（扁平网络）
  
Service Network（ClusterIP）：
  虚拟 IP，由 kube-proxy 维护 iptables/IPVS 规则，把流量负载到后端 Pod
  
Ingress（七层）：
  域名/路径路由，外部流量入口。底层仍是 NodePort / LoadBalancer + 反向代理（nginx/traefik/envoy）
```

#### 15.2 kube-proxy 的三种模式

| 模式 | 原理 | 适用场景 | 缺点 |
|------|------|----------|------|
| **iptables** | 每条 Service 对应 N 条 iptables 规则（N=后端 Pod 数） | 小规模（< 1k Service） | 规则数 O(n²)，更新延迟（内核 netfilter） |
| **IPVS** | 内核中的 L4 负载均衡器，规则数 O(n) | 大规模（> 1k Service） | 需要内核模块 `ip_vs` |
| **IPVS-DR** | 直接路由，回包不经过 kube-proxy | 高性能 | 配置复杂 |

> **你的现网**：MetalLB 暴露的 VIP 是 L2（ARP）或 BGP 模式，不是 Ingress。设备 MQTT 流量走 `1883 → MetalLB VIP → nginx Stream 模块 → iot-server Pod`。这是**四层负载均衡**，Ingress 只处理七层 HTTP/HTTPS， MQTT 用不了 Ingress。

#### 15.3 CoreDNS 与服务发现

```
服务名.命名空间.svc.cluster.local
```
- 同 Namespace 内：直接 `curl http://iot-server:8080`
- 跨 Namespace：`curl http://iot-server.iot:8080`
- Pod 直接访问：`pod-ip-10-244-1-5.default.pod.cluster.local`

CoreDNS 配置在 `Corefile` 里，可配缓存 TTL、转发到外部 DNS、负载均衡策略（`round_robin`）。

### 16. 探针：liveness / readiness / startup 的决策链 🔥🔥🔥

#### 16.1 三个探针的语义

| 探针 | 失败行为 | 设计目的 | 常见坑 |
|------|----------|----------|--------|
| **liveness** | 重启容器 | 进程假死（如死锁、无限等待） | 配置太敏感 → 循环重启（CrashLoopBackOff） |
| **readiness** | 从 Service 端点摘除 | 容器还没准备好接流量（如连接池未初始化） | 配置太宽松 → 流量打到还没就绪的 Pod → 报错 |
| **startup** | 禁用 liveness/readiness，直到通过 | 保护慢启动应用（Spring Boot 启动 60s+） | 设太短 → 启动期被 liveness 误杀 |

#### 16.2 优雅停机（Graceful Shutdown）完整链路

```
1. 用户执行 kubectl delete pod / 滚动更新触发
2. K8s 把 Pod 状态设为 Terminating
3. 同时做两件事：
   a. 从 Service EndpointSlice 删除该 Pod IP（ readiness 自动失败）
   b. 给容器内 PID 1 发 SIGTERM（可配置 terminationGracePeriodSeconds，默认 30s）
4. 应用收到 SIGTERM：
   a. 停止接新请求（Spring Boot: management.server.shutdown=graceful）
   b. 处理完存量请求
   c. 关闭连接池、释放资源
5. 如果超 grace period 还没退出 → K8s 发 SIGKILL（强制终止）
6. 可选 preStop 钩子：在 SIGTERM 前执行自定义脚本（如通知负载均衡器先摘流）
```

> **你的现网教训**：`readiness 过早`——Spring Boot 启动了但 Redis 连接池还没热，readiness 已通过，流量进来报错。后来加了 `initialDelaySeconds` 或改 readiness 检查「/health 且连接池可用」。

#### 16.3 长连接服务的特殊处理

iot-server 维护 MQTT 长连接，**优雅停机必须等客户端主动断开或超时**：
```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15"]  # 等连接漂移
terminationGracePeriodSeconds: 60  # 给足够时间处理存量连接
```

如果没有 `preStop` sleep，Pod 立即收到 SIGTERM，主动关闭 TCP 连接 → 客户端收到 RST → 客户端立即重连 → **重连风暴压垮剩余 Pod**。

### 17. 弹性伸缩：HPA / VPA / Cluster Autoscaler 🔥

| 组件 | 伸缩维度 | 触发条件 | 限制 |
|------|----------|----------|------|
| **HPA** | Pod 副本数 | CPU / 内存 / 自定义指标（QPS、MQ 堆积） | 受限于 Node 资源（没 Node 了只能 pending） |
| **VPA** | 单 Pod 的 requests/limits | 历史资源使用模式 | 需要重启 Pod（有状态应用慎用） |
| **Cluster Autoscaler** | Node 数量 | Pod 因资源不足 pending | 云厂商支持（AWS/Azure/GCP/阿里云） |

**HPA 的数学**：
```
desiredReplicas = ceil[currentReplicas × (currentMetricValue / targetMetricValue)]
```

> **追问**："HPA 扩容时，新 Pod 启动需要时间，流量高峰已经过了怎么办？"——
> 1. **预测式扩容**：KEDA + Prometheus + 业务指标（如队列长度增速）提前扩容
> 2. **兜底**：PodDisruptionBudget 保证最小可用；预热副本（overprovision）
> 3. **你的场景**：IoT 连接是长连接，新 Pod 不会立即分担已有连接，需要客户端重连或负载均衡器主动迁移——这是 K8s 原生做不到的，需要应用层配合（如 MQTT broker 的会话迁移）。

### 18. 存储：从 emptyDir 到 CSI 🔥

#### 18.1 存储类型对比

| 类型 | 生命周期 | 数据持久 | 适用场景 |
|------|----------|----------|----------|
| `emptyDir` | Pod | ❌ | 临时缓存、共享内存 |
| `hostPath` | Node | ⚠️（Node 换就没了） | 单节点日志、监控（不推荐生产） |
| `nfs` | 外部 | ✅ | 共享读、低并发写 |
| `PV/PVC + StorageClass` | 独立 | ✅ | 生产有状态应用 |

#### 18.2 你的现网教训：ES on NFS

```
ES data on NFS → 高并发写时 NFS 成为瓶颈 → 索引写入变慢 → Pulsar backlog → 级联故障
```

**根因链**：
1. NFS 协议基于文件锁和同步语义，高并发随机写性能差（尤其小文件频繁 fsync）
2. ES 索引底层是 Lucene，写操作频繁 `fsync` 保证 durability
3. NFS 的 `fsync` 是网络往返 → RTT 放大 → 写吞吐量暴跌

**正确做法**：
- ES data 用 **本地 SSD**（`hostPath` 或 `local` PV）或 **云盘 PV**（EBS、阿里云 ESSD）
- 如果需要共享，用 **对象存储**（S3、MinIO）做 snapshot，而非 NFS 做实时数据

> **面试话术**："我们踩过 ES 数据放 NFS 的坑，写性能瓶颈导致 Pulsar 消息积压。后来改为本地盘 + elasticsearch-buffer 组件做缓冲，写性能提升一个数量级。"

## 三、发布策略与编排工具

### 19. 发布策略的工程权衡 🔥🔥

| 策略 | 资源成本 | 回滚速度 | 风险 | 适用场景 |
|------|----------|----------|------|----------|
| **滚动更新** | 1x（maxSurge 控制） | 慢（逐 Pod 回滚） | 中 | 通用无状态应用 |
| **蓝绿** | 2x | 秒级（切流量） | 低 | 核心交易、支付 |
| **金丝雀** | 1x + 小部分额外 | 快（切回来） | 低 | 新功能验证、A/B 测试 |
| **重建** | 0x（停服期间） | 快 | 高 | 非在线任务 |

#### 19.1 滚动更新的隐藏参数

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # 更新时最多超出的 Pod 数（或百分比）
      maxUnavailable: 25%  # 更新时最少可用的 Pod 数
```

**数学**：设副本数=4，`maxSurge=1, maxUnavailable=1`：
- 第一轮：启动 1 个新 Pod（总数 5），等就绪后停 1 个旧 Pod（总数 4）
- 第二轮：再启动 1 个新 Pod（总数 5），停 1 个旧 Pod（总数 4）
- ... 直到全替换

**坑**：`maxUnavailable=0` + `maxSurge=0` 同时设为 0 → 无法滚动（必须至少一个大于 0）。

#### 19.2 金丝雀发布的技术实现

**七层（HTTP）**：Ingress-Nginx / Istio 按权重分流
```yaml
# Ingress-Nginx
nginx.ingress.kubernetes.io/canary: "true"
nginx.ingress.kubernetes.io/canary-weight: "10"  # 10% 流量给新版本
```

**四层（TCP/MQTT）**：需要负载均衡器支持（MetalLB 不支持权重），或应用层自己做（如客户端随机数决定连哪个端点）。

> **你的场景**：MQTT 长连接是四层，金丝雀难做。通常做法是**新开一个 Service 指向新版本 Pod**，让新设备连新 Service，老设备保持老连接。这是**连接级灰度**，不是请求级。

### 20. Helm 与 Operator 🔥

#### 20.1 Helm 的本质

Helm 是 K8s 的「包管理器 + 模板引擎」：
- **Chart**：一组模板化的 YAML + `values.yaml`（参数文件）
- **Release**：Chart 的一次安装实例（可升级、回滚）
- **Values 覆盖**：`helm install -f my-values.yaml` 覆盖默认参数，实现多环境（dev/staging/prod）差异化

#### 20.2 Operator 模式：把运维知识代码化

```
CRD（自定义资源定义）：定义一种新的 K8s API 对象（如 MySQLCluster）
    ↓
Operator（自定义控制器）：Watch 这种对象，执行运维操作
    ↓
实现：自动部署、备份、故障切换、扩缩容
```

**经典 Operator**：
- **etcd-operator**：自动 etcd 集群管理
- **prometheus-operator**：自动发现 ServiceMonitor，配置 Prometheus 抓取
- **mysql-operator**：自动主从复制、备份、故障切换

> **面试话术**："我们还没有自己写 Operator，但用了 Prometheus Operator 做监控自动发现。如果以后要自动化管理 iot-server 的 MQTT 集群状态（如分片迁移），可能会考虑写一个简单的 Operator。"

### 21. CI/CD 流水线深度拆解 🔥

#### 21.1 一条工业级流水线

```
代码提交 (Git Push / PR Merge)
    ↓
触发 CI
    ├─ 编译构建 (Maven/Gradle)
    ├─ 单元测试 (JUnit)
    ├─ 代码质量扫描 (SonarQube：圈复杂度、重复率、漏洞)
    ├─ 依赖安全扫描 (SCA：OWASP Dependency-Check / Snyk)
    ├─ 镜像构建 (Docker / Jib / Kaniko)
    ├─ 镜像安全扫描 (Trivy：OS CVE + 语言包漏洞)
    └─ 推送到镜像仓库 (Harbor)
    ↓
CD（持续交付）
    ├─ 部署到测试环境 (Helm upgrade --install)
    ├─ 自动化集成测试 (API 测试 / 契约测试)

    └─ 灰度发布 (Canary)
    ↓

    ├─ 错误率、RT、QPS 正常？
    ├─ 是 → 全量发布
    └─ 否 → 自动回滚 (helm rollback)
```

#### 21.2 GitOps：声明式 CD 的现代范式

**核心思想**：Git 仓库是唯一事实源（Single Source of Truth）。

```
CI 构建镜像 → 更新 Git 仓库中的镜像 tag（如 Argo CD Application 的 values.yaml）
    ↓
Argo CD / Flux 检测到 Git 变更
    ↓
自动 apply 到 K8s 集群
    ↓
Argo CD 持续监控集群状态 == Git 声明？
    ├─ 是 → 一致
    └─ 否 → 自动纠偏（有人 kubectl 改了集群会被拉回 Git 状态）
```

**优势**：
- 所有变更可审计（Git 历史 = 变更记录）
- 回滚 = `git revert` + Argo CD 自动同步
- 多环境一致性（dev/staging/prod 用同一个 Git 仓库的不同分支/目录）

### 22. Java 镜像构建工具对比 🔥

## 五、Service Mesh

### 24. Service Mesh 的本质与代价 🔥

#### 24.1 架构

```
App Pod（业务容器） ←→ Sidecar（Envoy） ←→ 网络
                        ↕
                     Istiod（控制面）
```

- **数据面**：Envoy Sidecar 拦截所有进出流量，执行路由、熔断、重试、mTLS、限流、遥测
- **控制面**：Istiod 下发 xDS（Listener/Route/Cluster/Endpoint）配置给 Envoy

#### 24.2 解决了什么、付出了什么

| 收益 | 代价 |
|------|------|
| 治理能力下沉（熔断、重试、超时、灰度）不侵入业务 | **延迟增加**（Sidecar 多一跳，RT + 2~5ms） |
| 跨语言统一治理（Java/Go/Python 共享同一套策略） | **资源消耗**（每个 Pod 多一个 Envoy，内存 50~150MB） |
| mTLS 自动加密（零信任网络） | **运维复杂度**（xDS 配置调试难、证书轮换） |
| 全链路遥测自动采集 | **版本兼容性**（Istio 升级可能导致流量中断） |

> **面试判断题**："你们要不要上 Service Mesh？"——**看场景**。
> - 微服务数量 > 50、多语言、强安全要求 → 值得上
> - 服务数 < 20、纯 Java、Spring Cloud 够用 → 没必要（徒增复杂度）
> - **你的场景**：IoT 平台 ≈30 服务，但核心瓶颈在长连接 + 存储，Service Mesh 的收益有限，且 Envoy 的额外内存对边缘节点可能是负担。优先把 Spring Cloud Gateway + Nacos 用好。

## 六、项目实战 · IoT 平台 K8s 生产映射 🔥🔥🔥

### 25. 现网拓扑与 textbook 对照

```
[设备 MQTT] ──1883──→ MetalLB VIP ──→ nginx:1883 (TCP Stream 透传) ──→ iot-server Pod
                                              ↓
                                    ┌─→ EventBus ──→ ES / MySQL / Redis
                                    └─→ Pulsar（级联场景）

[设备 GIIC] ──CoAP-TCP──→ 148 Nginx(Stream) ──→ 4× iot-server (物理机混部) ──→ Redis / MySQL / ES

[K8s 平台]  ≈30 服务 · Nacos · MetalLB · StatefulSet(MySQL/Redis/ES) · Deployment(iot-server)
```

### 26. 考点→现网映射表

| 考点 | 现网实践 | 面试官追问 |
|------|----------|-----------|
| **JVM 容器感知** | GIIC 节点 **128G 物理机 -Xmx32G**（非 cgroup 小容器）；OOM case **Docker -Xmx8G**（容器 OOM 137） | "为什么物理机敢设 -Xmx32G，容器不敢？" → 物理机无 cgroup limit，JVM 按 128G 算默认堆；容器有 limit，-Xmx 超 limit 必被杀 |
| **requests/limits** | 10W K8s 压测：BestEffort Pod 占内存 → **iot 与 ES 反亲和** | "为什么 BestEffort 会导致争用？" → 没设 requests，Scheduler 以为不占资源，把大量 Pod 堆到同一 Node |
| **存储** | ES data on **NFS** → write 堵 → **elasticsearch-buffer 堆本地盘** | "NFS 为什么不适合 ES？" → 文件锁 + fsync RTT + 随机写性能差 |
| **网络** | MQTT **1883 → MetalLB VIP → nginx TCP 透传**（四层） | "为什么不用 Ingress？" → Ingress 是七层 HTTP，MQTT 是 TCP 长连接，需要 Stream 模块或 MetalLB L4 |
| **探针** | 滚动重启 **readiness 过早** → 连接池未热 | "怎么解决？" → `initialDelaySeconds` + 自定义 readiness 检查连接池可用 |
| **发布** | 单集群多服务；GIIC 协议包 **L1 改完需重打协议包上传** | "协议包怎么热更新？" → 目前不支持，需要重启 Pod（设计缺陷，可谈改进思路） |
| **调度** | ES / iot-server **反亲和** | "Anti-Affinity 的 topologyKey 选什么？" → `kubernetes.io/hostname`（不同 Node）或自定义拓扑（不同机架） |

### 27. 口播 30 秒（面试用）

> 我日常对接 **单例 K8s 约 30 服务**，设备 MQTT 走 **MetalLB L2 VIP + nginx Stream 透传** 到 **内嵌 MqttServer**。GIIC 15W 压测是 **4×128G 物理机混部 + 148 Nginx 入口**，和 textbook 的「纯 Pod 弹性」不同，是 **长连接 + JVM 大堆 + 混部 MySQL** 的容量题；10W K8s 压测则踩过 **ES on NFS 写慢 + BestEffort Pod 内存争用** 的坑，后来加了 **Pod 反亲和 + elasticsearch-buffer 本地盘缓冲**。容器化不是简单打镜像，**JVM 堆外内存、CPU limit 对 GC 并行度的影响、长连接优雅停机**，都是 IoT 场景特有的深度问题。

## 七、高频追问与连环追问 🔥🔥🔥

### 追问链 1：容器底层

**Q**: 容器和 VM 区别？
→ **A**: 共享内核 vs 独立内核；Namespace+Cgroups vs Hypervisor。
→ **追问 1**: Namespace 能隔离什么、不能隔离什么？
  → **A**: 隔离视图（PID/Network/Mount），不隔离系统调用路径、内核模块、时间（除非单独设）。
→ **追问 2**: Cgroups v1 内存统计包含哪些？为什么容器 OOM 了但 JVM 没报 OOM？
  → **A**: v1 的 `memory.usage_in_bytes` = RSS + Cache + kmem；JVM 只感知堆（-Xmx），容器 limit 杀的是 RSS 超 limit（Exit 137），不是 JVM OutOfMemoryError。
→ **追问 3**: 你们怎么解决的？
  → **A**: `-XX:MaxRAMPercentage=75` + limit 留 25% 非堆 + 压测实测 RSS。

### 追问链 2：K8s 调度

**Q**: K8s 怎么保证副本数？
→ **A**: Deployment → ReplicaSet Controller 持续 reconcile，实际 < 期望则创建 Pod。
→ **追问 1**: 如果 Node 挂了，上面的 Pod 怎么办？
  → **A**: Node Controller 检测心跳超时（默认 40s），标记 Node 为 NotReady，驱逐 Pod（Taint `node.kubernetes.io/not-ready:NoExecute`），Pod 被重新调度。
→ **追问 2**: 重新调度时怎么保证不堆到同一个 Node？
  → **A**: Pod Anti-Affinity（`topologyKey: kubernetes.io/hostname`）+ 资源 requests 让 Scheduler 算清楚 Node 剩余容量。
→ **追问 3**: 如果集群没有足够 Node 呢？
  → **A**: Pod 状态 Pending，配合 Cluster Autoscaler（云环境）自动加 Node；裸金属集群只能人工扩容或提前预留 Buffer Node。

### 追问链 3：网络

**Q**: K8s Service 是怎么实现负载均衡的？
→ **A**: kube-proxy 维护 iptables/IPVS 规则，把 ClusterIP 的流量 DNAT 到后端 Pod IP。
→ **追问 1**: iptables 和 IPVS 什么区别？
  → **A**: iptables 规则数 O(n²)（每个 Service × 每个后端一条规则），IPVS 用内核 hash 表 O(n)，大规模下 IPVS 性能更好。
→ **追问 2**: 你们 MetalLB 用的什么模式？
  → **A**: L2（ARP）模式，简单但单点瓶颈；BGP 模式更优但需路由器配合。
→ **追问 3**: MQTT 长连接怎么做优雅停机？
  → **A**: `preStop: sleep 15` + `terminationGracePeriodSeconds: 60`，等客户端感知连接断开并重连到其他 Pod，避免重连风暴。

### 追问链 4：发布

**Q**: 你们怎么做灰度发布？
→ **A**: HTTP 服务用 Ingress 权重金丝雀；MQTT 长连接用**新开 Service 做连接级灰度**（新设备连新版本）。
→ **追问 1**: 如果新版本有 Bug，怎么快速回滚？
  → **A**: `kubectl rollout undo deployment/xxx` 或 Helm `helm rollback release-name 2`（Deployment 保留历史 ReplicaSet）。
→ **追问 2**: 回滚时正在处理的请求会丢吗？
  → **A**: 配合优雅停机（`preStop` + `SIGTERM` 处理存量）不会丢；但如果应用没正确处理 SIGTERM，或 grace period 太短，会强制 SIGKILL 丢请求。

### 追问链 5：Java 容器化

**Q**: Java 应用上容器要注意什么？
→ **A**: JVM 容器感知（`UseContainerSupport` + `MaxRAMPercentage`）、CPU limit 对 GC/线程池的影响、堆外内存限制、优雅停机。
→ **追问 1**: 为什么 `-Xmx` 和容器 limit 不能设一样？
  → **A**: 容器内存 = 堆 + 元空间 + 线程栈 + 直接内存 + 页缓存 + JVM 自身。`-Xmx=limit` → RSS 必超 limit → OOM Kill。
→ **追问 2**: CPU limit=1 核会有什么后果？
  → **A**: `availableProcessors()=1` → G1 GC 单线程、JIT 单线程、`ForkJoinPool` 并行度=0 → GC STW 增加 → RT 飙升，即使 CPU 使用率不到 50%。
→ **追问 3**: 你们压测时怎么发现这个问题的？
  → **A**: P99 高但 CPU 不高 → jstack 看 GC 线程只有 1 个 → 取消 CPU limit 或提高 limit → P99 下降 60%。

## 八、速查命令卡（面试前 10 分钟看）

```bash
# 容器资源
kubectl top pod -n <ns>                    # Pod CPU/内存实时
kubectl describe pod <pod> | grep -A5 "Requests\|Limits"
cat /sys/fs/cgroup/memory/memory.usage_in_bytes   # 容器内看内存 RSS

# 调度
kubectl get nodes -o yaml | grep allocatable    # Node 可分配资源
kubectl get pod <pod> -o yaml | grep -A10 affinity  # 看亲和配置

# 网络
kubectl get svc -n <ns> -o wide             # Service ClusterIP + 后端 Pod
iptables -t nat -L KUBE-SERVICES -n | grep <cluster-ip>   # 看 iptables 规则
ipvsadm -Ln | grep <cluster-ip>             # 看 IPVS 规则

# 发布
kubectl rollout history deployment/<name>   # 查看历史版本
kubectl rollout undo deployment/<name>      # 回滚到上一版
helm history <release>                      # Helm 发布历史
helm rollback <release> <revision>          # Helm 回滚

# 排障
kubectl get events -n <ns> --sort-by='.lastTimestamp'   # 按时间排序事件
kubectl logs <pod> --previous               # 看上一个容器实例的日志（CrashLoopBackOff 用）
kubectl debug -it <pod> --image=busybox --target=<container>   # 1.18+ 临时调试容器
```
