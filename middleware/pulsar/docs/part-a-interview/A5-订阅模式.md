# A5 四种订阅模式

> 优先级: **P1 面试** | 预计阅读 30 分钟 | 深度：批次 1

## 本章解决什么问题

Pulsar **同一 Topic 可被多种消费方式同时存在**（多个 Subscription），每种 Subscription 选一种 **订阅模式**，决定消息如何分给多个 Consumer 实例。选错模式 = 乱序、扩缩容无效或主备不切换。

---

## 面试常问

1. 四种订阅模式区别与适用场景？
2. Key_Shared 和 Kafka Consumer Group 有何不同？
3. Failover 能保证全局有序吗？
4. Shared 为什么吞吐高但无序？
5. 你们项目用 Shared + 非分区，会有什么问题？

---

## 核心知识

### 对比总表（必背）

| 模式 | 同时 Active 的 Consumer | 分区内顺序 | Key 内顺序 | 吞吐 | 典型场景 |
|------|-------------------------|------------|------------|------|----------|
| **Exclusive** | 1 | ✅ | ✅（单分区时） | 低 | 单实例任务、强顺序 |
| **Failover** | 1（其余 standby） | ✅ | ✅ | 低 | 主备容灾 |
| **Shared** | 全部 | ❌ | ❌ | **最高** | 日志分析、无顺序要求 |
| **Key_Shared** | 全部 | ❌ 跨 Key | ✅ 同 Key | 高 | 订单/设备 ID 有序 |

**注意：** 「分区内有序」仅对 **分区 Topic** 有意义；**非分区 Topic** 只有一个逻辑流，但仍可能被 Shared 打乱处理顺序（多 Consumer 时）。

### Exclusive

- 一个 Subscription **只允许一个** Consumer 连接；第二个会失败。
- 消息按存储顺序投递给该 Consumer。
- **不要用** 多实例部署同一 `subscriptionName`，除非你想故意报错。

### Failover

- 多个 Consumer 同订阅，**只有一个 active**，其余 standby。
- Active 崩溃后，standby 接管，**切换期间短暂不可用**（默认检测约数十秒级，可配）。
- 适合「逻辑单线程消费 + 高可用」，不适合要并行提速。

### Shared

- 所有 Consumer **同时活跃**，消息 **轮询/随机** 分发，**不保证顺序**。
- 扩展 Consumer 即可提高并行度（无 Key 约束时）。
- **反模式：** 业务要求「同一 orderId 顺序处理」却用 Shared。

### Key_Shared

- 相同 **Message Key** 的消息路由到 **同一 Consumer**（在 rebalance 时可能变化）。
- 策略：
  - **AUTO_SPLIT**：自动分配 Key 范围；
  - **STICKY**：尽量减少 Key 迁移，降低 rebalance 乱序窗口。
- Consumer 数量 **不是越多越好**：超过有效分区/Key 分布时部分实例空闲。
- 与 Kafka：Kafka 是 Partition 绑定 Consumer；Pulsar 是 **Key 绑定 Consumer**，Partition 仍决定写在哪，读侧 Key_Shared 再二次分配。

### 选型决策树

```
需要严格全局有序（跨 Key）？
  └─ 是 → 非分区 Topic + Exclusive/Failover（单 Consumer）
  └─ 否 → 需要同一业务 ID 有序？
        └─ 是 → Key_Shared + Producer 设 Key
        └─ 否 → 要最高吞吐 → Shared
```

## 面试标准答案

### 题：四种订阅模式分别适用什么场景？

> Exclusive 适合只能有一个消费者实例的场景，比如全局单线程任务。Failover 适合要顺序又要高可用，主挂掉备顶上，但同一时刻只有一个在消费。Shared 适合不关心顺序、要尽量提高并行度的场景，比如日志清洗，所有实例一起抢消息。Key_Shared 适合既要并行又要按 Key 有序的场景，比如同一订单 ID 或设备 ID 的消息必须由同一个消费者顺序处理，这是物联网和订单系统里最常见的模式。选型错误最常见的误区是用 Shared 处理要按 Key 有序的业务，会导致乱序和状态错误。

### 题：Failover 能保证顺序吗？

> Failover 保证的是**同一个 active Consumer 消费时**，分区内按顺序处理。如果有多个分区，分区之间仍然无序。而且主备切换过程中会有短暂停顿，切换窗口内可能重复投递，需要幂等。Standalone 只有一个 Broker 时无法验证真正的 Failover 切换。

## 生产环境注意点

- `subscriptionName` 全环境、全服务统一命名，写入配置中心。
- Key_Shared 扩缩容 Consumer 会 **rebalance**，短暂乱序需业务容忍或 STICKY。
- 监控每个 Subscription 的 **backlog**，不同订阅互不影响。

---

## 易错点

1. **Shared + 设备 ID 有序需求** → 必乱序（你们现状需评估，见 [B13](../part-b-java-dev/B13-推动策略改造.md)）。
2. **Failover 开多实例却期望并行** → 只有 1 个在干活。
3. **Key_Shared 但不设 Key** → 退化为类似 Shared 随机行为。
