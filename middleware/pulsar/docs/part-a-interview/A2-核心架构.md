## 核心知识

### 1. 三层分离（Pulsar 与 Kafka 最大差异）

| 层 | 组件 | 存什么 | 扩展方式 |
|----|------|--------|----------|
| 元数据 | Metadata Store（ZK / Oxia / etcd） | Topic 定义、Bundle 归属、Cursor 位置索引等 | 元数据集群 HA |
| 计算 | **Broker** | 不持久化消息体；有读缓存、连接状态 | 加 Broker |
| 存储 | **BookKeeper（Bookie）** | Journal + Ledger，消息实体 | 加 Bookie |

Kafka 把「分区日志」放在 Broker 本地磁盘上；Pulsar 把日志放在 BookKeeper，Broker 可随时替换、扩缩容，**存储与计算解耦**。

### 2. 架构图（必须能白板画）

```
                         ┌──────────────────────────────────────┐
                         │     Metadata Store (ZK / Oxia)        │
                         │  • Topic / Namespace 配置             │
                         │  • Bundle → Broker 映射               │
                         │  • Cursor 元数据（指针、订阅信息）     │
                         └───────────────────┬──────────────────┘
                                             │ 读写元数据
    ┌──────────────┐    PUBLISH/LOOKUP     ┌▼──────────────┐
    │   Producer   │ ────────────────────► │    Broker      │
    └──────────────┘                       │  • 协议解析     │
                                           │  • 路由到 BK    │
    ┌──────────────┐    SUBSCRIBE/READ     │  • ML Cache    │
    │   Consumer   │ ◄──────────────────── │  • 无消息盘持久化 │
    └──────────────┘                       └───────┬────────┘
                                                   │ 写/读 Entry
                         ┌─────────────────────────▼─────────────────────────┐
                         │              BookKeeper Cluster                  │
                         │   Bookie1        Bookie2        Bookie3           │
                         │   Journal(SSD)   Journal        Journal           │
                         │   Ledger dirs    Ledger         Ledger            │
                         └─────────────────────────────────────────────────┘
```

**Proxy（可选）：** 独立接入层，终结海量 TCP 连接，再转发 Broker。10W 设备/连接场景常用，Broker 专注消息处理。

### 3. Broker「无状态」的准确含义

**正确理解：**

- Broker **不在本地磁盘持久化 Topic 消息内容**（消息在 BookKeeper）。
- Broker 重启后，可从 Metadata + BookKeeper **恢复服务**，已持久化消息不丢。
- Broker **有运行时状态**：连接表、Managed Ledger 读缓存、部分内存索引、Bundle 本地负载信息。

**错误理解（面试扣分）：**

- 「Broker 没有任何状态」→ 错。
- 「Broker 重启消息就没了」→ 错，消息在 BK。
- 「Consumer 直接从 Broker 内存读消息」→ 过度简化；可能是 Cache 命中，未命中则读 BK。

### 4. Managed Ledger：Topic 在存储层的化身

- 一个 **Topic-Partition** 对应一个 **Managed Ledger**（逻辑对象，运行在 Broker 进程内，数据在 BK）。
- Managed Ledger 由一系列 **Ledger**（BK 概念）组成：写满或到期则 **滚动** 开新 Ledger。
- **Cursor** 挂在订阅上，指向「逻辑消费位置」（entryId），ACK 后 **MarkDelete** 推进，之前 Entry 可被 GC（受 Retention 约束）。

与 Kafka 对比：Kafka 分区内有序日志 + offset；Pulsar 多订阅各自 Cursor，**Retention 不依赖某个消费组是否消费**。

### 5. Bundle：负载均衡单元

- 多个 Topic（按 hash）归入一个 **Bundle**。
- Bundle 整个 **unload/load** 到某台 Broker，用于扩缩容、热点迁移。
- 面试常问：Topic 很多时，Bundle 粒度避免「一 Topic 一迁移」过碎。

### 6. 写入路径（逐步，建议背诵骨架）

```
1. Producer 连接 Broker（或经 Proxy），发送消息（可 batch）
2. Broker 确定 Topic-Partition → 对应 Managed Ledger
3. Broker 将消息转为 Entry，选择 BookKeeper Ensemble（多个 Bookie）
4. 并行写 Journal（顺序写）+ 异步刷 Ledger
5. 达到 Write Quorum / Ack Quorum（E-Q-W 配置，如 3:3:2）
6. Broker 收到足够 BK 确认 → 返回 Producer ACK（send 完成）
```

**E-Q-W 示例 `3:3:2`：** 3 副本写、至少 3 路写成功、2 路确认即可向 Producer 报成功（具体以 Broker/BK 配置为准）。

### 7. 读取路径

```
1. Consumer 向 Broker 拉取（或 push 型 listener）
2. Broker 查 Managed Ledger：读缓存（堆内 ManagedLedgerCache）是否命中
3. 命中 → 内存返回；未命中 → 向 Bookie 读对应 Ledger:Entry
4. Consumer 处理完毕 ACK
5. Broker 更新该 Subscription 的 Cursor（MarkDelete）
6. 后台按 Retention/Compaction 策略清理已标记数据
```

### 8. Lookup 与 Topic 发现

- Client 首次访问 Topic 会 **lookup**：Metadata 返回 Topic 归属 Broker 地址。
- Broker 集群变更、Bundle 迁移后，Client 会收到 **重定向** 或自动重新 lookup（Pulsar Client 内置）。

## 面试标准答案

### 题：说说 Pulsar 架构？

> Pulsar 采用**计算存储分离**。Broker 负责协议、连接、路由和缓存，本身不把消息持久化在本地磁盘，因此计算层可以水平扩展。消息实际写在 BookKeeper 集群里，通过 Journal 顺序写、Ledger 只追加的方式保证持久化，并用多副本 quorum 确认。元数据如 Topic、Bundle 映射、订阅 Cursor 等存在 ZooKeeper 或新一代 Oxia 里。Producer 写消息时 Broker 并行写多个 Bookie，达到 ack quorum 后 ACK 给客户端；Consumer 读时优先走 Broker 的 Managed Ledger 缓存，未命中再读 Bookie，消费后更新 Cursor。这种架构适合多租户、跨机房复制和海量 Topic 场景，和 Kafka 把日志绑在 Broker 上的模型不同。

## 生产环境注意点

| 点 | 说明 |
|----|------|
| Bookie Journal 磁盘 | 必须 SSD，否则写入 P99 飙升 |
| Broker 堆内存 | ManagedLedgerCache 过大易 OOM |
| Bundle 热点 | 某 Broker 负载过高需手动 unload 均衡 |
| 元数据集群 | ZK 故障影响 lookup，需监控 |

---

## 易错点与反例

1. **把 Broker 无状态理解成「可随时杀无影响」** → 杀 Broker 会断连接，正在飞的 batch 可能失败，需 Client 重试。
2. **忽略 Proxy** → 上万连接打 Broker 易连接耗尽，应用 Proxy 接入。
3. **Topic 数 = 分区数混谈** → 海量 Topic 是 Managed Ledger 元数据压力，不是分区概念。
