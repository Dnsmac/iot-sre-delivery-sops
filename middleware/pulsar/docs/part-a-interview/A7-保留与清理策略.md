# A7 保留与清理策略

> 优先级: **P1 面试** | 预计阅读 30 分钟 | 深度：批次 3 ✓

## 本章解决什么问题

消息「为什么会消失」「为什么还能回溯」「积压满了会怎样」——由 **TTL、Retention、Compaction、Backlog Quota** 四套机制回答，彼此独立，面试极易混为一谈。

---

## 一、四种机制总览

```
消息写入 Topic
    │
    ├─ TTL ──────────────► 到时间未消费也可删
    ├─ Retention ────────► 保留多久/多大（与 ACK 无关）
    ├─ Compaction ───────► 同 Key 只留最新
    └─ Backlog Quota ────► 消费太慢时处置积压
```

| 策略 | 配置层级 | 主要回答的问题 |
|------|----------|----------------|
| **TTL** | Namespace / Topic | 消息能活多久（从发布时间算） |
| **Retention** | Namespace | 集群里留多久/多大历史（含已 ACK） |
| **Compaction** | Namespace / Topic | 同 Key 是否只保留最新值 |
| **Backlog Quota** | Namespace | 慢消费者积压超限怎么办 |

---

## 二、TTL（Time To Live）

### 原理

- 消息从**发布时刻**起计时，超过 TTL 可被删除，**不管有没有 Consumer、有没有 ACK**。
- 用于防止「没人消费的消息」占满磁盘。

### 配置示例

```bash
pulsar-admin namespaces set-message-ttl persistent://company/production \
  --messageTTL 86400   # 秒，如 1 天
```

### 生产注意

| 场景 | 建议 |
|------|------|
| 开发环境 | TTL 设短，自动清理测试数据 |
| 核心业务 | 谨慎设 TTL，避免未消费数据被删 |
| 与 Retention 同时存在 | **更短的那个先起作用**（理解：多重过期条件） |

### 面试一句话

> TTL 管的是单条消息的寿命，到点就过期，不保证你能回溯很久以前的未消费消息。

---

## 三、Retention（保留策略）

### 原理

- 控制 Topic 上数据在 BookKeeper 中**保留多久或多大**，与 Consumer 是否 ACK **无关**。
- 即使所有 Subscription 都 ACK 了，消息仍可保留，供**新 Subscription 从 earliest 订阅**或 **Reader 按 MessageId 读**。

### 配置示例

```bash
pulsar-admin namespaces set-retention persistent://company/production \
  --size 10G \
  --time 7d
```

| 参数 | 含义 |
|------|------|
| time | 保留时间，如 7d、0 表示不按时间限 |
| size | 保留大小上限 |

### 典型用途

| 用途 | 说明 |
|------|------|
| 审计回溯 | 保留 30 天所有事件 |
| 新服务补数据 | 新 Subscription 从 earliest 消费历史 |
| 与 Kafka 对比 | 类似 log.retention，但 Pulsar 不绑定某个 CG |

### 面试陷阱

- **Retention 删的是存储上的旧 Entry**，不是「取消消费权限」。
- Retention 太短 → 无法 seek 到旧 MessageId。

---

## 四、Compaction（键值压缩）

### 原理

- 对同一 **Message Key**，只保留**最新一条**（逻辑上），适合「当前状态」类数据。
- **不是** Retention 的替代品；Compaction 在 Retention 允许的范围内折叠 Key。

### 与 Retention 区别（必背）

| | Retention | Compaction |
|---|-----------|------------|
| 维度 | 时间/大小 | Key |
| 结果 | 整段历史按时间删 | 同 Key 旧值被新值替代 |
| 典型 Topic | 订单事件流 | 设备最新配置、账户余额快照 |

### 触发

```bash
pulsar-admin topics compact persistent://company/config/device-state
```

Namespace 可设 `compactionThreshold` 等自动策略。

### 注意

- 无 Key 的消息对 Compaction 无意义。
- Compaction 是**后台任务**，有延迟。

---

## 五、Backlog Quota（积压配额）

### 原理

- 当某 **Subscription** 的 backlog（未消费积压）超过阈值，触发策略，防止慢消费者拖垮集群。

### 策略类型（常见）

| 策略 | 行为 |
|------|------|
| producer_request_hold | 阻塞生产者（背压） |
| producer_exception | 生产者抛错 |
| consumer_backlog_eviction | 丢弃旧消息（危险，需审批） |

### 配置示例

```bash
pulsar-admin namespaces set-backlog-quota persistent://company/production \
  --limit 1G \
  --policy producer_request_hold \
  --type destination_storage
```

### 排查

```bash
pulsar-admin topics stats persistent://company/production/events
# subscriptions.<name>.backlogSize
# subscriptions.<name>.msgBacklog
```

见 [P4 Backlog](../part-d-problems/P4-积压.md)。

## 六、组合场景（面试加分）

| 场景 | 配置思路 |
|------|----------|
| 订单事件，保留 7 天审计 | Retention 7d，无 Compaction |
| 设备最新配置 | Compaction + 较长 Retention |
| 日志流，可丢旧数据 | 短 Retention + 无 Compaction |
| 防止磁盘被打满 | Backlog Quota + 监控告警 |
| 测试环境 | 短 TTL + 短 Retention |

---

## 七、面试标准答案

### 题：TTL 和 Retention 区别？

> TTL 是从消息发布时间算起，到了就过期，即使没人消费也会删，主要防止无人消费的消息堆积。Retention 是 Topic 级别的保留策略，控制数据在 BookKeeper 里留多久或多大，和是否已经 ACK 无关，已消费的消息也可以继续保留用于回溯或新订阅。生产上两者可以同时配置，要一起评估磁盘和业务要回溯多久。

### 题：Compaction 是什么？和 Retention 区别？

> Compaction 是对相同 Message Key 只保留最新一条，适合配置类、状态类 Topic。Retention 是按时间或大小删除历史数据。Compaction 不会替代 Retention，而是在 Retention 窗口内把同 Key 的多条合并成最新。订单流水用 Retention，设备最新状态用 Compaction。

---

## 八、易错点

1. 以为 **ACK 后消息立刻物理删除** → 通常还要等 Retention/MarkDelete GC。
2. 对核心业务设了 **短 TTL** → 未消费数据丢失。
3. **Backlog 涨** 只加 Consumer 不查 **下游慢 / 分区不够**。
4. 开启 **consumer_backlog_eviction** 不知会丢数据。
