# A3 多租户层级

> 优先级: **P1 面试** | 预计阅读 30 分钟 | 深度：批次 4 ✓

## 本章解决什么问题

弄清 Pulsar **三层命名空间**各自职责、如何做多团队隔离、策略在哪一层配置，以及面试里「物理隔离」该怎么准确表述。

---

## 面试常问

1. Topic 完整路径是什么？persistent 和 non-persistent 区别？
2. Tenant、Namespace、Topic 分别管什么？
3. 多租户如何实现隔离？是否物理隔离 Broker？
4. Namespace 上可以配哪些策略？
5. 和 Kafka 的 Topic 命名有什么本质不同？

## 一、三层模型

```
persistent://{tenant}/{namespace}/{topic}
     │              │          │         └── 消息通道（业务事件）
     │              │          └── 策略单元（TTL、Retention、Quota、Schema）
     │              └── 组织/环境（公司、业务线、dev/prod）
     └── 持久化（non-persistent:// 重启丢数据，生产慎用）
```

| 层级 | 作用 | 类比 |
|------|------|------|
| **Tenant** | 顶层租户，配额与集群绑定、管理员角色 | 云账号 / 事业部 |
| **Namespace** | 一组 Topic 共享策略与权限 | 数据库 schema |
| **Topic** | 实际收发消息的队列/流 | 表名（但更动态） |

**与 Kafka：** Kafka 多为 `cluster + topic`；Pulsar 强制 **tenant/namespace** 前缀，天然适合多团队共用集群。

---

## 二、Namespace 级策略（面试高频）

在 Namespace 上统一配置，下属 Topic **默认继承**（Topic 级可覆盖部分项）：

| 策略 | 作用 |
|------|------|
| Retention / TTL | 保留多久、消息寿命 |
| Backlog Quota | 积压超限时的背压或驱逐 |
| Schema Compatibility | BACKWARD / FULL 等 |
| Replication Clusters | Geo 复制目标集群 |
| Persistence | ensemble / write / ack quorum |
| Bundles | 负载均衡与隔离单元 |

```bash
pulsar-admin namespaces policies persistent://company/order
pulsar-admin namespaces set-retention persistent://company/order --time 7d --size 10G
```

## 三、隔离方式（准确表述）

### 3.1 逻辑隔离（默认就有）

- **ACL / RBAC**：按 tenant/namespace 授权 produce/consume/admin。
- **配额**：消息速率、带宽、存储上限。
- **独立 Subscription**：同 Topic 多服务互不影响（见 [B4](../part-b-java-dev/B4-多服务协作.md)）。

### 3.2 资源隔离（Isolation Policy）

- 将某 Namespace 的 **Bundle** 绑定到指定 **Broker 集合** 或 **Bookie 机架**。
- 是 **机架/资源池级** 隔离，**不保证**「一台物理机只跑一个租户」。
- 用于：大客户独占 Bookie、合规要求磁盘域分离。

**易错点（必背）：** 不能说「Namespace 物理隔离 Broker 和 Bookie」——准确说法是 **通过 Isolation Policy 将 Bundle 调度到指定资源集合**。

### 3.3 环境隔离（实践）

| 做法 | 推荐度 |
|------|--------|
| 不同 Tenant：`company-dev` / `company-prod` | 高 |
| 同 Tenant 不同 Namespace | 中 |
| 仅 Topic 后缀 `_test` | 低 |

## 四、Bundle 与负载均衡（了解）

- Topic 按 **hash 落在 Bundle** 上，Bundle 由某 Broker 负责。
- Broker 过载时 **unload/load** Bundle 迁移。
- 运维：`pulsar-admin namespaces unload`、`broker-stats`。

---

## 五、生产环境注意点

- 禁用 `public/default` + Auto-Create 作为生产默认。
- 预创建 Tenant/Namespace，IaC 或脚本（本仓库 `setup-dev-tenant.ps1`）。
- 策略在 Namespace 定好，避免每个 Topic 各配一套。
- 跨环境 **subscriptionName 一致**，Topic 全名用配置注入。

---

## 六、易错点

1. 把 Namespace 说成「数据库实例级物理隔离」。
2. 测试 Producer 连到 prod tenant（配置未隔离）。
3. 所有业务共用一个 namespace，无法按域调 Retention/Quota。
4. 使用 `non-persistent://` 做核心业务。

---

## 七、动手验证

```powershell
.\scripts\setup-dev-tenant.ps1
docker exec pulsar-standalone bin/pulsar-admin tenants list
docker exec pulsar-standalone bin/pulsar-admin namespaces list dev
docker exec pulsar-standalone bin/pulsar-admin namespaces policies persistent://dev/test
```

---

## 面试标准答案

> Topic 全名是 persistent://tenant/namespace/topic。Tenant 是顶层租户，Namespace 是策略和权限的边界，Topic 是消息通道。多租户通过 ACL、配额、以及可选的 Isolation Policy 把 Bundle 绑到指定 Broker/Bookie 资源集实现隔离，这是资源池级隔离而不是简单的单机物理隔离。生产上我们用独立 tenant 区分环境，在 namespace 上统一配置 retention 和 schema 策略。
