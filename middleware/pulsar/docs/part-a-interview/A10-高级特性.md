# A10 高级特性（面试加分）

> 优先级: **P1 加分 / P3 扩展** | 预计阅读 30 分钟 | 深度：批次 4 ✓

## 本章解决什么问题

面试「还了解什么」时的加分项：事务、延迟消息、去重、Geo、分层存储、Functions、KoP——各解决什么问题、**代价与限制**是什么。

---

## 一、特性总览

| 特性 | 解决什么 | 核心机制 | 限制/代价 |
|------|----------|----------|-----------|
| **Transaction** | 跨 Topic 原子发/收 | Transaction Log + 两阶段 ACK | 吞吐下降，运维复杂 |
| **Delayed Message** | 定时/延迟投递 | `deliverAt` / `deliverAfter` | Broker 调度精度、堆积 |
| **Deduplication** | Broker 端去重 | Producer `sequenceId` + 去重窗口 | 需开启；非业务全场景 |
| **Geo-Replication** | 跨机房容灾/多活 | 异步复制 Topic | 最终一致、冲突 |
| **Tiered Storage** | 降存储成本 | 热 BK + 冷 S3/GCS | 冷读延迟高 |
| **Pulsar Functions** | 轻量流处理 | 单消息 map/filter | 非复杂窗口状态 |
| **KoP** | Kafka 协议迁移 | Kafka API → Pulsar 存储 | 特性子集需验证 |

---

## 二、Transaction（了解即可）

- 将多条消息的 produce/consume/ack **绑定为一个事务**，commit 后可见。
- 适用：转账、库存扣减与事件**强一致**（仍建议业务幂等作兜底）。
- 面试：**性能开销大，大多数互联网业务用幂等 + 至少一次即可**。

---

## 三、Delayed Message

```java
producer.newMessage()
    .value(payload)
    .deliverAfter(10, TimeUnit.MINUTES)
    .send();
```

- 用于：订单超时取消、重试退避、定时通知。
- 注意：大量延迟消息会增加 Broker 调度负担；极高精度用专门调度系统可能更合适。

---

## 四、Deduplication

- Broker 在配置的 dedup 窗口内，对相同 Producer 的 **sequenceId** 去重。
- **不能替代** Consumer 幂等（Consumer 重投、多 Producer 仍可能重复）。
- 开启：`pulsar-admin namespaces set-deduplication`。

---

## 五、Geo-Replication

```
Cluster A (北京)  ──异步复制──►  Cluster B (上海)
         │                              │
    Producer/Consumer              只读或双写
```

- **最终一致**，有复制延迟。
- 冲突：同 Topic 双写需业务层解决（版本号、LWW）。
- 运维：[C7](../part-c-ops/C7-跨机房复制.md)。

**面试句：** Geo 是异步复制，适合灾备和就近读，不是强一致双活除非业务接受冲突处理。

---

## 六、Tiered Storage

- 热数据在 BookKeeper；旧 Ledger **Offload** 到对象存储。
- 降成本；**冷读延迟**上升，需压测。
- 运维：[C8](../part-c-ops/C8-分层存储.md)、[P11](../part-d-problems/P11-Bookie磁盘满.md)。

---

## 七、Pulsar Functions & KoP

| | Functions | KoP |
|---|-----------|-----|
| 用途 | Topic 上轻量 ETL、路由 | Kafka 客户端连 Pulsar |
| 限制 | 非 Flink 级窗口 | 部分 Kafka 特性需对照文档 |

迁移路径：Kafka → KoP → 逐步改用 Pulsar 原生 API。

---

## 八、面试组合答法示例

**题：如何保证跨机房数据可用？**

> 用 Geo-Replication 做异步复制，接受最终一致和复制延迟。核心业务在应用层做幂等和版本号。冷数据用 Tiered Storage  offload 到 S3 省 Bookie 磁盘。强一致跨 Topic 才考虑 Transaction，但要评估性能。

---

## 九、易错点

1. 以为 Deduplication = 精确一次端到端。
2. Geo 双写无冲突策略。
3. Tiered Storage 上线不压测冷读 SLA。
4. 所有延迟任务都塞 Pulsar Delay（百万级定时任务不适合）。
