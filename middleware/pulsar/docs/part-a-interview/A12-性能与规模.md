## 一、瓶颈分层

```
┌─────────────────────────────────────────┐
│ 应用：同步 send、无 batch、大对象 GC      │
├─────────────────────────────────────────┤
│ Broker：CPU、ManagedLedger Cache、连接数  │
├─────────────────────────────────────────┤
│ BookKeeper：Journal 磁盘 IO、网络         │
├─────────────────────────────────────────┤
│ Consumer：处理慢、receiverQueue 过小      │
└─────────────────────────────────────────┘
```

| 路径 | 典型瓶颈 |
|------|----------|
| **写入** | Bookie Journal 顺序写带宽、E-Q-W 确认数 |
| **读取** | Broker 缓存命中、Bookie 随机读、Consumer 慢 |
| **元数据** | 海量 Topic / 分区 → ZK/Oxia 压力 |

---

## 二、提吞吐（按影响排序）

1. **架构**：分区数、Key_Shared、消息大小设计
2. **Producer**：Batching + LZ4/ZSTD
3. **Consumer**：并行实例、`receiverQueueSize`
4. **集群**：加 Bookie（写）、加 Broker（接入/读）
5. **客户端 JVM**：GC、对象分配（最后才抠）

详见 [B10](../part-b-java-dev/B10-性能调优.md)、[P5](../part-d-problems/P5-性能不足.md)。

---

## 三、延迟 vs 吞吐权衡

| 手段 | 吞吐 | 延迟 |
|------|------|------|
| 开 Batching | ↑ | P99 ↑ |
| 开压缩 | ↑（大消息） | CPU 换带宽 |
| sync send | ↓ | 更可预测 |
| 减小 batch delay | ↓ | P99 ↓ |

---

## 四、规模问题与方案

| 问题 | 现象 | 方案 |
|------|------|------|
| **海量 Topic** | 元数据膨胀、加载慢 | 合并 Topic + Message Key 区分业务 |
| **海量连接** | Broker 连接数打满 | **Pulsar Proxy** 聚合 |
| **海量订阅** | Cursor 多 | 合并消费逻辑、减少无用 Subscription |
| **单 Topic 热点** | 单分区/单 Key 打满 | 拆分 Key、增加分区 |
| **磁盘** | Bookie 满 | Retention、Tiered Storage、扩盘 |

## 五、10 万设备场景（面试标准设计）

**错误：** 10 万个 Topic 或 10 万个分区（元数据/调度爆炸）。

**推荐：**

```
persistent://tenant/iot/device-telemetry
  分区数: 64~256（按吞吐算，非按设备数）
  Producer: key = deviceId
  Consumer: Key_Shared, N 实例
```

**粗算分区：**

```
10W 设备 × 1 msg/10s × 512B ≈ 5 MB/s   → 少数分区即可
10W 设备 × 1 msg/s   × 512B ≈ 50 MB/s → 约 8~16 分区起（需压测验证）
```

压测阶梯：1K → 10K → 50K → 100K；**必须 Cluster**，见 [C11](../part-c-ops/C11-十万设备压测.md)、[B12](../part-b-java-dev/B12-环境模型.md)。

---

## 六、与你们现状

- **Shared + 非分区**：扩展读有限，10W 设备**乱序**风险高。
- 改造路径：[B13](../part-b-java-dev/B13-推动策略改造.md)。

---

## 七、易错点

1. Standalone 压测数字当生产容量。
2. 分区数 = 设备数。
3. 只加 Consumer 不加分区（分区 Topic 下）。
4. 忽视 Bookie 磁盘 IO 只调 JVM。

---

## 面试标准答案

> 写入瓶颈多在 BookKeeper Journal 磁盘和副本确认。提吞吐靠 batching、压缩、增加分区与 Bookie。海量设备不要海量 Topic，用少量分区 Topic 加 deviceId 作 Key 和 Key_Shared 消费。十万设备要按消息速率算分区并在集群上阶梯压测，Standalone 只能看趋势。
