# P3 消息乱序

> 链接: [A5 订阅](../part-a-interview/A5-订阅模式.md) | [B2](../part-b-java-dev/B2-生产者.md) | [B3](../part-b-java-dev/B3-消费者.md) | [B13](../part-b-java-dev/B13-推动策略改造.md)

---

## 典型现象

- 同一设备/用户：「上线」事件早于「注册」被处理。
- 订单状态从「已支付」回退到「待支付」的展示。
- 多实例 Consumer 日志里**同一 Key 交错**出现。
- 压测时乱序率上升，单实例时正常。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **SubscriptionType.Shared** | 多 Consumer 轮询，**全局无序**（你们当前架构） |
| 2 | **非分区 Topic + 多 Producer** | 无分区边界，仅 Key_Shared 能救 Key 内有序 |
| 3 | **未设置 Message Key** | Key_Shared 退化为近似随机分配 |
| 4 | **异步发送多线程** | 完成顺序与发送顺序不一致 |
| 5 | **Producer RoundRobin + 无 Key** | 分区 Topic 上消息进不同分区 |
| 6 | **Consumer 内线程池乱序** | receive 有序，提交到线程池后完成乱序 |
| 7 | **重投递 / NACK** | 旧消息晚于新消息被处理 |
| 8 | **Geo 复制多活写入** | 跨机房时钟与复制延迟 |

## 排查步骤

### 1. 确认订阅类型与 Topic 类型

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics stats persistent://dev/test/events
# subscriptions.*.type → Shared / Key_Shared
```

```java
// 代码审查
.subscriptionType(SubscriptionType.???)
```

### 2. 检查 Producer Key

```java
producer.newMessage().key(deviceId).value(...).send();
// 日志：key 是否 null、是否每设备稳定
```

### 3. 单 Consumer 复现

- 只启 **1 个** Consumer：仍乱序 → Producer/Key/分区问题。
- 单 Consumer 有序、多 Consumer 乱序 → **几乎确定是 Shared**。

### 4. 查异步与线程池

- 是否 `sendAsync` 无 Key 且多线程
- Listener 是否 `executor.submit` 后乱序 ACK

### 5. 看重投递

- `redeliveryCount > 0` 的旧消息是否插队

## 解决方案

| 目标 | 方案 |
|------|------|
| 全局有序 | 单分区 Topic + Exclusive 或单 Consumer |
| 按设备/订单有序 | **分区 Topic + Key + Key_Shared** |
| 提高并行 | 分区数 ≈ Consumer 数，Key 均匀 |
| 发送侧 | 同 Key 单线程发送或 sync send |
| 消费侧 | Key_Shared；处理逻辑单线程 per Key 或按 Key 排队 |
| 改造路径 | [B13](../part-b-java-dev/B13-推动策略改造.md)、[附录 K′ 迁移速查](../appendices/K-Shared改KeyShared速查.md) |

**你们现状：** Shared + 非分区 + Auto-Create → 乱序**符合预期**；要修必须改架构，不是调参数能彻底解决。

---

## 验证脚本思路

1. 同一 `device-001` 连发 100 条带序号消息。
2. 3 个 Shared Consumer 消费，统计序号逆序次数。
3. 改为 Key_Shared + Key，逆序应接近 0（允许重投递边缘情况）。

---

## 面试一句话

> 乱序首选查订阅模式：Shared 不保证顺序。要 Key 内有序用 Key_Shared 加 Producer Key，要高并行用分区 Topic；非分区加 Shared 只适合不要求顺序的日志类场景。
