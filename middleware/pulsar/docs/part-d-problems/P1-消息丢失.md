---

## 典型现象

- 业务日志显示 Producer **已发送**，下游系统**无记录**。
- 监控上 `msgInCounter` 增加，某 Subscription 的 `msgOutCounter` **长期不增**。
- 用户反馈「偶发丢单」，难以复现。
- 与「重复消费」混淆：实际是**从未被正确处理**或**被策略删除**。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **异步发送未处理失败** | `sendAsync` 失败只打日志未重试，业务以为成功 |
| 2 | **发到 non-persistent Topic** | Broker 重启后消息不可恢复 |
| 3 | **TTL / Retention 过期** | 慢消费或未消费数据被删，见 [A7](../part-a-interview/A7-保留与清理策略.md) |
| 4 | **订阅名/Subscription 错误** | 消息在别的 Subscription，当前服务「看不到」 |
| 5 | **Consumer 处理失败未 NACK 且未 ACK** | 进程崩溃前未 ACK → 应重投；若误以为丢失，查是否被 skip |
| 6 | **Backlog 驱逐策略** | `consumer_backlog_eviction` 主动丢旧消息 |
| 7 | **Auto-Create 到错误 Namespace** | 环境不一致，写到测试 Tenant |
| 8 | **事务未 commit**（若使用） | 半提交消息不可见 |

## 排查步骤

### 1. 确认消息是否进入 Broker

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics stats-internal persistent://dev/test/hello
```

关注：

- `msgInCounter` / `bytesInCounter` 是否随发送增长
- 各 `subscriptions.*.msgOutCounter` 谁在读
- `storageSize`、`backlog` 是否异常

### 2. 核对 Topic 全名与持久化

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics list public/default
# 必须是 persistent://tenant/ns/topic，非 non-persistent
```

### 3. 查 Namespace 策略

```powershell
docker exec pulsar-standalone bin/pulsar-admin namespaces get-message-ttl persistent://dev/test
docker exec pulsar-standalone bin/pulsar-admin namespaces get-retention persistent://dev/test
docker exec pulsar-standalone bin/pulsar-admin namespaces get-backlog-quotas persistent://dev/test
```

### 4. 查 Producer 侧

- 同步 `send` 是否 catch 异常
- 异步是否在 `whenComplete` / `exceptionally` 中处理失败
- 是否 `blockIfQueueFull=false` 且队列满被静默丢弃（抛 `ProducerQueueIsFull`）

### 5. 查 Consumer 侧

- `subscriptionName` 是否与预期一致
- 是否有 Consumer `connected`（`topics stats` → subscriptions）
- 是否 ACK 前业务已写库（应先处理再 ACK，见 [P2](P2-重复消费.md)）

### 6. 按 MessageId 追踪（若有）

```java
// 记录 send 返回的 MessageId，Consumer 日志对比
log.info("sent {}", messageId);
```

## 解决方案与预防

| 措施 | 说明 |
|------|------|
| 发送确认 | 关键路径用 sync send 或 async + 失败重试/落库 |
| 持久化 Topic | 生产禁止 non-persistent |
| 合理 Retention/TTL | 核心业务避免过短 TTL；监控磁盘 |
| 显式创建 Topic | 禁用依赖 Auto-Create，见 [B13](../part-b-java-dev/B13-推动策略改造.md) |
| 幂等消费 | 即使「丢」实为重复，业务也不出错 |
| 告警 | `msgIn - msgOut` 差值持续扩大、backlog 暴涨 |
| 禁用危险 Backlog 策略 | 不用 `consumer_backlog_eviction` 除非明确接受丢消息 |

## 面试一句话

> Pulsar 默认持久化 + 至少一次投递，真正「丢」多半是发送失败未处理、策略删数据、或看错 Subscription；排障先看 stats 里消息是否进 Topic、谁在消费、Namespace TTL/Retention/Backlog 策略。
