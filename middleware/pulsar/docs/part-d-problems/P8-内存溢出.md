# P8 OOM / 内存暴涨

> 优先级: **P2 排障** | 深度：批次 3 ✓  
> 链接: [P4 积压](P4-积压.md) | [P5 性能](P5-性能不足.md) | [B10](../part-b-java-dev/B10-性能调优.md)

---

## 典型现象

- JVM `OutOfMemoryError: Java heap space`（应用或 Broker/Bookie）。
- 容器被 OOMKilled，重启循环。
- 堆外/direct memory 耗尽。
- Full GC 频繁后进程僵死。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **receiverQueueSize × Consumer 数 × 消息大小** | 预取过多大消息 |
| 2 | **maxPendingMessages 过大** | 异步发送堆积 |
| 3 | **Backlog 极大 + 全量加载** | 业务一次性 list 所有消息 |
| 4 | **未 ACK 消息堆积** | 客户端持有大量 Message 引用 |
| 5 | **Broker/Bookie heap 配太小** | 集群组件 OOM |
| 6 | **泄漏** | 静态 Map 缓存 Message、未 close Client |
| 7 | **批消息解压** | 单批超大 |

---

## 排查步骤

### 1. 区分进程

| 进程 | 典型配置 |
|------|----------|
| 业务 JVM | `-Xmx`、堆 dump |
| Broker | `PULSAR_MEM`、heap dump |
| Bookie | `BOOKIE_MEM`、journal 目录 |

### 2. 应用 heap dump

```bash
jmap -dump:format=b,file=heap.hprof <pid>
# 看 byte[]、MessageImpl、ConcurrentLinkedQueue
```

### 3. 查 Pulsar 客户端参数

```java
.receiverQueueSize(???)
.maxPendingMessages(???)
```

估算：`receiverQueueSize × avgMsgSize × consumerInstances`。

### 4. 查 backlog

若 backlog 巨大且应用试图缓存，优先消积压而非加 heap。

### 5. 容器 limit

```yaml
resources.limits.memory  # 是否小于 JVM -Xmx + 堆外
```

**容器内存 ≥ Xmx + 直接内存 + 元空间 + 原生库余量**。

---

## 解决方案

| 措施 | 说明 |
|------|------|
| 减小预取 | 降低 `receiverQueueSize` |
| 控制异步队列 | `maxPendingMessages`、背压 `blockIfQueueFull` |
| 流式处理 | 勿一次 `receive` 全 backlog |
| 及时 ACK | 减少未确认消息驻留 |
| 单例 Client | 避免多 Client 重复缓冲 |
| 集群 | 按官方公式调 Broker/Bookie 内存 |
| 消息瘦身 | 压缩、拆字段、外部存储大 payload |

---

## 面试一句话

> 应用 OOM 先看 Pulsar 预取和异步 pending：receiverQueueSize 乘消息大小乘 Consumer 数；大 backlog 不要一次装进内存；容器 limit 要大于 Xmx 加堆外。
