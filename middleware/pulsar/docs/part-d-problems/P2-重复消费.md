# P2 重复消费

> 优先级: **P1 面试 / P2 排障** | 深度：批次 3 ✓  
> 链接: [A6 ACK](../part-a-interview/A6-ACK与投递语义.md) | [B3 Consumer](../part-b-java-dev/B3-消费者.md)

---

## 典型现象

- 同一订单/设备事件被处理**两次及以上**。
- 数据库出现重复主键、重复扣款。
- Consumer 日志里同一 `messageId` 或相同 payload 出现多次。
- **不是 Bug 时**：Pulsar 语义就是**至少一次（At-Least-Once）**。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **ACK 前崩溃** | 业务已写库但未 ACK，重启后重投 |
| 2 | **ACK 后崩溃（极少）** | 网络分区导致 ACK 未达 Broker，Broker 重投 |
| 3 | **negativeAcknowledge** | 主动 NACK 触发重投递 |
| 4 | **处理超时 / redelivery** | `ackTimeout` 或 unacked 超时自动重投 |
| 5 | **Shared 多 Consumer 重平衡** | 未 ACK 消息被其他 Consumer 再次拉取 |
| 6 | **业务重试逻辑重复发** | 上游 Producer 重试无幂等键 |
| 7 | **累积 ACK 误用** | 跳 ACK 导致边界重复（少见） |

---

## 排查步骤

### 1. 确认是否「设计如此」

- 问：是否要求**精确一次**？Pulsar 需 **幂等 + 去重表** 或 **Transaction API**（进阶）。

### 2. 查 Consumer 日志与 MessageId

```text
messageId= (ledgerId, entryId, partitionIndex)
redeliveryCount=  # stats 或日志
```

`redeliveryCount > 0` → 明确是重投递。

### 3. 查 topics stats

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics stats persistent://dev/test/hello
```

看 `subscriptions.<name>.msgRateOut`、`unackedMessages`、`blockedSubscriptionOnUnackedMsgs`。

### 4. 核对处理顺序

- 是否 **先 ACK 再写库**（错误，会导致丢单感；先写库再 ACK 则可能重复）
- 正确：**写库（幂等）→ ACK**

### 5. 查 NACK / 异常路径

- catch 里是否误 `negativeAcknowledge` 可重试错误
- DLQ 是否配置，避免无限 NACK

---

## 解决方案与预防

| 措施 | 实现要点 |
|------|----------|
| **业务幂等** | 以 `messageId` 或业务 `orderId` 做唯一键 INSERT IGNORE / UPSERT |
| **去重表** | 处理前 `INSERT dedup(message_id)`，冲突则 skip |
| **先写库再 ACK** | 事务或本地消息表保证一致性 |
| **避免过早 ACK** | Listener 里不要在异步 Future 完成前就 ACK |
| **合理 ackTimeout** | 处理时间 > timeout 会重复投递 |
| **Key_Shared** | 减少 rebalance 导致的交叉重复（不消除语义重复） |
| **事务消息** | 强一致场景评估 Pulsar Transaction |

```java
// 伪代码：幂等
if (dedupRepo.exists(msg.getMessageId())) {
    consumer.acknowledge(msg);
    return;
}
businessProcess(msg);
dedupRepo.save(msg.getMessageId());
consumer.acknowledge(msg);
```

---

## 与 P1 的区别

| | P1 丢失 | P2 重复 |
|---|---------|---------|
| 表现 | 永远没处理到 | 处理多次 |
| 常见根因 | 发送失败、Retention | ACK 时机、至少一次语义 |

---

## 面试一句话

> Pulsar Consumer 默认至少一次，重复是常态不是异常；解法是在业务层用 messageId 或业务键做幂等，先持久化处理结果再 ACK，并调大 ackTimeout 避免处理中被重投。
