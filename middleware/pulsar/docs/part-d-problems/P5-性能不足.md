# P5 性能不够

> 优先级: **P1 概念 / P2 调优** | 深度：批次 3 ✓  
> 链接: [B10 调优](../part-b-java-dev/B10-性能调优.md) | [B2](../part-b-java-dev/B2-生产者.md) | [B3](../part-b-java-dev/B3-消费者.md) | [P4 积压](P4-积压.md)

---

## 典型现象

- 目标 QPS/TPS 达不到，CPU 不高但吞吐低。
- 端到端延迟 P99 超标。
- 单机压测 OK，集群或生产不达标。
- 加机器后吞吐**线性上不去**。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **同步发送 / 未开 batching** | RTT  bound |
| 2 | **消息体过大** | 网络、BookKeeper 写放大 |
| 3 | **分区数不足** | Consumer 并行度上限 = 分区数 |
| 4 | **receiverQueueSize 过小** | 消费端管道空转 |
| 5 | **Shared 非分区 + 单 Consumer** | 无法水平扩展读 |
| 6 | **未压缩** | 带宽成为瓶颈 |
| 7 | **BookKeeper / 磁盘 IO** | 写延迟高 |
| 8 | **GC / 序列化** | Java 对象分配过多 |
| 9 | **Key 热点** | Key_Shared 单 Consumer 打满 |

---

## 排查步骤

### 1. 分层测瓶颈

```
Producer 本地吞吐 → Broker msgRateIn → Consumer msgRateOut → 业务处理
```

每段用 `topics stats` 的 rate 对比。

### 2. Producer 侧

- 是否 `send` 同步
- `batchingMaxMessages`、`batchingMaxPublishDelay`
- `compressionType`（LZ4/ZSTD）
- `maxPendingMessages`、`blockIfQueueFull`

见 `examples/java/pulsar-producer-tuning`、`pulsar-loadtest`。

### 3. Consumer 侧

- `receiverQueueSize`（通常 500~5000 试）
- Listener vs 同步 receive
- 业务处理是否阻塞 listener 线程

### 4. Topic 拓扑

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics partitioned-stats persistent://dev/test/events
# 分区数、各分区 rate 是否均衡
```

### 5. 集群

- Bookie 写延迟、磁盘类型（SSD）
- Broker CPU、网络带宽
- JVM heap（Broker/Bookie 分别看）

---

## 调优金字塔（影响从大到小）

```
1. 架构：分区数、订阅类型、消息大小设计
2. 批量与压缩：Producer batching + LZ4
3. 并行度：Consumer 实例数、receiverQueueSize
4. 集群资源：Bookie 磁盘、Broker 数
5. JVM 微优化：对象池、零拷贝（进阶）
```

---

## 推荐起点（Java）

```java
// Producer 高吞吐起点
.enableBatching(true)
.batchingMaxPublishDelay(5, TimeUnit.MILLISECONDS)
.compressionType(CompressionType.LZ4)
.blockIfQueueFull(true)

// Consumer
.receiverQueueSize(2000)
```

**注意：** batch 增大 → P99 延迟上升，需按 SLA 权衡。

## 面试一句话

> 性能先找瓶颈段：同步 send 和没开 batch 最常见；分区 Topic 要够分区才能扩 Consumer；大消息开压缩；最后才调 JVM。Shared 非分区扩展读的能力有限，高吞吐要分区加 Key_Shared。
