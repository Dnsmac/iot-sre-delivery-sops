# P9 本地 OK、集群不行

> 优先级: **P2 排障** | 深度：批次 3 ✓  
> 链接: [P6 连接](P6-连接问题.md) | [C1 集群部署](../part-c-ops/C1-集群部署.md) | [附录 I](../appendices/I-环境迁移清单.md)

---

## 典型现象

- `examples/java` 在 Standalone Docker **全部通过**。
- 上到测试/生产集群：**连不上、发不出、消费不到、权限拒绝**。
- 同一套 jar，仅改配置就失败。
- 「本地明明没问题」成为扯皮焦点。

---

## 原因（按概率排序）

| # | 原因 | 说明 |
|---|------|------|
| 1 | **serviceUrl / advertisedAddress** | 客户端解析到内网不可达地址 |
| 2 | **Tenant/Namespace 不存在** | 本地 Auto-Create，集群禁用 |
| 3 | **ACL / JWT 未配** | 403 Forbidden |
| 4 | **Topic 名不一致** | 环境变量未注入，仍写 `dev/test` |
| 5 | **TLS 差异** | 集群强制 SSL，本地明文 |
| 6 | **资源配额** | Namespace quota 限流、禁写 |
| 7 | **版本差异** | 本地 3.x、集群 2.10 API 行为不同 |
| 8 | **网络策略** | K8s NetworkPolicy 阻断 Pod→Broker |
| 9 | **时钟偏差** | JWT 过期、证书 not yet valid |

---

## 排查步骤

### 1. 配置 diff

对比：

- `pulsar.service.url`
- `topic` 全名
- `auth` token 文件/环境变量

### 2. 集群健康

```bash
pulsar-admin brokers healthcheck
pulsar-admin clusters list
pulsar-admin tenants list
```

### 3. 权限

```bash
pulsar-admin namespaces policies persistent://company/production
pulsar-admin topics permissions persistent://company/production/events
```

### 4. 从**与生产相同网络**的机器测试

```bash
bin/pulsar-client produce persistent://company/production/events -m "ping"
```

若 CLI 不通，应用也不必先查代码。

### 5. 看 Broker 返回地址

连接后 Broker 下发的 lookup 地址是否客户端可达（常见 **内网 hostname 外网不可达**）。

---

## 解决方案

| 措施 | 说明 |
|------|------|
| 配置中心化 | Spring `application-{env}.yml`、K8s ConfigMap |
| 启动自检 | 启动时 `admin.healthcheck` + 试发一条 |
| IaC 创建 Tenant/NS | `setup-dev-tenant.ps1` 推广到各环境 |
| 文档化 Topic 清单 | 禁止 Auto-Create 后必须预创建 |
| 统一 TLS | 各环境同一套 truststore 策略 |
| CI 连测试集群 | 合并前跑集成测试 |

## 本地 Standalone 对齐清单

```powershell
.\scripts\standalone-up.ps1
.\scripts\setup-dev-tenant.ps1
.\scripts\verify-examples.ps1
```

集群侧应有等价的 tenant `dev`、namespace `test` 或应用改用 `company/production`。

---

## 面试一句话

> 本地和集群差异常差在地址 advertised、权限和是否 Auto-Create；用 pulsar-client 在同一网络先打通，再查应用配置，不要先怀疑业务逻辑。
