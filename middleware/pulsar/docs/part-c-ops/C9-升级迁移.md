# C9 升级迁移

> 优先级: **P3 运维** | 深度：批次 4 ✓

## 本章解决什么问题

版本升级顺序、Kafka→Pulsar（KoP）迁移、以及应用与 Broker 版本对齐。

---

## 一、版本对齐

| 原则 | 说明 |
|------|------|
| Client ≤ Broker 大版本 | 客户端不宜高于 Broker 太多 |
| 滚动升级 | 逐节点，保证 quorum |
| 阅读 Release Notes | 3.x Oxia 等 breaking 变更 |

---

## 二、滚动升级顺序（参考）

1. 备份配置与元数据快照策略。
2. 升级 **Broker**（逐台，healthcheck）。
3. 升级 **Bookie**（逐台，观察 ADD_ENTRY）。
4. 升级 **Proxy / Manager**。
5. 应用滚动发布（新 Client）。

**勿**同时全停 Bookie。

---

## 三、Kafka → Pulsar（KoP）

| 阶段 | 动作 |
|------|------|
| 1 | 部署 Pulsar + 开启 KoP |
| 2 | Kafka 客户端改 bootstrap 指向 KoP |
| 3 | Mirror 历史数据（可选） |
| 4 | 逐步改用 Pulsar 原生 API |

限制：事务、部分 Admin API 需对照 KoP 文档验证。

---

## 四、业务迁移（Shared → Key_Shared）

见 [B13](../part-b-java-dev/B13-推动策略改造.md)、[P4 项目](../projects/P4-订阅与Topic改造.md)：

- 新 Topic + 双写 / 灰度 Consumer
- 不原地改订阅类型 expecting 无缝

---

## 五、回滚

- 保留上一版本镜像与配置。
- Broker 回滚前确认 Bookie 协议兼容。
- 应用配置 feature flag 切回旧 Topic。
