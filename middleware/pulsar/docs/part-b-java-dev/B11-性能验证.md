# B11 性能验证

> 优先级: **P2 开发** | 预计阅读 25 分钟 | 深度：批次 4 ✓

## 本章解决什么问题

如何**可重复地**验证调优效果、记录对比数据，以及为何必须在 Cluster 上签字 Standalone 数字。

---

## 一、验证流程

```
1. 定 SLA（QPS、P99 延迟、最大 backlog）
2. 基线：调优前 stats + 应用埋点
3. 单次只改一个变量（如 batching on）
4. 稳态运行 ≥ 10~30 分钟
5. 记录：msgRateIn/Out、backlog、CPU、GC、磁盘 IO
6. Cluster 复现后写入报告
```

---

## 二、Broker 侧指标

```powershell
docker exec pulsar-standalone bin/pulsar-admin topics stats persistent://dev/test/hello
```

| 字段 | 含义 |
|------|------|
| `msgRateIn` / `msgRateOut` | 入/出速率 |
| `storageSize` | 存储占用 |
| `subscriptions.*.msgBacklog` | 积压 |
| `subscriptions.*.unackedMessages` | 未 ACK |

Prometheus（生产）：`pulsar_rate_in`、`pulsar_subscription_back_log`、`bookie_ADD_ENTRY` 等，见 [C5](../part-c-ops/C5-监控告警.md)。

---

## 三、应用埋点

```java
long t0 = System.nanoTime();
producer.newMessage().value(payload).sendAsync()
    .whenComplete((id, ex) -> {
        long ms = (System.nanoTime() - t0) / 1_000_000;
        metrics.record("pulsar.send.latency", ms, ex == null ? "ok" : "err");
    });
```

消费侧：处理开始/结束、`redeliveryCount`、是否 DLQ。

## 六、环境约束（重要）

| 动作 | Standalone | Cluster |
|------|-----------|---------|
| 功能验证 | ✅ | ✅ |
| Batching 趋势 | ✅ | ✅ |
| **签字 QPS/延迟** | ❌ | ✅ |
| 连接数 10W | ❌ | ✅ |
| DLQ/ACK 验证 | ✅ | ✅ |

见 [B12](B12-环境模型.md)、[C11](../part-c-ops/C11-十万设备压测.md)。

---

## 七、易错点

1. 压测 1 分钟就下结论。
2. 同时改 batch、分区、Consumer 数，无法归因。
3. 用 Standalone 数字报给业务容量承诺。
4. 不看 backlog 只看出队速率。
