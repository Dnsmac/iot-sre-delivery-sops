# B10 性能调优

> 优先级: **P2 开发** | 预计阅读 35 分钟 | 深度：批次 1

## 调优金字塔（影响从大到小）

```
L0 架构（Topic 数、分区、订阅模式、消息大小）     ★★★★★
L1 Batching + 压缩（小消息）                      ★★★★★
L2 并发（分区数 × Consumer 实例）                 ★★★★
L3 Client（队列、预取、ACK 方式、超时）           ★★★
L4 Broker/Bookie（Cache、Journal、Bundle）       ★★  → 找运维
L5 硬件（SSD、网络、内存）                        ★★
```

**原则：** 在 L0~L3 用尽前，不要先改 L4/L5。

---

## L0 架构设计

| 决策 | 错误 | 正确 | 影响 |
|------|------|------|------|
| Topic 数量 | 10W 设备 = 10W Topic | 少量 Topic + deviceId Key | 元数据/GC |
| 分区数 | 1 分区扛全部 | `目标吞吐÷5~10MB/s每分区` | 写扩展 |
| 订阅 | 有序用 Shared | Key_Shared | 正确性 |
| 消息体 | 10MB 单条 | <1MB 或 chunking | 内存/网络 |

**分区估算：**

```
10W 设备 × 1条/10s × 512B ≈ 5 MB/s  → 1~2 分区
10W 设备 × 1条/s × 512B   ≈ 50 MB/s → 8~16 分区
```

---

## L1 Batching + 压缩

小消息（<1KB）不开 Batching，吞吐可差 **5~20 倍**。

```java
.enableBatching(true)
.batchingMaxPublishDelay(10, TimeUnit.MILLISECONDS)
.compressionType(CompressionType.LZ4)
```

| batchingMaxPublishDelay | 效果 |
|-------------------------|------|
| 0~1ms | 低延迟，吞吐一般 |
| 10~50ms | 高吞吐，P99 +delay |

验证：[BatchCompareBenchmark](../../examples/java/pulsar-producer-tuning/)

---

## L2 并发度

- 分区只能**增加**不能减少。
- Key_Shared：有效 Consumer 数受 Key 分布和分区数约束。
- Shared：Consumer 可多加，但无序。

---

## L3 Client 参数

**Producer：** `maxPendingMessages` 500~2000，`blockIfQueueFull(true)` 防 OOM。

**Consumer：** `receiverQueueSize` 开发 100 / 生产 1000；`ackTimeout` = P99×3。

**ACK：** 可幂等 → 累积 ACK 换吞吐。

---

## L4 升级信号（找运维）

| 信号 | 动作 |
|------|------|
| ADD_ENTRY P99 > 10ms | Journal SSD / 加 Bookie |
| Broker CPU > 80% | 扩 Broker |
| backlog 全局涨 | 集群容量 |

---

## 决策树

```
吞吐不够？
├─ <1KB 消息 → Batching+LZ4 开了吗？
│   └─ 开了 → 分区？Consumer 数？
│       └─ 仍不够 → L4 指标
├─ 大消息 → Chunking
└─ 全局慢 → 集群；单 Topic → 代码/配置

延迟高？
├─ 减小 batchingMaxPublishDelay
├─ 减小 receiverQueueSize
└─ 优化 Consumer 逻辑

OOM？
├─ blockIfQueueFull
├─ 减小预取
└─ Chunking
```
