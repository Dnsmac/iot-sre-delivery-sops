# B2 Producer 开发

> 优先级: **P2 开发** | 预计阅读 40 分钟 | 深度：批次 2 ✓

## 本章解决什么问题

把消息**正确、稳定、够快**地发进 Pulsar：发送模式、Key 路由、Batching、压缩、背压、Schema、异常处理。Producer 配错了，Consumer 再完美也白搭。

---

## 一、创建 Producer

### 1.1 依赖与 Client

```xml
<dependency>
  <groupId>org.apache.pulsar</groupId>
  <artifactId>pulsar-client</artifactId>
  <version>3.2.3</version>
</dependency>
```

```java
// 应用内单例
PulsarClient client = PulsarClient.builder()
    .serviceUrl("pulsar://localhost:6650")
    .build();

Producer<byte[]> producer = client.newProducer()
    .topic("persistent://dev/test/events")
    .create();
```

| 原则 | 说明 |
|------|------|
| 一个 JVM 一个 `PulsarClient` | 内置连接池 |
| Producer 可多个 | 不同 Topic 各一个，用完 close |
| Topic 在 builder 指定 | 也可 `newProducer().topic(...)` 链式 |

### 1.2 Typed Producer（Schema）

```java
Producer<OrderEvent> producer = client.newProducer(Schema.AVRO(OrderEvent.class))
    .topic("persistent://company/order/order-created")
    .create();

producer.send(new OrderEvent("order-1", 100.0));
```

- 生产环境 **强烈建议** 注册 Schema，禁止随意改字段不兼容。
- 见 [B4](B4-多服务协作.md)、[A9](../part-a-interview/A9-Schema注册.md)。

## 二、发送模式

### 2.1 同步 `send()`

```java
MessageId id = producer.send("payload".getBytes());
// 或
MessageId id = producer.send(producer.newMessage().value(bytes).key("k1"));
```

| 优点 | 缺点 |
|------|------|
| 简单，失败抛异常 | 阻塞线程，吞吐低 |

适合：低频控制消息、管理接口、测试。

### 2.2 异步 `sendAsync()`（高吞吐必用）

```java
producer.newMessage()
    .key(orderId)
    .value(jsonBytes)
    .property("source", "order-service")
    .eventTime(System.currentTimeMillis())
    .sendAsync()
    .thenAccept(messageId -> log.debug("ok {}", messageId))
    .exceptionally(ex -> {
        log.error("send failed, orderId={}", orderId, ex);
        metrics.increment("pulsar.send.fail");
        return null;  // 必须处理，否则「静默丢发送感知」
    });
```

**生产铁律：** 凡 `sendAsync` **必须** `exceptionally` 或 `whenComplete`，并打点监控。

### 2.3 `flush()` 与关闭

```java
producer.flush();   // 将 batch 缓冲区刷出
producer.close();   // 关闭前 flush
client.close();
```

- 压测结束、进程退出前 **必须 flush**，否则 batch 窗口内消息可能未发出。
- [ProducerDemo](../../examples/java/pulsar-basics/src/main/java/com/demo/pulsar/ProducerDemo.java)

## 三、Message 组成

| 字段 | API | 用途 |
|------|-----|------|
| Payload | `.value(byte[])` | 业务 body |
| Key | `.key(String)` | 分区路由 + Key_Shared |
| Properties | `.property(k,v)` | 业务元数据，不参与路由 |
| EventTime | `.eventTime(long)` | 事件时间，回溯用 |
| SequenceId | `.sequenceId(long)` | 去重（需 Broker 开启 dedup） |
| DeliverAt | `.deliverAfter(10, SECONDS)` | 延迟消息 |

```java
producer.newMessage()
    .key(deviceId)                          // 10W 设备：deviceId 作 Key
    .value(payload)
    .property("fwVersion", "1.2.3")
    .eventTime(sampleTimeMs)
    .sendAsync();
```

**你们改造点：** Shared 消费 + 无 Key → 应加 **Key** 并改 **Key_Shared**（[B13](B13-推动策略改造.md)）。

## 四、性能相关配置（大数据量必看）

### 4.1 生产推荐模板

```java
Producer<byte[]> producer = client.newProducer()
    .topic("persistent://company/iot/telemetry")
    .producerName("iot-gateway-1")           // 可选，便于排查
    .enableBatching(true)
    .batchingMaxPublishDelay(10, TimeUnit.MILLISECONDS)
    .batchingMaxMessages(1000)
    .batchingMaxBytes(128 * 1024)
    .compressionType(CompressionType.LZ4)
    .maxPendingMessages(1000)
    .maxPendingMessagesAcrossPartitions(50000)
    .blockIfQueueFull(true)                  // 防 OOM
    .sendTimeout(30, TimeUnit.SECONDS)
    .create();
```

### 4.2 参数详解

| 参数 | 推荐 | 说明 |
|------|------|------|
| `enableBatching` | **true** | 小消息吞吐差 5~20 倍若关闭 |
| `batchingMaxPublishDelay` | 10~50ms | 越大吞吐越高，P99 延迟越高 |
| `batchingMaxMessages` | 500~2000 | 每批条数上限 |
| `compressionType` | **LZ4** | CPU/带宽平衡；ZSTD 更高压缩 |
| `maxPendingMessages` | 500~2000 | 单分区队列；满则阻塞或失败 |
| `blockIfQueueFull` | **true** | true=背压；false=可能 OOM |
| `sendTimeout` | 30s | 发送超时失败回调 |

### 4.3 延迟敏感场景

```java
.batchingMaxPublishDelay(1, TimeUnit.MILLISECONDS)
.batchingMaxMessages(10)
// 或 batching 关闭（吞吐会掉）
```

### 4.4 大消息 Chunking

```java
Producer<byte[]> producer = client.newProducer()
    .topic("persistent://dev/test/large")
    .enableChunking(true)
    .chunkMaxMessageSize(1024 * 1024)  // 1MB 分块
    .create();
```

- 单条超过 `maxMessageSize`（默认约 5MB，可配）必须分块。
- Consumer 需开启 chunk 消费，注意 **内存**（见 [B5](B5-大数据量注意点.md)）。

## 五、分区与路由

```java
// 默认 Hash 路由：相同 Key → 相同分区
producer.newMessage().key("user-123").value(v).send();

// 无 Key：Round Robin 各分区
producer.newMessage().value(v).send();
```

- **非分区 Topic** 设 Key 仍只有一个分区，Key 只影响 Key_Shared 消费，不影响写并行。
- 要写并行 + Key 有序：**分区 Topic + Key**。

## 六、异常与可靠性

| 场景 | 处理 |
|------|------|
| send 失败 | 重试 + 告警；记录 businessKey 补发 |
| Broker 短暂不可用 | Client 自动重连；sendAsync 失败走 exceptionally |
| 不想丢 | 同步 send 或 sendAsync + 失败落本地表/队列 |
| 精确一次发 | Broker 端 dedup + sequenceId；或 Transaction |

**不要** 以为「发到 Broker 返回 OK」= 消费者一定处理成功；那是 Consumer 侧 ACK 的事。

## 七、多环境配置

```yaml
# application-prod.yml
pulsar:
  service-url: pulsar://prod-proxy:6650
  topic: persistent://company/production/telemetry
  producer:
    batching-enabled: true
    compression: LZ4
```

开发可关 Batching 方便调试；**测试/生产必须与压测一致**（[B12](B12-环境模型.md)）。

## 八、常见问题（开发自查）

| 现象 | 检查 |
|------|------|
| 吞吐很低 | Batching 开了吗？压缩？分区数？ |
| 延迟很高 | batchingMaxPublishDelay 太大？ |
| OOM | blockIfQueueFull？pending 太大？ |
| 同 Key 没落同分区 | 是否分区 Topic？Key 是否 null？ |
| 发送无异常但对方收不到 | Topic 名错、租户错、non-persistent？ |
