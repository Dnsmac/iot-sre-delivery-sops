# B13 推动策略改造：说服同事与上级

> 优先级: **P2 开发** | 预计阅读 50 分钟 | 深度：批次 2 ✓  
> 配合 [附录 K](../appendices/K-方案一页纸模板.md) | [P4](../projects/P4-订阅与Topic改造.md)

## 本章解决什么问题

你们当前典型现状：**Shared 订阅 + 非分区 Topic + 默认 Auto-Create**。技术上能跑，但一旦有 **顺序要求、流量上涨、多环境上线、10W 设备压测**，风险会集中爆发。本章教你用 **证据 + 分期 + 可回滚** 推动改，而不是「Pulsar 书上说要 Key_Shared」。

---

## 一、什么时候「不用改」（必须先讲）

| 现状 | 可维持条件 | 对上级一句话 |
|------|------------|--------------|
| **Shared** | 日志/埋点；不要求顺序；幂等；可接受乱序 | 「我们要吞吐，不要顺序」 |
| **非分区** | 峰值 ≪ 5~10 MB/s；6 个月内无压测/翻倍 | 「单通道够用，已留监控」 |
| **Auto-Create** | 仅 dev；Topic <20；无生产 | 「生产会关，本期不动」 |

**三条全满足** → 只加：生产关 Auto-Create + backlog 告警。  
**任一条不满足** → 走下文改造路径。

---

## 二、技术事实 → 业务语言（说服核心）

### 2.1 Shared 的问题（你们最可能踩坑）

| 技术 | 业务后果 | 真实案例描述方式 |
|------|----------|------------------|
| 多 Consumer 抢消息，无 Key 亲和 | 同一订单/设备事件被不同实例处理 | 「用户先收到已支付再收到待支付」 |
| 无法与「按 ID 排队」对齐 | 状态机错乱、补偿任务增多 | 「客诉：状态跳变」 |
| 排查难 | 日志分散在多实例 | 「复现不了，因为随机分到不同 Pod」 |

**改法：** `SubscriptionType.Key_Shared` + Producer `.key(businessId)` + 可选 `KeySharedPolicy.stickyHashRange()`。

**代码改动面（给同事看）：**

```java
// Before
.subscriptionType(SubscriptionType.Shared)

// After
.subscriptionType(SubscriptionType.Key_Shared)
.keySharedPolicy(KeySharedPolicy.stickyHashRange())

// Producer 增加
producer.newMessage().key(deviceId).value(payload).sendAsync()...
```

### 2.2 非分区 Topic 的问题

| 技术 | 业务后果 |
|------|----------|
| 单 Managed Ledger 写入 | 流量翻倍后 Producer 延迟、积压 |
| 加 Consumer 不能线性提速（Key_Shared 也受分区数限制） | 「加了 4 台实例几乎没快」 |
| 分区只能增不能减 | 「上线前不规划，后面只能救火」 |

**改法：** `create-partitioned-topic -p N`，N 用 [A4 公式](../part-a-interview/A4-Topic体系.md) 估算。

```bash
pulsar-admin topics create-partitioned-topic \
  persistent://company/iot/telemetry -p 8
```

### 2.3 Auto-Create 的问题

| 技术 | 业务后果 |
|------|----------|
| `persistent://company/order/order-creatd` typo | 消息进黑洞 Topic，stats 有 in 无 out |
| 测试无、生产自动有 | 「我本地好好的」 |
| 无 Namespace 策略 | 磁盘打满、无 Retention |

**改法：** 生产 `allowAutoTopicCreation=false`；CI 脚本建 Topic；配置中心写死全路径。

## 三、决策表（打印贴墙）

| # | 问题 | 答「是」→ |
|---|------|----------|
| 1 | 同一 deviceId/orderId 必须顺序？ | Key_Shared + Key |
| 2 | 峰值接近单 Topic 瓶颈或要压测？ | 分区 Topic |
| 3 | 有 test/staging/prod？ | 生产禁 Auto-Create |
| 4 | 多服务消费同一 Topic？ | 每服务独立 subscriptionName 文档化 |
| 5 | 6 个月内有 10W 连接/设备？ | Cluster + Proxy + 分区规划 |

填表见 [P4 阶段 0](../projects/P4-订阅与Topic改造.md)。

## 四、证据怎么拿（无数据别开会）

### 4.1 一周最小证据包

| 天 | 动作 | 产出 |
|----|------|------|
| D1 | 扫代码：`SubscriptionType.Shared`、`.topic(`、无 `.key(` | 改造清单 Excel |
| D2 | `topics list` + 配置 diff | 环境不一致列表 |
| D3 | 核心 Topic `topics stats` 截图 24h | backlog、rate |
| D4 | 同一 Topic 开 Key_Shared 测试环境对比 | 乱序 case 消失 |
| D5 | 填 [附录 K](../appendices/K-方案一页纸模板.md) | 一页纸草案 |

### 4.2 命令模板

```powershell
# 积压与速率
docker exec pulsar-standalone bin/pulsar-admin topics stats `
  persistent://company/namespace/your-topic

# 看各 subscription
# subscriptions.<name>.backlogSize
# msgRateIn / msgRateOut
```

### 4.3 乱序复现（说服同事杀手锏）

1. Shared + 2 个 Consumer 实例。
2. Producer 带相同 `key=test-1` 发 100 条有序序号。
3. 消费日志看序号是否交叉。
4. 改 Key_Shared + STICKY 再测 → 单 Consumer 内有序。

## 五、话术（可直接改名词用）

### 5.1 对开发同事（技术会）

> 我们不是否定现有方案，而是 **Shared 只适合无顺序场景**。  
> 【订单/设备】链路已经要求同 ID 顺序，属于 **模式选错**，调 JVM 没用。  
> 我建议只动 **【一个 Topic】**：Consumer 改 Key_Shared，Producer 加 key，subscription 名不变，两周灰度。  
> 分区先不动，除非 stats 显示单 Topic 吞吐已经顶到 【X MB/s】。

**反驳表：**

| 他们说 | 你回 |
|--------|------|
| 一直没事 | 「没顺序要求时 Shared 是对的；有要求时迟早出事，只是流量还没暴露。」 |
| 加机器就行 | 「非分区加机器对写吞吐帮助有限，Consumer 并行还受模式限制。」 |
| 改动太大 | 「第一期只加 key + 改订阅类型，Topic 名不变。」 |

### 5.2 对上级 / 产品（业务会）

> 当前消息总线在 【低流量、无顺序】 场景运行正常。  
> 【核心业务】需要 【同一客户/设备事件按序处理】，现技术方案 **无法保证**，已出现/可能出现 【状态错误、客诉、对账困难】。  
> 建议分三期：**① 生产消息通道治理（关自动建 Topic、统一命名）约 【3 人日】；② 核心链路消费模式升级 【5 人日】；③ 按 【压测/双十一】 数据加分区 【视结果】**。  
> 若不改，【压测/扩容】时风险集中在 【时间点】，可能 **临时停服改架构**。

**不要讲：** BookKeeper、Ledger — 讲 **风险、工期、范围、可回滚**。

### 5.3 对架构师（选型会）

> Pulsar 的优势是多订阅、存储计算分离；我们没用分区是在 **L0 架构** 上留了债。  
> 与 Kafka 对比：我们相当于 **单分区 + 随机消费组**，丢了 Pulsar Key_Shared 的能力。  
> 建议与 【MQTT 接入 / 10W 设备】 统一规划：少 Topic + deviceId Key + 分区按压测定。

## 六、分期改造（默认路线）

| 阶段 | 内容 | 风险 | 人日参考 | 回滚 |
|------|------|------|----------|------|
| **0** | 盘点 Topic/订阅/Key/峰值 | 低 | 2~3 | — |
| **1** | 生产关 Auto-Create；脚本建 Topic；命名规范 | 低 | 3~5 | 临时开回 Auto-Create |
| **2** | 单核心 Topic：Key_Shared + Producer Key | 中 | 5~8 | 改回 Shared |
| **3** | 新分区 Topic 或 `update-partitioned-topic` | 中 | 5~15 | 双写切回旧 Topic |
| **4** | 监控、DLQ、压测报告、文档 | 低 | 持续 | — |

**阶段 2 灰度建议：**

- 新 subscription：`order-service-keyshared` 并行消费，对比 backlog。
- 或 单 Pod 先上，再扩实例。
- **不要** 同时改分区 + 改订阅 + 改 Schema。

## 七、与 10W 设备 / 压测的关系

| 错误预期 | 正确预期 |
|----------|----------|
| 10W 设备 = 10W Topic | 1~2 个 Topic + 10W 个 Key |
| Standalone 压过就行 | Cluster + Proxy + EMQX/MQTT 另论 |
| Shared 能扛 10W 连接 | 连接与消费模式是两件事；顺序仍要靠 Key_Shared |

压测见 [C11](../part-c-ops/C11-十万设备压测.md)、[Pulsar C11](../../pulsar/docs/part-c-ops/C11-十万设备压测.md)。
