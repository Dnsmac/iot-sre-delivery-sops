# B4 多服务协作规范

> 优先级: **P2 开发** | 预计阅读 35 分钟 | 深度：批次 3 ✓

## 本章解决什么问题

多个 Java 微服务共用同一 Pulsar 集群时，如何命名 Topic、划分订阅、共享 Schema、避免互相抢消息或进度串线——这是 Pulsar 相对 Kafka 的**核心优势**（多 Subscription 独立 Cursor），也是团队最容易踩坑的地方。

---

## 面试常问

1. 两个服务消费同一 Topic，要几个 Subscription？
2. 订阅名和 Consumer 实例数什么关系？
3. 新服务要从头读历史数据怎么做？
4. 和 Kafka Consumer Group 的对应关系？
5. 如何避免测试环境写到生产 Tenant？

## 一、命名空间与 Topic 规范

### 1.1 全名格式

```
persistent://{tenant}/{namespace}/{topic-name}
```

### 1.2 Topic 命名建议

```
persistent://{tenant}/{namespace}/{domain}-{event}
```

| 部分 | 示例 | 说明 |
|------|------|------|
| tenant | `company` | 公司/环境级隔离 |
| namespace | `order` | 业务域 |
| topic | `order-created` | 事件名，kebab-case |

**反例：** `persistent://public/default/mytopic`（生产禁用 public/default + Auto-Create）

### 1.3 环境隔离

| 方式 | 做法 |
|------|------|
| 推荐 | 不同 tenant：`company-dev` / `company-prod` |
| 可选 | 同 tenant 不同 namespace：`order-dev` / `order-prod` |
| 禁止 | 仅 Topic 后缀 `_test` 无租户隔离 |

配置通过 `application-{profile}.yml` 或环境变量注入，禁止写死在代码里。

## 二、订阅名 = 服务身份

### 2.1 规则

- **一个微服务（逻辑应用）= 一个 subscriptionName**。
- 该服务水平扩容：多个 Consumer **实例**，**相同** subscriptionName。

```
order-service          → 处理订单创建
inventory-service      → 扣库存
analytics-service      → 埋点统计
```

### 2.2 与 Kafka 对比

| Kafka | Pulsar |
|-------|--------|
| Consumer Group = 一组消费者共享 offset | Subscription = 一组消费者共享 Cursor |
| 同 Topic 另一 CG = 另一套 offset | 同 Topic 另一 Subscription = 另一套 Cursor |

**面试句：** 在 Pulsar 里要让两个服务各自消费全量消息，不是两个 Consumer Group 抢分区，而是**两个 Subscription 各读一份**。

### 2.3 反例

```java
// 错误：订单服务和库存服务都用 "my-sub"
.subscriptionName("my-sub")
```

结果：两个服务**竞争同一条消息**，且共用一个进度，一方 ACK 影响另一方。

## 三、多服务消费同一 Topic（标准模式）

```
                    ┌─ subscription: order-service ──► 订单服务 (N 实例)
Topic: order-created┼─ subscription: inventory-service ► 库存服务
                    └─ subscription: analytics-service ► 分析服务
```

每个 Subscription：

- 独立 **msgBacklog**
- 独立 **Cursor**
- 可不同 **SubscriptionType**（一般业务 Key_Shared，分析 Shared）

```java
// 订单服务
client.newConsumer().topic(ORDER_CREATED).subscriptionName("order-service")...

// 分析服务（同一 Topic，不同订阅名）
client.newConsumer().topic(ORDER_CREATED).subscriptionName("analytics-service")...
```

## 四、服务间事件契约

### 4.1 Schema 协作

1. 公共 Maven 模块 `events-api` 放 Avro/JSON/Protobuf 定义。
2. Namespace 设 **BACKWARD** 兼容（默认）：**先升 Consumer，再升 Producer**。
3. CI 跑 Schema 兼容性检查。

见 [P7 Schema](../part-d-problems/P7-Schema问题.md)、[附录 L Schema](../appendices/L-Schema注册表速查.md)。

### 4.2 消息属性约定

| 属性 | 用途 |
|------|------|
| `traceId` | 链路追踪 |
| `source` | 生产服务名 |
| `version` |  payload 版本 |

### 4.3 幂等与去重

- 消费方以 `messageId` 或业务 `eventId` 去重。
- 跨服务调用失败：本服务 NACK 或进 DLQ，**不要**要求 Pulsar 精确一次。

## 五、新服务接入与补数

| 需求 | 配置 |
|------|------|
| 只消费新消息 | `SubscriptionInitialPosition.Latest` |
| 全量历史 | `Earliest`（受 Retention 限制） |
| 从某天回放 | `seek(timestamp)` |

新服务 = **新 subscriptionName**，不影响老服务 Cursor。

## 六、权限与治理（多团队）

```bash
pulsar-admin namespaces set-clusters persistent://company/order --clusters company-cluster
pulsar-admin namespaces grant-permission persistent://company/order \
  --roles order-team --actions produce,consume
```

- 按 namespace 授权，避免全集群 admin。
- 禁止生产 Auto-Create（[B13](B13-推动策略改造.md)）。

## 七、与你们现状的对照

| 现状 | 风险 | 建议 |
|------|------|------|
| Shared + 非分区 | 单服务多实例也乱序 | Key_Shared + 分区 |
| Auto-Create | 环境串 Topic | IaC 预创建 + B8 配置 |
| 订阅名随意 | 服务抢消息 | 订阅名 = 服务名登记册 |

## 八、易错点

1. 复制粘贴 Demo 的 `subscriptionName("my-sub")` 到所有服务。
2. 把 DLQ Topic 和消费 Topic 用同一 subscriptionName。
3. 分析服务用 Exclusive，导致只能单实例。
4. 测试 Producer 连到 prod tenant（配置未隔离）。

## 九、动手验证

1. 启动 `ProducerDemo` 向 `persistent://dev/test/hello` 发 10 条。
2. 开两个不同 `subscriptionName` 的 Consumer，应各收到 10 条。
3. 开两个**相同** subscriptionName 的 Consumer（Shared），应**分摊** 10 条。

```powershell
.\scripts\verify-examples.ps1
```

---

## 面试标准答案

> 多个服务消费同一 Topic 时，每个服务使用不同的 subscriptionName，各自维护独立的消费进度，互不影响。同一服务扩容时多个 Consumer 实例使用相同的 subscriptionName 和 Shared 或 Key_Shared 模式分担消息。这和 Kafka 多个 Consumer Group 各读一份类似，但 Pulsar 用 Subscription 一等公民表达更清晰。
