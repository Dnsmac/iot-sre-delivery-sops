## 一、Consumer 与 Subscription

### 1.1 基本消费循环

```java
Consumer<byte[]> consumer = client.newConsumer()
    .topic("persistent://dev/test/my-topic")
    .subscriptionName("order-service")
    .subscriptionType(SubscriptionType.Shared)
    .subscribe();

while (true) {
    Message<byte[]> msg = consumer.receive();
    try {
        handle(msg);
        consumer.acknowledge(msg);
    } catch (Exception e) {
        consumer.negativeAcknowledge(msg);
    }
}
```

### 1.2 Subscription 命名

- 同一 **subscriptionName** 下所有 Consumer 实例共享**同一 Cursor**（进度）。
- **不同微服务必须用不同 subscriptionName**（见 [B4](B4-多服务协作.md)）。

---

## 二、四种订阅类型（开发必选）

| 类型 | 并行 | 同一 Key 有序 | 典型场景 |
|------|------|---------------|----------|
| **Exclusive** | 单 Consumer | — | 单实例任务 |
| **Failover** | 主备 | — | HA 单活 |
| **Shared** | 多 Consumer 轮询 | **无** | 日志、可乱序 |
| **Key_Shared** | 多 Consumer | **同 Key 同 Consumer** | 订单、设备 |

### 当前项目现状（需改造）

- **Shared + 非分区**：消息在多个 Consumer 间**随机分配**，同设备/订单可能乱序。
- 目标：**Key_Shared + 分区 Topic + Producer Key**，见 [B13](B13-推动策略改造.md)。

### Key_Shared 示例

```java
Consumer<byte[]> consumer = client.newConsumer()
    .topic("persistent://dev/test/device-events")
    .subscriptionName("device-processor")
    .subscriptionType(SubscriptionType.Key_Shared)
    .keySharedPolicy(KeySharedPolicy.stickyHashRange())
    .receiverQueueSize(1000)
    .subscribe();
```

| 策略 | 说明 |
|------|------|
| `autoSplitHashRange` | 默认，按 Key 哈希分配 |
| `stickyHashRange` | Key 尽量粘在同一 Consumer，减少 rebalance 乱序 |

## 三、MessageListener（推荐写法）

```java
consumer.listener((c, msg) -> {
    try {
        process(msg);
        c.acknowledge(msg);
    } catch (Exception e) {
        c.negativeAcknowledge(msg);
    }
}).subscribe();
```

- 吞吐高于单线程 `receive()`。
- **不要在回调里长时间阻塞**（外部 RPC、大 SQL），否则占满 listener 线程。
- 异步处理时：**先完成业务写库（幂等）再 ACK**，见 [P2](../part-d-problems/P2-重复消费.md)。

---

## 四、ACK / NACK / 重投递

```java
consumer.acknowledge(msg);
consumer.acknowledgeAsync(msg);
consumer.negativeAcknowledge(msg);
consumer.acknowledgeCumulative(msg); // 慎用：确认该 id 及之前所有
```

- 默认 **至少一次**；ACK 前崩溃 → 重投。
- NACK → 稍后重投递，Shared 下可能换 Consumer，顺序更乱。

详见 [A6 ACK 语义](../part-a-interview/A6-ACK与投递语义.md)。

## 五、DLQ 配置

```java
.deadLetterPolicy(DeadLetterPolicy.builder()
    .maxRedeliverCount(3)
    .deadLetterTopic("persistent://dev/test/my-dlq")
    .build())
```

流程：失败 → NACK → 超过次数 → 进入 DLQ Topic → 人工/批处理修复。避免无限 NACK 打满 CPU。

## 六、并发与流控

| 参数 | 作用 |
|------|------|
| `receiverQueueSize` | 预取缓冲；过大占内存（见 [P8](../part-d-problems/P8-内存溢出.md)） |
| `maxUnackedMessages` | 未 ACK 上限，背压 |

## 八、Reader（无 Subscription）

只读、不 ACK、不影响 Subscription 进度——适合离线导出。见 [A5](../part-a-interview/A5-订阅模式.md)。

---

## 九、生产环境注意点

- 关键业务：**幂等键**（messageId 或业务 id）+ 先写库再 ACK。
- 设备/订单：**禁止**长期 Shared + 非分区（见 B13）。
- 监控：backlog、`msgRateOut`、Consumer `connected`（[P4](../part-d-problems/P4-积压.md)）。

---

## 十、易错点

1. 两个服务共用同一 `subscriptionName` → 抢消息、进度混乱。
2. Listener 里先 ACK 再异步写库 → 可能丢业务语义上的「处理完成」。
3. Shared 下期望 Key 有序 → 架构选错，调参无解。
4. 不设 DLQ，NACK 死循环。

## 面试标准答案

> Shared 下消息轮询分给多个 Consumer，不保证顺序。Key_Shared 保证相同 Key 由同一 Consumer 处理，Key 内有序且可并行不同 Key。设备场景应使用 Key_Shared、Producer 带 Key、分区 Topic，而不是 Shared 加非分区。
