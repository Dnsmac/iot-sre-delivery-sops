## 核心知识

| 特性 | 说明 | 价值 |
|------|------|------|
| 原因码 | CONNACK/PUBACK/DISCONNECT 等带原因 | 排障可定位 |
| 用户属性 | 键值扩展元数据 | 链路追踪、租户标签 |
| 会话过期 | Session Expiry Interval | 替代 Clean Session 粗粒度 |
| 消息过期 | Message Expiry | 过期自动丢 |
| 共享订阅 | `$share/group/topic` | 多消费者负载均衡 |
| Receive Maximum | 流控 | 背压、防打爆 |
| 主题别名 | Topic Alias | 省带宽 |

### 共享订阅

```
$share/g1/acme/iot/+/telemetry
```

- 同组 **竞争消费**，一条消息只给一个成员（Broker 实现相关）。
- 类似 **消费组**，但仍在 MQTT 语义内。

### 选型建议

- **新项目** 设备与 Broker 均支持 → 可考虑 5.0。
- **存量 3.1.1 设备** → 网关协议转换或长期双栈。

Paho：**org.eclipse.paho.mqttv5** 独立客户端；本仓示例以 **3.1.1** 为主。

## 面试标准答案

### 题：MQTT 5.0 值得升级吗？

> 若团队被 3.1.1 的模糊错误码、无法流控、共享订阅需求困扰，且 EMQX 等 Broker 与固件都能支持，5.0 值得规划。若大量旧设备只支持 3.1.1，应在网关统一 3.1.1 接入，后端用 5.0 或 Kafka。面试层面说清差异即可，不必未上线就全栈 5.0。

### 题：共享订阅和 Kafka 消费组像吗？

> 思想类似，都是多个订阅者分担消息，但实现、重平衡、offset 语义不同。MQTT 共享订阅不替代 Kafka 的长期存储与回溯，适合 **实时接入层** 多实例消费。

## 生产环境注意点

- Broker 与客户端 **版本协商** 失败会 CONNACK 1。
- 规则引擎、桥接对 5.0 属性支持不一，上生产前压测。

---

## 易错点与反例

1. **以为 5.0 自动更快** — 特性多，实现不当更复杂。
2. **共享订阅组名混乱** — 消息分配不均。
3. **忽略 Receive Maximum** — 仍打满 inflight。

## 动手验证
