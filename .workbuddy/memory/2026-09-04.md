## Pulsar Bookie ARM64 SIGSEGV 排查
- 现象：bookie 容器 SIGSEGV 崩溃（pid=1），Corretto-21.0.8.9.1，linux-aarch64，ZGC，core dump 落 /pulsar/core.1，hs_err 在 /tmp/hs_err_pid1.log；problematic frame 打印超时未显示。日志里 Ledger fenced WARN 是 BookKeeper 正常行为非根因。
- 已知匹配：Pulsar 3.3.0/3.3.1 的 Alpine（musl）镜像在 aarch64 上已知崩溃问题，官方在 3.3.4/4.0.2 修复；另一已知类：RocksDB librocksdbjni 在 Corretto21+aarch64 崩溃（BookKeeper#4558，Pulsar 4.0.3+/BK 4.17.x 修复）。
- 给出的方案：①先抓 /tmp/hs_err_pid1.log 的 problematic frame + 确认镜像是否 Alpine（ldd --version / ld-musl）；②Alpine→换 Debian 镜像或升级 Pulsar≥3.3.4/4.0.2；③RocksDB 帧→升级；④通用缓解：-Dio.netty.transport.noNative=true、ZGC 换 G1（PULSAR_GC）；⑤hs_err 落持久卷：-XX:ErrorFile=/pulsar/data/hs_err_%p.log。
- 待用户提供：Pulsar/BookKeeper 版本、镜像 tag、hs_err 的 problematic frame 行。

## Pulsar Bookie 崩溃二次定位（关键新证据）
- 用户已加 -Dio.netty.transport.noNative=true 仍崩溃——排除 Netty native 路径。
- JVM 参数含 -XX:+UseZGC -XX:+ZGenerational -XX:+AlwaysPreTouch -XX:+UseTransparentHugePages——ZGenerational 在 linux-aarch64 是已知 SEGV bug 家族（JDK-8311066: ZPhysicalMemoryManager::nmt_commit SEGV on aarch64，影响 JDK21）。
- 两次崩溃 tid=163 完全相同 + 错误报告器本身超时挂死（timer expired, abort）→ 判定为 VM/GC 层崩溃而非 native 业务库崩溃。
- 处方：第一步删 -XX:+ZGenerational（保留非分代 ZGC）；诊断期同时去掉 THP/AlwaysPreTouch 减变量；仍崩则整体换 G1；加 -XX:ErrorFile=/pulsar/data/hs_err_%p.log 留崩溃报告到持久卷。
- 另见 UncleanShutdownDetectionImpl "Dirty file already exists"——反复崩溃的次生证据非根因。

## 自打包指南文档 + 官方解释勘误
- 用户问"3G 镜像自己打包麻烦不？官方有解释吗"。产出：04-Middleware-Linux/Pulsar-ARM64-glibc镜像自打包指南-2026-09.md。
- 重要勘误：官方 3.3+/4.0 镜像基座也是 Alpine（官方 release 流程文档原文 docker pull alpine:3.21 for 3.3.x+；3.0.x 才是 ubuntu:22.04），官方靠三件事兜底 musl：gcompat 兼容层 + 自编 snappy + JLink Corretto(/opt/jvm)。此前"官方一直是 glibc 基座"的说法只对 3.0.x 成立，已向用户明确修正。
- 因此 Harbor musl 镜像有两种来历需鉴别（文档给了30秒命令）：官方retag（有gcompat+/opt/jvm布局，musl非根因，崩溃另有其因）vs 内部自建漏gcompat（musl裸奔=根因）。无论哪种，自打包glibc镜像都是最优解且兼作判决性实验（还崩则指向Corretto JIT）。
- 方案A（推荐）：清华镜像 bin tarball（纯Java架构无关）+ eclipse-temurin:21-jre-jammy 多架构基座 + 十几行 Dockerfile，20-40min，产物1.5-2GB；pulsar vs pulsar-all 差别=connectors/offloaders，给了tar -tzf核验命令。方案B官方源码构建不推荐（JDK21+磁盘20G+1h+且产物仍alpine）。
- 完整链路：build→当场验基座→save(堡垒机400M分卷)→load→retag推Harbor→helm --set images.*.tag 顺序滚 zk→bookie→broker。验收不变：3副本24h不崩；还崩则musl彻底排除，看hs_err frame指向libjvm.so与否。
