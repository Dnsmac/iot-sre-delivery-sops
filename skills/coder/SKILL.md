# CODER — 深度审查（五维 + 调用链）

**开场声明：** `[CODER] 已 Read coder skill，只读深度审查。`

> **定位**：在 `/code-review`（标准、快）之上的 **加严层**。  
> **默认**：不替代标准 Review；**按需**在 BUC Phase B 追加，或单独 `/coder` 运行。

---

## 与 `/code-review` 的分工

| 层级 | 命令/skill | 深度 | 耗时 |
|------|------------|------|------|
| 标准 | `/code-review` | diff + P0/P1 + 文档 | 短 |
| **加深** | **`/coder`** | **五张 R 表** + 调用链 | 中 |

**禁止**用「看起来没问题」代替 **R1～R5 表格**。

---

## 范围

- `git diff`（工作区 + 分支相对 merge-base）或 Phase A 交付包（无 diff 时的方案级审查）
- 对照 hotfix readme / 「改什么 / 影响面」
- **只读**；改代码须用户 **`批准修复`** 或 **`直接修 review 问题`**

---

**Verdict 规则**（对齐 BUC Phase C）：

| 条件 | Verdict |
|------|---------|
| P0/P1（含热路径读改写、旁路误伤、多余写放大） | **`需修改后再审`** → 触发 BUC Phase C 或用户 `批准修复` |
| 仅 P2/P3 | **`通过（含建议）`** |
| 五表齐、无 P0/P1 | **`通过`** |

---

## 审查动作（Agent 内部必做）

1. diff 中 **每一处** 新增/变更的 **外部方法调用**，向上追 1～2 层：写库？热路径？频率？
2. iot-server **默认** 生产：高并发、多实例、Reactive、突发流量
3. 对照 **「只改目标场景」**：旁路（未删除设备、非级联、冷路径）是否仍按原逻辑？
4. **R4 必列**「可写可不写」项，不得默认可合入

---

## 单独 `/coder`（无 BUC）

- 用户：`/coder` + 说明审查范围（当前 diff / 指定 commit / 方案+文件）
- 无 diff 时：Read 交付包 + 相关类，R3/R5 基于 **拟改** 路径

---

## `/bsp` 仅影响评估

- L0：`仅影响评估` 或 `coder方案` → Read 本 skill，**禁止编码**
- 输出 R1/R2 + 简要 R4（方案级），可无 R5 逐行 diff

---

## BUC Phase B 按需加深（见 `buc-orchestrator`）

| L0（/buc） | Phase B |
|------------|---------|
| 默认 | 先 `code-review`；**命中加深条件** → **同会话追加** `/coder` |
| `coder` | **仅** coder（省时间，小 diff 且你信得过标准项时） |
| `coder+` | code-review **+** coder（大改推荐） |
| `coder跳过` | 仅 code-review，不自动加深 |

**自动加深条件**（默认开启，命中任一条 → 标准 Review 通过后跑 coder）：

- 改动 **>3 文件** 或 **跨 2+ Maven 模块**
- 热路径（查询/写入 ES 索引/心跳/级联消费/MQ 订阅回调）
- 新增 **DB/Redis 写**、新 `@Scheduled` / 定时补偿

---

## 禁止

- 未填 R1～R5 称「深度审查完成」
- CODER 通过就跳过 T7 功能验收
- 同一 commit 范围 **重复全量** coder（BUC 已 coder+ 通过时；新 diff 用 Review 衍生 #n）

---

`用户指令 > coder > code-review > bsp-orchestrator`
