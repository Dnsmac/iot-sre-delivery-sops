## 2. 现象

| 现象 | 说明 |
|------|------|
| 6G / 8G 堆均「卡死」 | 接口超时、消息处理停滞；加内存仅多撑 1～2 天 |
| `jstat -gcutil` | Old **96.41%** 恒定；YGC≈FGC；FGCT **12406 s** |
| `jstack` | 319 线程，无明显死锁；大量 WAITING（GC 风暴特征） |
| `GC.class_histogram` | 1800 万 `JSONObject`、1800 万 `HashMap`、20 万 `JetLinksDeviceMetadata` |

**误判方向（排查过程中排除）**：

- ❌ 「设备数无限增长」→ MAT 证实 Operator **正好 5050 个**
- ❌ 「1800 万 HashMap = 1800 万 cache key」→ 是每台物模型 JSON 展开的内部节点
- ❌ 「单纯内存参数过小」→ 8G 下 Dominator 已占 78%
- ⚠️ RedisClusterManager / 心跳 10s（4 月分析）→ **相邻隐患**，非本次 5.7G Dominator

## 3. 排查过程（按时间顺序）

### 3.1 现场采样（无需 dump）

```bash
docker exec kh-iot-server-1 jstat -gcutil 7 1000 10
docker exec kh-iot-server-1 jstack 7 | head -300
docker exec kh-iot-server-1 jcmd 7 GC.heap_info
docker exec kh-iot-server-1 jcmd 7 GC.class_histogram | head -80
docker exec kh-iot-server-1 jcmd 7 GC.class_histogram | grep -E "HashMap|JSONObject|JetLinks|byte"
```

**判断**：Old 顶满 + FGC≈YGC → **堆泄漏或超大常驻集 + Full GC 风暴**，不是线程死锁。

### 3.2 抓堆（堡垒机限制）

```bash
docker exec kh-iot-server-1 jcmd 7 GC.heap_dump /application/static/upload/emergency-dump.hprof
# 约 11.2 GB 文件；堡垒机带宽限制难以整包下载
```

**对策**：本地 MAT 分析 `emergency-dump.hprof.gz`；或服务器 headless 生成 Leak_Suspects.zip（几 MB）。

### 3.3 MAT Dominator Tree（定因）

| 对象 | Retained |
|------|----------|
| `ExtendDeviceClusterConfiguration` | **6,078,323,032 B（≈5.66 GiB）** |
| 其余（EventBus、H2 MVStore 等） | 远小于此 |

**Path to GC Roots**（摘要）：

```text
ExtendDeviceClusterConfiguration（operatorCache）
  └── ExtendDeviceClusterConfiguration$1（ClusterDeviceRegistry 匿名子类）
        ├── registry ← HistoryMessageManagerImpl
        │     └── history-log-worker Thread（Java Local）
        ├── registry ← MqttServerDeviceGateway × N
        └── ExtendDeviceOperator × N
```

### 3.4 MAT OQL（验证「5000 台」疑问）

```sql
-- 不支持 COUNT(*)；用列表 + 状态栏行数
SELECT o.@objectId FROM org.jetlinks.pro.device.metadata.ExtendDeviceOperator o
-- 结果：Total 5,050 entries

SELECT o.@objectId, o.@retainedHeapSize FROM org.jetlinks.pro.device.metadata.ExtendDeviceOperator o
-- 单条：3,379,744 B（≈3.2 MB）～ 15,621,296 B（≈14.9 MB）
```

**闭环**：5050 Operator ≈ 5000 台设备；**key 没有失控，value 太胖 + 永不释放**。

### 3.5 代码定位（业务仓只读）

**泄漏点**：`khlinks-manager/kh-device/device-manager/.../ExtendDeviceClusterConfiguration.java`

```java
private final Map<String, Mono<DeviceOperator>> operatorCache = new ConcurrentHashMap<>();
// 无 maximumSize、无 TTL、注销事件未 invalidate
```

**放大路径**：

- `HistoryMessageManagerImpl.writeDeviceMessageToTs` → 每条历史补报 `registry.getDevice()`
- MQTT 网关、级联、数据流等共用同一 `DeviceRegistry`

**历史**：`DeviceMetadataAop` 曾在注销时 `operatorCache.remove`，但已 `@Deprecated` 且 `@Aspect` 关闭，逻辑未迁到新实现。

## 4. 根因（机制）

| 编号 | 机制 | 说明 |
|------|------|------|
| **H-1** | 无界 `operatorCache` | 每个被 `getDevice()` 且 Config 有 productId 的 deviceId **永久驻留** |
| **H-2** | Value 极胖 | 每台 `ExtendDeviceOperator` + 物模型 TSL → 3～15 MB retained |
| **H-3** | 无注销清理 | 设备删库/下线不 `remove`，旧 AOP 逻辑丢失 |
| **H-4** | 历史补报灌缓存 | `history-log-worker` 批量 `getDevice()` |
| H-5（副） | 心跳 10s | 加速上线/下线事件（4 月文档）；减缓填充速率，非 5.7G 主因 |
| H-6（副） | RedisClusterManager 修复7 | 订阅表增长；4 月 OOM 第一现场，本次非 Dominator |

### 4.1 「5000 台有限，为何 6G？」— 最终解释

```
5050 个 cache key（= 设备数）
× 每台 3～15 MB 物模型对象树（含 ~40 个 JetLinksDeviceMetadata、~3600 个 HashMap/台）
× 永不淘汰
≈ Dominator 5.7 GB
→ 8G 堆剩余 < 2G → Full GC 风暴 → 卡死
```

histogram 里 **204 万 metadata、1800 万 HashMap** 是 **5050 棵树上的枝叶**，不是 204 万台设备。

## 7. 教训 / 以后第一眼查什么

1. **6G/8G 都卡 + Old 长期 >90% + FGC≈YGC** → 先怀疑 **堆常驻集过大**，不是调 `-Xmx`。
2. **`class_histogram` 只能看「有什么类」**，定因必须 **heap dump + Dominator Tree**。
3. **设备数有限 ≠ 内存安全**：`有限 key × 胖 value × 不淘汰` 照样 OOM。
4. 数 Operator 用 **MAT Histogram `# Objects`** 或 OQL 列表行数，不要用 `COUNT(*)`。
5. 设备注册表类缓存：**必须有 maximumSize + TTL + 注销 invalidate**。

## 9. 面试 90 秒口径

> 现网 kh-iot-server 跑两三天就卡死，6G 和 8G 都一样。jstat 看 Old 区长期 96%，Full GC 次数几乎等于 Young GC。  
> 我抓了 heap dump，用 MAT 看 Dominator，发现 `ExtendDeviceClusterConfiguration` 一个对象占了堆的 78%。  
> 沿 GC Root 追到 `operatorCache`：无界 Map 缓存了 5050 个 DeviceOperator，和我们 5000 台设备数一致，但每台物模型在堆里占 3 到 15 MB，合计约 6G，把堆吃满了。  
> histogram 里上千万 HashMap 不是上千万设备，是每台物模型 JSON 展开的内部节点。  
> 修复方向是给 operatorCache 加 Caffeine 上限和过期、设备注销时 invalidate，历史补报不要每条都走 registry.getDevice；加内存只能推迟，不能根治。
