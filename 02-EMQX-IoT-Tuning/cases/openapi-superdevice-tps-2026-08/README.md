## 2. 瓶颈分层

| 类 | 根因 | 云端可做 |
|----|------|----------|
| **拓扑查询** | Caffeine TTL 仅 ~1s；miss 后多表/ registry 重链路；OpenAPI 未走部分 Redis 缓存 | 延长 TTL、二级缓存、减 miss 路径 |
| **E2E 读写/invoke** | 等设备 MQTT 回包占大头；`getDeviceMetadataNode` **每次重复解析大物模型**；权限/元数据可缓存 | 元数据节点本地缓存 + single-flight（36630）；权限缓存；去无必要 gRPC 回环（收益有限） |
| **测试方法** | 真 E2E 时并发不够会被误判；需区分「缓存命中 vs 真查库/真下发」 | JMeter 分接口压；记录命中率 |

## 4. 诚实结果口径

- **能讲清**：五接口各自差多少、为什么 E2E 和拓扑不是同一类瓶颈、36630 修的是「重复解析物模型」。  
- **不编造**：若复测数字未写入本仓，简历写「参与优化与验证设计」，不写「已全部达 100 TPS」。  
- **上限认知**：真等设备回包时，TPS ≈ 有效并发 / 平均 RT；设备侧不降延迟，云端微优化补不满 80% 缺口。

## 5. 30 秒口述

> OpenAPI 五接口压测，拓扑差一截、读写 invoke 差更多。我把问题拆成两类：拓扑是缓存 TTL 太短和 miss 后重查询；E2E 是每次重复解析大物模型再等设备回包。先做了物模型节点本地缓存和 single-flight，拓扑缓存单独调 TTL；并用分段耗时说明哪些必须端侧配合。
